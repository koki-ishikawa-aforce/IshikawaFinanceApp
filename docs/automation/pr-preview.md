# PR プレビュー配信

無人モード(`/issue-work`)が作った PR を人間がマージ判断するとき、コードやスクリーンショットではなく **実際に触れる画面** で確認できるようにする仕組み。

ワークフロー: `.github/workflows/pr-preview.yml`

## 全体像

1. `packages/web/` に変更がある PR が作られる / 更新されると、モック起動モード(`NEXT_PUBLIC_MOCK=1`)で web の Static Export をビルドする
2. 成果物を `gh-pages` ブランチの `pr-<番号>/` に置き、ブランチ全体を GitHub Pages へデプロイする
3. 配信 URL を PR にコメントする(同じコメントを書き換えるので、push のたびには増えない)
4. PR がクローズ / マージされると `pr-<番号>/` を削除して再デプロイする

配信される画面はモックデータで動くため、**API サーバーにもデータベースにも接続しない**。ログインも不要で、URL を開けばそのまま画面が出る。

- 既定のテーマは darling。`?mockRole=honey` を付けると honey になる。指定したロールはタブ単位で保持されるため、画面を移動してもテーマとデータは食い違わない
- 既定の世帯は「口座も登録済み」の状態。`?mockScenario=accounts-unregistered` を付けると、別銀行貯蓄口座と NISA 口座がまだ登録されていない世帯になり、設定 > 口座タブの追加ボタンなど未登録の人にだけ出る画面を触れる。ロールと同じくタブ単位で保持される
- fixture(`packages/web/src/mocks/`)を用意していない画面はエラー状態で描画される。用意済みの経路は `src/mocks/resolve.ts` の一覧が正

URL の形: `https://<オーナー>.github.io/<リポジトリ名>/pr-<番号>/`

## セットアップ(リポジトリ設定)

ワークフローは実行時に GitHub Pages の有効化を API で試みる。ただし Pages 設定と環境の変更には管理者権限が必要で、Actions の `GITHUB_TOKEN` には付与できないため、**通常はこの自動有効化は成功せず、下記の手動セットアップが必要になる**。有効化できなかった場合は**配信を省略して PR にその旨をコメントし、ワークフロー自体は成功で終わる**(プレビューが出ないことで PR の検証を止めないため)。ワークフローは設定の現状を読み取り(こちらは読み取り権限で可能)、手動セットアップが済んでいれば次の実行から配信する。

自動で有効化できなかったときは、リポジトリ管理者が手動で設定する:

1. リポジトリの **Settings** → **Pages** を開く
2. **Build and deployment** の **Source** を **GitHub Actions** にする
3. **Settings** → **Environments** → **github-pages** を開き、**Deployment branches** の制限を解除する(`No restriction`)
4. 次に PR が更新されたときから配信が始まる(すぐ試すなら対象 PR に空コミットを push する)

3 を飛ばすと配信だけが必ず失敗する。Pages を有効にすると `github-pages` 環境が自動で作られ、既定では**デフォルトブランチからのデプロイしか許可されない**一方、このワークフローは PR 上で走る(参照は `refs/pull/<番号>/merge`)ため、制限に掛かって弾かれる。

> **公開範囲**: GitHub Pages の公開範囲はリポジトリの公開設定に従う。パブリックリポジトリではプレビューも誰でも見られる状態になる。配信されるのはモックの固定データのみで、実際の家計データは含まれない。

## 置き場所ブランチ(`gh-pages`)

Pages の Actions デプロイ(`actions/deploy-pages`)は**サイト全体を毎回置き換える**ため、PR ごとのサブパスを並存させるには全 PR 分の現状を保持する場所が要る。それが `gh-pages` ブランチで、次の性質を持つ:

- 中身はビルド成果物だけで、ソースは入らない。**人が編集する対象ではない**
- 毎回 1 コミットの孤児コミットで force push する(履歴を溜めるとビルド成果物でリポジトリが肥大するため)
- サイト直下の `index.html` は現存するプレビューの一覧。直リンクが分からなくなったときの入口

PR 間で同時に push すると互いのプレビューを消してしまうため、ワークフローは `concurrency: pr-preview` でリポジトリ全体を 1 本ずつ直列化している。

## 制約

- **`packages/web/` に変更が無い PR では配信されない**。画面が変わらない PR にプレビューは要らず、1 PR あたり 4 分前後の実行枠を使うため、ワークフローの `paths` で対象を絞っている。途中まで web を触っていた PR が最終差分から web を落として閉じた場合だけ配信物が残るので、サイト直下の一覧から気づいて手動で消す
- **fork からの PR では配信されない**。`GITHUB_TOKEN` が読み取り専用になり `gh-pages` へ push できないため、ジョブごとスキップする
- **プレビューはビルド時点の固定**。モックデータを書き換える操作(登録・削除など)を行っても保存はされず、リロードで元に戻る
- ベースパスはビルド時に `NEXT_PUBLIC_BASE_PATH` で差し込む。未設定なら空文字なので、通常のビルド・ローカル開発・VRT の挙動は変わらない

## 止め方・トラブル時

- **一時的に止める**: `.github/workflows/pr-preview.yml` の `on:` を `workflow_dispatch:` のみに変更する
- **完全に止める**: ワークフローを削除し、`gh-pages` ブランチを削除する。Settings → Pages の Source を None に戻す
- **プレビューが古い**: 対象 PR の最新 push で PR preview ワークフローが成功しているかを確認する。ブラウザのキャッシュが残る場合はスーパーリロードする
- **書体が違って見える**: 丸ゴシック(Zen Maru Gothic)はビルド成果物に同梱され、`_next/static/media/*.woff2` から読まれる。ここが 404 になっていると全画面が代替書体になり、見た目の判断を誤る。ブラウザの開発者ツールのネットワークタブで woff2 が 200 で返っているかを確認する
- **クローズ済み PR のプレビューが残っている**: そのワークフロー実行が失敗している。`gh-pages` ブランチから該当ディレクトリを削除して push すれば次のデプロイで消える
