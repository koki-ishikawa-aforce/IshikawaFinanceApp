## 1. メール取込系 📩

### 1.1 SMBC 通知メール

- 日次メール取込バッチが起動された（EventBridge スケジュール）
- 過去 5 日以前のメールが Gmail API で一括取得された（重複は Gmail message ID で除外）
- SMBCカード利用通知メールが受信された
- SMBC銀行入金通知メールが受信された
- SMBC銀行出金通知メールが受信された
- SMBCカード引落確定通知メールが受信された
- カード返金通知メールが受信された
- メール本文がパースされ取引候補が抽出された
- メールパースに失敗し取込保留になった
- Gmail message ID で同一メールの二重受信が検出され重複として除外された

### 1.2 Amazon 注文確認メール

- Amazon 注文確認メールが受信された
- Amazon 注文確認メールから商品情報（商品名・カテゴリ・金額）が抽出された
- Amazon 注文と SMBC カード利用通知が金額・タイミングで突合された

## 2. 取引（決済・収入）系 🟧

### 2.1 収入（世帯外から入る）

- 給与が振り込まれた（SMBC銀行入金）

経費精算入金は §10「経費（家計分析対象外）系」で扱う。

### 2.2 支出（世帯外へ出る）

- カード決済が発生した（SMBCカード利用通知。発生主義で支出 + 未払金計上）
- 銀行振込で家賃が支払われた（SMBC銀行出金）
- 銀行引落で公共料金が支払われた（水道・電気・ガス）
- 銀行引落で通信料が支払われた

各支出はカテゴリ（住居・光熱・通信／食費／娯楽／その他）と費用区分（世帯／個人(夫)／個人(妻)／経費(会社)）に自動分類される。
費用区分が「経費(会社)」の取引は家計分析（ゴール①）から除外。詳細は §10。

## 3. 資金移動系 🟧

- SMBC→NISA口座（SBI / 楽天証券）への積立振込が発生した（→ NISA積立累計に加算）
- SMBC→別銀行貯蓄口座への振込が発生した（→ シャドウ口座残高に加算）
- 別銀行貯蓄口座→SMBC への入金が発生した（取り崩し補填等。SMBC側の入金通知で受領）
- カード引落でSMBC銀行残高減・クレカ未払金消込が発生した

## 4. クレカ未払金系 🟧

- カード利用が未払金として計上された（決済発生時、支出計上と同時）
- カード引落で未払金が消込された（引落確定時）

## 5. 自動分類系 🟥

学習データは **完全個人別（F-1）**（per-user）。加盟店名 → カテゴリ／費用区分／経費種別 を **独立に学習**（フィールド独立、T-2）。Amazon 取引は加盟店名「AMAZON.CO.JP」を学習対象外とし、商品カテゴリをキーに学習する **特例フロー（X-1）** を持つ。詳細は シナリオC（06）参照。

### 5.1 通常加盟店の自動分類

- 加盟店名で学習データが検索された
- 取引のカテゴリが学習済み加盟店ルールから自動分類された
- 取引の費用区分が学習済み加盟店ルールから自動分類された
- 取引の経費種別が学習済み加盟店ルールから自動分類された（ジム / 交通費 / AI 利用 等、加盟店名で判別可能なもの）
- 学習データに無い加盟店の取引が「未分類」フラグで取り込まれた
   未学習加盟店時のデフォルト: カテゴリ=未分類、費用区分=カード所有者の「個人(本人)」、経費種別=NULL

### 5.2 Amazon 取引の特例フロー（商品キー学習）

- Amazon 注文と SMBC カード利用通知が金額・タイミングで突合された
- Amazon 商品キー（商品カテゴリ）で学習データが検索された
- Amazon 商品キーから経費種別／カテゴリ／費用区分が自動分類された
- Amazon 商品キーが学習データに無く、未分類フラグで取込まれた
- Amazon 注文の商品情報から経費種別判定不能と判定された
- Amazon 注文と SMBC カード利用通知の突合タイムアウトが検知された（双方向 3 日）

### 5.3 学習データ更新（手動修正の副作用）

- ユーザーの手動修正が学習データに反映された（新規ルール登録）
- ユーザーが学習データの上書きを承認した（既存ルール変更、L-4 の「以後このルールに従う」確認時）
- ユーザーが学習データを上書きせず今回のみ修正した（L-4 の「今回限り」確認時）
- 加盟店の自動分類が無効化された（手動、修正画面の「この加盟店は学習しない」チェック）
- 加盟店の自動分類が再有効化された
- 過去の未分類取引への学習適用がユーザーに確認された（J-3 確認ダイアログ）
- 過去の未分類取引が一括で再分類された（対象は本人の未分類取引のみ）
- Amazon 商品キー → 分類のマッピングが学習データに登録された

### 5.4 学習データ構造の規約

学習データのスキーマ（per-user、フィールド独立 T-2）:

```
merchant_classification_rules (per-user)
├─ merchant → category（カテゴリ）
├─ merchant → cost_division（費用区分、4 値全て）
├─ merchant → expense_type（経費種別、経費(会社) 時のみ）
└─ merchant → disabled_flag（学習無効化）

amazon_product_classification_rules (per-user)
├─ product_category → category
├─ product_category → cost_division
└─ product_category → expense_type
```

※ 学習は memorization 方式（ユーザー手動修正の蓄積）。明示的なルール編集 UI は持たない。手動修正は「§8 訂正・例外系」で扱い、その副作用として学習データが更新される。
※ F-1 採用により、夫婦の学習は一切波及しない（同一加盟店でも夫婦各自が初回未分類で個別学習）。

## 10. 明細確定（CSV/PDF 取込・差額管理）系 📥⚠️

### 10.1 差額検出・暫定計上

- カード引落確定通知の金額と、当月利用通知合計の差額が検出された
- 差額が「不明（その他）」として家計分析に一時計上された（=暫定状態）

### 10.2 明細取込（CSV／PDF・カード明細・銀行明細 両方）

- 明細 CSV または PDF（カード or 銀行）がアップロードされた
- アップロードされた PDF が Lambda 内で Claude API（Anthropic SDK）を介して CSV 形式に変換された
- PDF→CSV 変換に失敗し、ユーザーに通知された
- CSV のフォーマット検証に成功し取込が完了した
- CSV のフォーマット検証に失敗し取込が中止された
- CSV から抽出された取引が、既存の通知由来取引と「日付・金額・加盟店名の3項完全一致」で突合され重複が除外された
- CSV にしか無い取引が新規に取り込まれ、自動分類された
- CSV 取込により月次差額（不明）が確定し、月次レポートが「暫定」→「確定」に切り替わった

明細取込は通知対象外（公共料金のクレカ払い・ガソリン・ETC・10円以下 等）の補完が主目的。
PC は CSV、スマホは画面印刷 PDF を想定。**PDF と CSV は形式がほぼ一致しているため Claude による変換が可能**（実証検証で行数・金額完全一致、加盟店名 NFKC正規化後 96% 一致を確認）。変換後は CSV と同一フローを通る（CSV を正式な内部表現とする）。
**変換手段**: Lambda 内で Anthropic SDK（Claude API）を直接呼び出し。月数件の従量課金で約 30 円程度。
銀行明細はメール通知に穴があった場合の保険。

## 11. 通知配信系 📱📧

LINE を主チャネル、メールはフェイルセーフ。LINE 上には明細を載せず、サマリ＋アプリリンクのみ送る。

### 11.1 LINE 通知

- CSV 取込リマインダーがプレーンテキスト形式で毎月5日から CSV 取込完了まで毎日 LINE 共通トークルームに配信された（SMBC カード明細・SMBC 銀行明細のダウンロード URL ＋ アプリのアップロード画面 URL を含む）
- CSV 取込完了が検知され、当月のリマインダー送信が停止された
- 月次レポートのサマリ（世帯費用カテゴリ別・NISA積立累計・残高推移）が Flex Message のリッチカード形式で LINE 共通トークルームに配信された（CSV取込・分析完了後 = 月次レポートが「CSV確定」状態に昇格したタイミング、アプリへのリンク付き）
- 月次レポートの本人サマリ（個人費用合計・経費(会社)合計）が Flex Message のリッチカード形式で LINE 各個人 DM に配信された（同上タイミング、アプリへのリンク付き）
- OAuth 失効通知が該当する本人の LINE 個人 DM に配信された
- LINE 通知の送信に失敗した（リトライ対象）
- LINE 配信ログが保存された（送信した payload を json で保持。発火タイミング: 月次レポート配信／リマインダー配信／OAuth 失効通知配信／フェイルセーフメール送信。シナリオC 確定。スナップショット廃止に伴う配信時点の値の凍結用途）

### 11.2 メール（フェイルセーフ）

- LINE が連続 N 回送信失敗したことを検知し、致命的エラー通知メールが夫婦各自に送信された
- フェイルセーフメールの送信に失敗した

※ メールフェイルセーフのトリガーは **「LINE 連続送信失敗」のみ**（システム障害時の最終手段）。OAuth 失効や個別の致命的エラー（CSV 取込連続失敗・月末バッチ失敗 等）は LINE で通知し、LINE 自体が止まった時だけメール経路へエスカレーションする。

## 12. 経費（家計分析対象外）系 🟧⚪

### 12.1 経費取引の暫定計上（カード利用時）

- 取引が経費(会社)としてマークされ、経費種別（ジム/新聞図書/AI利用/交通費/その他）に紐付けられた
- 経費種別の月次累計が更新された
- 経費種別の月次累計が予算上限に達した
- 上限超過分が **先着順** で「個人(本人)」として子取引に分割された（月内の経費取引を時系列順に充当、上限ありの種別のみ）
- カード利用が立替経費として手動でマークされた（自動判別が外れた場合の補正）
- 取引のフラグが「経費(会社) ↔ それ以外」で切り替えられた（誤分類の補正）
- 取引修正により当月の経費按分が自動再計算された（過去取引を経費 ↔ 個人切替・経費種別変更・削除等のたびに、当月内の先着順按分を再評価）
- 経費精算管理タブが閲覧された（本人のみ可視。経費取引一覧と当月累計を表示。進捗バーなし、合計のみ）

### 12.2 月次経費精算サイクル

- 経費種別の月次累計が月初（毎月1日 0:00）にリセットされた
- 経費精算入金が会社から SMBC に到着した（給与とは別、当月分が翌月15日頃）
- 経費精算入金額と当月の暫定経費合計が突合された
- 突合差額（会社が認めなかった「不認定分」）が「個人(本人)」費用に自動振替された
- 月次経費精算サイクルが確定し、月次レポートが「最終確定」状態に昇格した

### 経費(会社)フラグの取引の扱い

- ゴール①（支出を目的別に把握）の集計から **除外**（暫定段階）
- 不認定分は「個人(本人)」費用として家計分析対象に **昇格**（最終確定段階）
- 月次レポートの「世帯費用 / 個人費用」表示から **除外**（暫定段階）／ **昇格分は反映**（最終確定段階）
- 一方で SMBC銀行残高推移・クレカ未払金管理には常に **反映**（実際にお金が動いているため）
- プライバシー: 本人のみ可視。相手は合計すら見えない

## 14. 改訂版で対象外としたもの

初版（48イベント）にあったが、改訂スコープでは扱わない:

- 現金・PayPay 関連の取引・資金移動
- 夫婦間の精算（夫が立替→妻に精算してもらう等）
- 定期取引のライフサイクル（メール通知で都度拾う運用）
- NISA評価額変動
- 予算超過アラート・異常支出検知
- 機械学習による自動分類精度向上（Phase 2 元案。改訂版では memorization 方式の学習のみを採用）
- 夫婦の目標合意・再設定・事前承認
- 目標資産額に対する分析

## 15. 重要な観察（改訂版）

- 「自動で集計できる」を主原則とするが、利用通知メールの仕様上、一部支出（公共料金・通信料・ガソリン・ETC・10円以下 等）は通知対象外。**完全自動 ≠ メール通知のみ** であり、月次の **CSV 取込で精度確定** するハイブリッド構成になる。
- 月次レポートには **CSV確定／最終確定** の 2 状態がある（シナリオC で暫定生成は廃止）。CSV 取込・分析完了で「CSV確定」に昇格して LINE 配信、経費精算入金との突合で「最終確定」に昇格（配信なし、値のみ更新）。
- **ダッシュボード・月次レポート画面はリアルタイム集計** に統一（シナリオC）。月末スナップショットは廃止し、配信時点の値の凍結は **LINE 配信ログ**（payload を json 保持）で代替。
- **学習データは完全個人別（F-1）**。夫婦の学習は一切波及しない。同じスーパーでも夫婦各自で初回未分類になる冗長は仕様（プライバシーと実装単純性を優先したトレードオフ）。
- **学習データはフィールド独立（T-2）**。加盟店名 → カテゴリ／費用区分／経費種別 を別々のマッピングで保持。「同じ加盟店でカテゴリは固定だが費用区分は揺れる」ケース（コンビニで昼食=個人 / 家族用買い物=世帯）に対応するため。
- **Amazon は加盟店名「AMAZON.CO.JP」を学習対象外** とする特例（シナリオC、X-1）。代わりに **商品カテゴリをキーに学習** する別テーブルを持つ。突合タイムアウトは双方向 3 日。
- 「**シャドウ口座**（別銀行貯蓄・NISA）」という概念で、SMBC外の残高を SMBC通知から派生的に追跡する仕組みが必要。SMBCを経由しない動きは手入力で補完する原則。
- **費用区分 4 値（世帯／個人(夫)／個人(妻)／経費(会社)）** のうち、経費(会社) は家計分析（ゴール①）から除外する一方、残高・未払金管理（ゴール②）には反映するという "二重ステータス" を持つ。
- **経費(会社) はさらに 5 種類の経費種別** に分かれ、上限管理の対象になる（ジム/新聞図書/AI利用 は上限あり、交通費/その他経費 は無制限）。**月次レポートは 3 段階状態（暫定→CSV確定→最終確定）** で、経費精算入金（翌月15日頃）との突合で最終確定する。
- **Amazon 注文確認メールを補助データソース** として取り込み、加盟店名「Amazon」では判別できない経費種別（特に新聞図書費）を商品情報から自動分類する。
- **プライバシールールが3段階**（世帯フルオープン／個人は明細本人のみ・合計相手可視／経費は本人のみ完全プライベート）になり、ダッシュボード・月次レポート両方の表示ロジックに影響する。
- 自動分類は **memorization 学習**（ユーザー手動修正の蓄積）。明示的なルール編集 UI は持たない。未学習加盟店は「未分類」で取り込み、ユーザー修正で学習データに自動反映される仕組み。
- **通知は LINE 主・メールはフェイルセーフ**。LINE 上にはサマリ＋アプリリンクのみ載せ、明細はアプリで本人が閲覧。共通トークルームには世帯部分のみ、個人部分は各個人 DM へ振り分けることでプライバシールールを担保する。
- メール（フェイルセーフ）は OAuth 失効や致命的エラー時のみ。Gmail は **取込側** で OAuth 連携、**送信側** は別経路（SMTP / SES 等）を想定。
- **アーキテクチャは AWS サーバーレス + Neon Free Tier の超低コスト構成**（月 30〜200円）。フロント = LIFF（Next.js Static Export → S3+CloudFront）、バックエンド = Hono on Lambda、DB = Neon、シークレット = Parameter Store、PDF→CSV = Claude API 直接呼び出し。メール取込は **1日1回のバッチ**（取込ラグ最大24時間、5日のCSV取込リマインダーには十分間に合う）。
