## 2. 集約境界の議論

### 2.1 集約サイズの妥当性

**各集約のサイズ評価:**

| 集約ルート | サイズ評価 | 理由 |
|---|---|---|
| 取引候補 | 適切 | 1 取引 1 集約。状態変化（通常 / Amazon突合 / タイムアウト未分類）が単一トランザクションで管理される |
| 日次メール取込バッチ | 適切 | バッチ単位でライフサイクルを管理。バッチ内の取引候補は別集約（取引候補）として独立 |
| 明細取込ジョブ | 適切 | 1 アップロード 1 ジョブ。状態遷移が単方向で管理可能なサイズ |
| 加盟店学習ルール | 適切 | ユーザー ＋ 加盟店名の 1 ルール 1 集約。T-2 フィールド独立の不変条件を 1 集約で完結 |
| Amazon商品キー学習ルール | 適切 | 加盟店学習ルールと同構造。X-1 特例を独立集約で分離したことで責務が明確 |
| 一括分類セッション | 適切 | CSV 取込 1 件につき 1 セッション。ただし List<未分類取引> が大量になる可能性あり → 件数が多い場合はページング（結果整合）で対処するのが現実的だが、不変条件（セッション単位の管理）は集約内で完結するため許容範囲 |
| 取引（家計分析） | 適切 | 1 取引 1 集約。分類状態の OR 表現で不変条件が集約内に閉じている |
| 月次レポート | やや大きい（許容） | 複数費用区分の合計・NISA・残高推移を 1 集約に内包。しかし「月次レポートの CSV確定 / 最終確定」という状態遷移の整合性は 1 集約で守るべき範囲であり、分割すると不変条件が崩れる。許容する |
| 口座（残高） | 適切 | 1 口座 1 集約。三井住友カードは未払金集約への参照（ID）のみを持ち、実体を内包しない設計が適切 |
| 三井住友カード未払金集約 | 適切 | 「当月未払金合計 = Σ エントリ」という不変条件を 1 集約で守る。エントリ数は月内カード利用件数に限定されるため過大にならない |
| 月次経費サイクル | 適切 | 月次・ユーザー単位の 1 集約。経費種別累計リストと按分子取引参照リストを内包するが、「累計 ≤ 上限」という不変条件の整合性はこの範囲で完結する |
| 按分子取引 | 適切 | 上限超過時の 1 件の派生取引 1 集約。親取引IDを保持するが親集約の実体を参照しない（ID のみ） |
| 経費精算入金 | 適切 | 1 入金 1 集約。突合状態の遷移が集約内に閉じている |
| アプリユーザー | 適切 | 1 ユーザー 1 集約。Phase 進捗を内包するが、Phase ごとの順序強制（SectionA → SectionB）が 1 集約で守るべき不変条件のため適切 |
| 配信メッセージ | 適切 | 1 メッセージ 1 集約。送信ライフサイクル（予約 → 送信 → 成功 / 失敗 / スキップ）が集約内に閉じている |
| LINE配信ログ | 適切 | 1 送信記録 1 集約。冪等性キーで重複を防ぐ。変更不可の監査記録として扱う |
| フェイルセーフメール | 適切 | 1 メール 1 集約。送信ライフサイクルが集約内に閉じている |
| カテゴリマスタ | 適切 | 1 カテゴリ 1 集約。改名履歴を内包するが、カテゴリ単位の管理に閉じている |
| 経費種別マスタ | 適切 | カテゴリマスタと同構造。1 経費種別 1 集約 |
| 月次上限 | 適切 | ユーザー ＋ 経費種別の 1 設定 1 集約。「上限あり OR 無制限」の状態が 1 集約で管理される |
| Phase0設定値 | 許容（やや特殊） | LINE_Channel設定・LINE_Webhook設定・許可リスト設定という 3 要素を 1 集約に内包。「三要素が揃って初めて運用可能」という不変条件を守るためにまとめることは正当。ただし将来的に各要素が独立して更新されるケースが増えた場合は分割を検討する |

**結論:** 21 集約のサイズはいずれも妥当。月次レポートと Phase0設定値はやや大きい傾向があるが、不変条件の整合性を守るために必要な範囲として許容する。

### 2.2 集約間参照は ID か

全集約の参照方式を検査した。以下の点について確認:

**OK（ID参照で完結）:**

|---|---|---|
| 口座（三井住友カード）→ 三井住友カード未払金集約 | `三井住友カード未払金集約ID`（ID のみ）| OK |
| 取引（家計分析）→ カテゴリマスタ | `カテゴリID` | OK |
| 取引（家計分析）→ 経費種別マスタ | `経費種別ID` | OK |
