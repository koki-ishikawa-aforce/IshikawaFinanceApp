# ユビキタス言語: 残高・資産推移管理

> 2026-07-24 改訂: §2 の未払金計上・引落消込に、取引取込から届くトリガーイベント名（`カード利用取引取込イベント` / `引落確定通知受信イベント`、08a §3）を明記（#286）。

> Phase 3.5 反映: 別銀行貯蓄口座に `銀行名`、NISA 口座に `証券会社名` 属性を追加（[2026-05-01-phase3.5-ux-ui-design.md §14.2-3](../superpowers/specs/2026-05-01-phase3.5-ux-ui-design.md)）。表示用の per-user 編集可能属性。

> 親: [docs/domain/08-ubiquitous-language.md](./08-ubiquitous-language.md)
> サブドメイン: Core（07-bounded-contexts.md §2.2）

## 責務

SMBC 銀行残高・三井住友カード未払金・別銀行貯蓄口座残高（シャドウ）・NISA 積立累計（シャドウ）の 4 軸を、取引・資金移動・手入力を発生主義で反映して時系列に追跡する。経費(会社) 取引も含む全取引を反映する（家計分析と扱いが異なる軸）。資金移動の用途判別（給与／経費精算入金／NISA積立／別銀行戻し）は本コンテキスト内で完結する（§1.1.4 確定）。別銀行貯蓄口座の残高鮮度の根拠データ（最終更新日時）を保有し、家計分析が画面表示時の判定に借用する。

## 1. データ（data）

```
// 本コンテキストの中核は「口座（残高）」と「未払金」の 2 系統の集約。
// 別銀行貯蓄口座と NISA 積立累計はシャドウ口座として SMBC 取引から派生して動く。

// クロスコンテキスト参照（ID のみ借用）
// referenced from: オンボーディング・認証
data ユーザーID = 文字列
// referenced from: 家計分析
data 取引ID = 文字列
// referenced from: 経費精算
data 経費精算入金ID = 文字列

// 共通語彙の借用
data 金額 = 整数
data 発生日時 = 日時
data 所有者 = 夫 OR 妻 OR 共有

// --- 口座マスタ参照（本コンテキスト内で持つ） ---

// aggregate root
data 口座 = SMBC銀行口座 OR 三井住友カード OR 別銀行貯蓄口座 OR NISA口座

data 共通口座属性 = 口座ID
   AND 所有者ユーザーID
   AND 口座種別
   AND 登録日時
   AND アクティブ状態
   AND 版数  // 楽観ロックのトークン（#459）。読み出したときの状態を表し、保存時にこの版と一致するときだけ書き込む

data 口座種別 = SMBC銀行 OR 三井住友カード OR 別銀行貯蓄 OR NISA
data アクティブ状態 = アクティブ OR 非アクティブ
data 非アクティブ = 非アクティブ化日時 AND 非アクティブ理由
data 版数 = 非負整数  // 保存が成功するたびに 1 進む。読み出しから保存までに他の更新が入ると不一致になり、後勝ちを拒否する

data SMBC銀行口座 = 共通口座属性 AND SMBC残高
data 三井住友カード = 共通口座属性 AND 三井住友カード未払金集約参照
data 別銀行貯蓄口座 = 共通口座属性 AND 銀行名 AND 別銀行貯蓄残高 AND 残高鮮度根拠
data NISA口座 = 共通口座属性 AND 証券会社名 AND NISA積立累計

// Phase 3.5 追加: 表示用の銀行名・証券会社名（per-user, 編集可）
data 銀行名 = 文字列  // 例: 「楽天銀行」「住信SBIネット銀行」。オンボーディング Phase 2-B で初期入力、設定画面で編集可
data 証券会社名 = SBI証券 OR 楽天証券 OR その他証券会社  // オンボーディング Phase 2-B で選択、設定画面で編集可
data その他証券会社 = 文字列  // ユーザー入力の任意文字列（例: 「マネックス証券」）

data 三井住友カード未払金集約参照 = 三井住友カード未払金集約ID

data 残高鮮度根拠 = 最終更新日時
// referenced from: 家計分析（鮮度評価ロジックは家計分析側、本コンテキストは最終更新日時のみ供給）

// --- SMBC 銀行口座残高 ---

data SMBC残高 = 現在残高
   AND 初期残高
   AND 初期残高基準時刻
   AND 最終更新日時
   AND List<反映済み引落確定通知ID>  // #388: 引落消込の残高反映を冪等にする記録

data 現在残高 = 整数
data 初期残高 = 整数
data 初期残高基準時刻 = 日時  // 論点9: ユーザー入力時点

// --- 三井住友カード未払金（集約） ---

// aggregate root
data 三井住友カード未払金集約 = 三井住友カード未払金集約ID
   AND 口座ID
   AND 当月未払金合計
   AND List<未払金エントリ>
   AND 最終消込日時?

data 三井住友カード未払金集約ID = 文字列

data 未払金エントリ = 計上中エントリ OR 引落消込済みエントリ
data 計上中エントリ = エントリID AND 取引ID AND 計上日時 AND 金額
data 引落消込済みエントリ = エントリID AND 取引ID AND 計上日時 AND 消込日時 AND 金額 AND 引落確定通知ID

data エントリID = 文字列

// --- 別銀行貯蓄残高（シャドウ口座） ---

data 別銀行貯蓄残高 = 現在残高
   AND 初期残高
   AND 初期残高基準時刻
   AND 最終更新日時
   AND List<シャドウ口座更新>

data シャドウ口座更新 = SMBCからの振込加算 OR SMBCへの振込減算 OR 取り崩し手入力 OR 残高補正手入力
data SMBCからの振込加算 = 取引ID AND 加算金額 AND 反映日時
data SMBCへの振込減算 = 取引ID AND 減算金額 AND 反映日時
data 取り崩し手入力 = 入力者ユーザーID AND 取り崩し金額 AND 入力日時 AND メモ?
data 残高補正手入力 = 入力者ユーザーID AND 補正前金額 AND 補正後金額 AND 入力日時 AND メモ?

// --- NISA 積立累計（シャドウ口座） ---

data NISA積立累計 = 現在累計
   AND 初期累計
   AND 初期累計基準時刻
   AND 最終更新日時
   AND List<NISA積立累計更新>

data NISA積立累計更新 = NISA積立加算 OR NISA積立補正手入力
data NISA積立加算 = 取引ID AND 加算金額 AND 加算日時 AND 振込先証券会社
data NISA積立補正手入力 = 入力者ユーザーID AND 補正前累計 AND 補正後累計 AND 入力日時 AND メモ?
// #458: 積立累計は加算しかされない軸のため、二重加算・桁の打ち間違いを戻す手段がこれになる
// （初期累計を下げて辻褄を合わせると「始めた時点でいくら積み立てていたか」の記録が壊れる）
data 振込先証券会社 = 証券会社名  // Phase 3.5: 同じ型を使用（編集可となったため列挙ではなく証券会社名 data で表現）

// --- 入金用途判別（§1.1.4: 残高・資産推移管理に閉じ込める） ---

data 入金用途判別ルール = 銀行入金用途判別ルール
data 銀行入金用途判別ルール = 勤務先入金判別ルール AND 別銀行戻し判別ルール

// OQ-21（2026-07-24 確定）: 給与と経費精算入金は同一の勤務先から同一の摘要で入金されるため、
// 振込元名・摘要では判別できない（実調査で確認）。入金日と金額の 2 シグナルで判定し、
// 両者が一致したときのみ自動確定、矛盾したときは手動確認に倒す。
data 勤務先入金判別ルール = 勤務先振込元名パターン AND 給与支給日窓 AND 給与判別閾値金額
data 勤務先振込元名パターン = 正規化済み振込元名  // NFKC + 長音統一 + 空白圧縮の後に比較（OQ-7）
// 勤務先振込元名パターンの保管先は下の勤務先振込元名簿（#448 / OQ-61）。給与はひとりずつ
// 受け取るものなので利用者ごとに持つ（世帯にひとつだと夫婦の勤務先が別々のとき、片方の給与が
// 毎回手動確認待ちに落ちる）
data 給与支給日窓 = 月内基準日  // 既定 21 日。以降を給与シグナル、以前を経費精算シグナルとする
data 給与判別閾値金額 = 金額  // 既定 25 万円。以上を給与シグナル、未満を経費精算シグナルとする
data 別銀行戻し判別ルール = 振込元名パターン  // 振込元 = 別銀行貯蓄口座

data 入金用途判別結果 = 給与判別 OR 経費精算入金判別 OR 別銀行戻し判別 OR 用途不明
data 判別経路 = 自動判別 OR 手動確認  // 確定した用途がどちらで決まったか（#390。ルールの精度を後から検証するために保持する）
data 給与判別 = 取引ID AND 判別日時
data 経費精算入金判別 = 取引ID AND 経費精算入金ID AND 判別日時
data 別銀行戻し判別 = 取引ID AND 判別日時
data 用途不明 = 取引ID AND 判別日時 AND 暫定処理

data 暫定処理 = 手動確認待ち  // 2 シグナルが矛盾する入金（例: 月内上中旬の 25 万円以上）はユーザーの判別を待つ（OQ-21、2026-07-24 改訂。旧: 25 万円以上は給与扱いとする保守処理）

// --- 勤務先振込元名簿（#448 / OQ-61。判別ルールの入口の保管先） ---

// aggregate root（利用者ごとに 1 つ）
data 勤務先振込元名簿 = 利用者ID AND List<勤務先振込元名登録>
data 勤務先振込元名登録 = 正規化済み振込元名 AND 表示用振込元名 AND 登録日時 AND 由来取引ID
data 表示用振込元名 = 振込元名  // 明細に載る生の表記。利用者が自分の明細と突き合わせるために残す
// 登録経路は「実際に届いた入金から候補を出して選んでもらう」1 本（OQ-61 ①）。設定画面での
// 手入力は作らない。相手の勤務先の振込元名は相手には見えない（個人に閉じる）

// --- 残高変動イベントの内部表現 ---

data 残高変動 = 入金変動 OR 出金変動 OR 引落消込変動 OR 手入力変動

data 入金変動 = 口座ID AND 取引ID AND 金額 AND 発生日時 AND 入金用途判別結果
data 出金変動 = 口座ID AND 取引ID AND 金額 AND 発生日時 AND 出金用途
data 引落消込変動 = 口座ID AND 引落確定通知ID AND 消込合計金額 AND 発生日時
data 手入力変動 = 口座ID AND 入力者ユーザーID AND 金額 AND 発生日時 AND 手入力種別

data 出金用途 = カード引落用 OR 別銀行振込用 OR NISA積立用 OR その他出金
data 手入力種別 = 取り崩し記録 OR 残高補正 OR 積立累計補正

// --- 残高変動履歴（#398。資産の推移グラフが読む正） ---

// aggregate root
data 残高変動履歴エントリ = 履歴エントリID
   AND 残高軸
   AND 口座ID
   AND 変動後の値
   AND 発生日時
   AND 由来イベントID

data 残高軸 = SMBC銀行残高 OR 別銀行貯蓄残高 OR NISA積立累計 OR カード未払い合計
// 資産の推移グラフが描く 4 本の線に対応する。口座種別と 1:1 で対応するが、
// 三井住友カードだけは残高ではなく未払い合計を追うため別概念として持つ

data 由来イベントID = ドメインイベントの識別子
// 同一の（残高軸, 由来イベントID）は 1 件だけ。イベント配信は at-least-once のため、
// 同じ変動が二度届いてもグラフに点が重ならないようにする冪等キー

// 月次レポート（08c）の残高推移パート・NISA積立累計は、本履歴から写し取った
// **CSV 確定時点の凍結値**（#398 で OQ-53 ③ を改訂。LINE の月次サマリはこの値を読む）。グラフの正は本履歴側にある

// --- 残高鮮度（家計分析が借用する根拠データ） ---

data 残高鮮度供給 = 口座ID AND 最終更新日時
// 経過日数の閾値（判定基準）は本コンテキストには置かない。単一ソースは家計分析側（08c / OQ-44）

data 経過判定基準 = 経過判定基準日数  // しきい値は本コンテキストでは保有せず、家計分析が判定する
```

## 2. 振る舞い（behavior）

```
// --- 残高更新（取引由来） ---

behavior 取引で口座残高を更新する = 取引ID AND 取引種別 AND 金額 AND 発生日時 -> 残高変動 AND 口座残高更新イベント
// 事前: 取引が（自動分類で or 未分類で）取り込まれた
// 事後: 経費(会社) 取引も含む全取引を反映する（家計分析と扱いが異なる）

behavior 取引で未払金を計上する = 取引ID AND 金額 AND 発生日時 -> 未払金エントリ AND 未払金計上イベント
// 事前: 取引種別 = カード利用
// 事前: トリガーは取引取込の「カード利用取引取込イベント」（08a §3）
// 事後: 計上中エントリとして三井住友カード未払金集約に追加される

behavior 引落確定通知で未払金を消込する = 引落確定通知 AND 計上中エントリリスト -> List<引落消込済みエントリ> AND 未払金消込イベント AND 引落消込変動
// 事前: 引落確定通知が取引取込から渡された（トリガーは「引落確定通知受信イベント」。08a §3）
// 事後: 計上中エントリが引落消込済みエントリに遷移し、SMBC 残高が減算される
// 注（#388）: 消込（未払金集約）と残高反映（口座集約）は別集約への順次保存で、間で失敗すると
//   消込済みなのに残高が未反映のまま残る。呼び出し側は同一通知の再受信で下の
//   「引落消込を SMBC 残高へ反映する」まで必ず進め、再実行で回復させる（OQ-43）

behavior 引落消込をSMBC残高へ反映する = 口座ID AND 引落消込変動 -> SMBC残高 AND 口座残高更新イベント
// 事前: 口座がアクティブ（非アクティブ口座への残高変動は適用しない）
// 事後: 消込合計金額だけ現在残高が減算され、引落確定通知IDが反映済みとして記録される
// 事後: 反映済みの引落確定通知の再反映は拒否される（冪等。反映順に関わらず過去の通知も拒否する）

// --- 入金用途判別（本コンテキストに閉じる） ---

behavior 入金用途を手動で確定する = 用途不明 AND 入金用途判別結果 AND 操作者ユーザーID -> 入金用途判別結果 AND 入金用途判別イベント
// 事前: 操作者 = 入金の帰属ユーザー本人（給与・経費精算入金は個人に閉じる。#390）
// 事前: 用途不明（暫定処理 = 手動確認待ち）の入金のみ。別の用途への変更は不可（単方向）
// 事後: 判別経路 = 手動確認 として確定する
// 事後: 同じ用途での再確定は冪等に成功し、未了だった反映（シャドウ残高・経費精算入金到着イベント）をやり直せる

behavior 勤務先振込元名を登録する = 入金用途判別結果 AND 操作者ユーザーID AND 勤務先振込元名簿 -> 勤務先振込元名簿
// 事前: 操作者 = 名簿の所有者本人 かつ 入金の帰属ユーザー本人（#448 / OQ-61）
// 事前: 入金用途判別結果 = 給与判別 または 経費精算入金判別（勤務先からの入金として確定済み）
// 事後: 正規化済み振込元名が名簿に載り、以後の判別で勤務先入金として扱われる
// 事後: 既に載っている振込元名の再登録は冪等（登録日時・表示用振込元名を据え置く）
// 注: 「入金用途を手動で確定する」と同時に選べる。用途の確定を保存できたあとに登録する
//     （確定しなかった入金の振込元を覚えると、以後その振込元が本人の確認を経ずに倒れる）

behavior 銀行入金の用途を判別する = 入金変動 AND 銀行入金用途判別ルール -> 入金用途判別結果 AND 入金用途判別イベント
// 事前: SMBC 銀行入金通知メールから派生した入金変動
// 事後: 勤務先振込元名パターンは判別する利用者の勤務先振込元名簿から取る（#448 / OQ-61）
// 事後: 名簿が空（勤務先を一度も登録していない）→ 別銀行戻しのみ判別し、残りは用途不明。
//       最初の 1 件を手動確認の窓口で確定するときに名簿へ登録され、以後は自動確定に乗る
// 事後: 勤務先入金は入金日シグナル（給与支給日窓）と金額シグナル（給与判別閾値金額）を突き合わせる
// 事後: 2 シグナル一致 → 給与判別 または 経費精算入金判別 を確定
// 事後: 2 シグナル矛盾 → 用途不明（暫定処理 = 手動確認待ち）。自動確定はせずユーザーの判別を待つ
// 事後: 給与判別 → 残高加算のみ
// 事後: 経費精算入金判別 → 経費精算へ「経費精算入金到着イベント」を発火
// 事後: 別銀行戻し判別 → 別銀行貯蓄口座から戻し扱いで両口座を更新

// --- シャドウ口座更新 ---

behavior 別銀行貯蓄残高をSMBC振込で加算する = 出金変動 AND 別銀行貯蓄口座 -> シャドウ口座更新 AND 別銀行貯蓄残高更新イベント
// 事前: 出金用途 = 別銀行振込用
// 事後: 別銀行貯蓄残高の最終更新日時が更新される
// 注（#415 / OQ-1(1) の実メール調査）: **銀行出金通知メールは届いていない**（実運用の観察）。
//   出金変動をメール起点で作ることはできないため、本 behavior と「NISA積立累計をSMBC振込で加算する」の
//   入力は CSV 取込・手入力の経路から来る。メール取込の実装もカード利用 / 振込入金 /
//   口座引落の事前お知らせの 3 種しかパースしない（08a §2.1）
// 注（#390）: SMBC 側の増減は「取引で口座残高を更新する」が取込時に済ませているため、
//   本 behavior と「別銀行戻し判別」の事後はシャドウ側だけを動かす（両方動かすと SMBC が二重に効く）。
//   同一取引の二重適用は口座集約が反映済み取引IDの集合で拒否する（OQ-43 の再実行回復と対）

behavior 別銀行貯蓄残高を取り崩しで減算する = 取り崩し手入力 AND 別銀行貯蓄口座 -> シャドウ口座更新 AND 別銀行貯蓄残高更新イベント
// 事前: 入力者ユーザーID = 口座所有者ユーザーID

behavior 別銀行貯蓄残高を手動補正する = 残高補正手入力 AND 別銀行貯蓄口座 -> シャドウ口座更新 AND 別銀行貯蓄残高更新イベント
// 事前: 入力者ユーザーID = 口座所有者ユーザーID

behavior NISA積立累計をSMBC振込で加算する = 出金変動 AND NISA口座 -> NISA積立加算 AND NISA積立累計加算イベント
// 事前: 出金用途 = NISA積立用
// 事前: 振込先証券会社が出金変動から特定済み

behavior NISA積立累計を手動補正する = NISA積立補正手入力 AND NISA口座 -> NISA積立累計更新 AND NISA積立累計補正イベント
// 事前: 入力者ユーザーID = 口座所有者ユーザーID
// 事前: 口座がアクティブ
// 補正は差分ではなく「実際の積立累計」への差し替え（証券会社の画面を見て入れ直す操作）
// 事後: 現在累計が補正後の値になり、最終更新日時が更新される
// 事後: 初期累計・初期累計基準時刻は動かさない（そこは「始めた時点」の記録で、
//       初期累計そのものの誤りは「初期残高を後から修正する」で直す）
// 不変: 補正後の積立累計は負にならない
// 注: 補正後の現在累計が初期累計を下回る状態も許す（通常の積み上げでは生じない状態だが、
//     下回る補正を拒むと「初期累計を誤って大きく入れた」ケースの復旧が塞がるため）。
//     「実際にいくら積み立てたか」を正とし、初期累計との整合は利用者の入力に委ねる

// --- 初期残高登録（オンボーディング Phase 2-B からの呼出） ---

behavior 初期残高を登録する = ユーザーID AND 口座種別 AND 初期残高 AND 入力日時 -> 口座 AND 初期残高登録イベント OR 重複登録エラー
// 事前: ユーザーIDの当該口座が未登録
// 事後: 初期残高基準時刻 = 入力日時（論点9）

data 重複登録エラー = ユーザーID AND 口座種別 AND 既存口座ID

behavior 初期残高を後から修正する = 口座ID AND 修正後初期残高 AND 修正者ユーザーID -> 口座 AND 初期残高修正イベント
// 事前: 修正者ユーザーID = 口座所有者ユーザーID

// --- 口座ライフサイクル ---

behavior 口座をアプリに登録する = ユーザーID AND 口座種別 AND 登録日時 -> 口座 AND 口座登録イベント
// 事前: ユーザーIDが許可リストに存在
// 事前: 同種別の口座が未登録
// 事後: 口座種別 = 三井住友カード のときは、三井住友カード未払金集約を対で開設する

behavior 三井住友カード未払金集約を開設する = 口座ID -> 三井住友カード未払金集約
// 事前: 対象の三井住友カード口座が登録済み（未払金集約は口座を参照するため、口座を先に作る）
// 事後: 当月未払金合計 = 0 AND 未払金エントリ = 空 AND 最終消込日時 = なし
// 三井住友カード口座の登録と対で行う（未払金の計上先が無いと、カード利用の取込が反映先を失う）
// 対の作成が途中で中断したら、同じ登録をやり直して開設し直す（口座は作り直せないため）

behavior 口座を非アクティブ化する = 口座ID AND 非アクティブ理由 -> 口座 AND 口座非アクティブ化イベント

behavior 口座を再アクティブ化する = 口座ID AND 操作者ユーザーID -> 口座 AND 口座再アクティブ化イベント
// 事前: 操作者ユーザーID = 口座所有者ユーザーID（配偶者は相手の口座を戻せない）
// 事前: 口座が非アクティブ（アクティブな口座への再実行は拒否する）
// 事後: 口座が残高一覧・世帯資産合計に戻り、以降の残高変動が再び適用される
// 事後: 口座の非アクティブ化日時・非アクティブ理由は消える。解除前の非アクティブ理由は
//       口座再アクティブ化イベントに載せて発行するが、このイベントの購読者もイベントの
//       保存先も無いため、「いつ・なぜ閉じたか」を後から引く手段は現時点では無い
// 残高・最終更新日時は動かさない（閉じている間に残高は変わっておらず、戻した時点を
// 「最近確認した」ことにすると残高鮮度の警告をすり抜けるため）
// 非アクティブ化と違い口座種別で絞らない（戻す操作を種別で拒むと、閉じた口座が
// 取り残されて復旧手段が無くなる）

// --- 銀行名・証券会社名の編集（Phase 3.5 追加） ---

behavior 別銀行貯蓄口座の銀行名を変更する = 口座ID AND 新銀行名 AND 操作者ユーザーID -> 別銀行貯蓄口座 AND 銀行名変更イベント
// 事前: 操作者 = 口座所有者本人（配偶者の口座名は変更不可）
// 事後: ダッシュボード・口座詳細・取引履歴の表示が新銀行名に切り替わる
data 銀行名変更イベント = 口座ID AND 旧銀行名 AND 新銀行名 AND 変更者ユーザーID AND 変更日時 AND 発生日時

behavior NISA口座の証券会社名を変更する = 口座ID AND 新証券会社名 AND 操作者ユーザーID -> NISA口座 AND 証券会社名変更イベント
// 事前: 操作者 = 口座所有者本人
// 事後: ダッシュボード・口座詳細の表示が新証券会社名に切り替わる
data 証券会社名変更イベント = 口座ID AND 旧証券会社名 AND 新証券会社名 AND 変更者ユーザーID AND 変更日時 AND 発生日時

// --- 残高変動履歴（#398） ---

behavior 残高の変動を履歴に記録する = 残高軸 AND 口座ID AND 変動後の値 AND 発生日時 AND 由来イベントID -> 残高変動履歴エントリ
// 事前: 残高を動かす振る舞いが完了し、対応するドメインイベントが発行された

// 不変: 同一の（残高軸, 由来イベントID）は 1 件だけ（同じ変動が二度届いても点が重ならない）
// 不変: 追記のみ。一度記録した変動は書き換えない（過去のグラフが後から変わらない）

behavior 資産の推移を読み出す = 開始年月 AND 終了年月 AND 閲覧者ユーザーID -> 残高時系列
// 事後: 4 軸それぞれについて期間内の点を発生日時の昇順で返す
// 事後: 期間中に一度も動きが無い軸でも、期間より前の値があれば期間開始時刻に世帯合算の
//       補助点を置き、線を消さない（まだ一度も記録が無い軸は従来どおり線が出ない。#538）
// 資産の推移（世帯合算の 4 軸）と世帯資産合計は世帯フルオープンのため閲覧者では絞らない
// （絞らないことを明示するために受け取る）。口座 1 件ごとの残高は下の残高一覧のとおり本人のみ可視

behavior 口座詳細を読み出す = 口座ID AND 開始年月 AND 終了年月 AND 閲覧者ユーザーID -> 口座詳細
// 事後: 口座 1 件の いまの値・その口座だけの推移・その口座の履歴 を返す（#406）
// 事後: いまの値は口座種別で意味が変わる（SMBC銀行/別銀行貯蓄 = 残高、NISA = 積立累計、
//       三井住友カード = 当月未払金合計。カードは未払金集約が正）
// 事後: 推移は期間より前の最後の値を期間の起点に置く（期間中に動きが無くても線が消えない）
// 事後: 履歴は残高変動履歴を正とし、発生日時が一致する手入力操作記録の種別・メモを添える
//       （自動反映と手入力が 1 つの並びに混ざる）
// 不変: 閲覧者 = 口座所有者本人のときだけ返す。他人の口座と存在しない口座は同じ「無し」を返し、
//       応答の違いから配偶者の口座の有無を数えられないようにする（P2-B5 / OQ-60 ①）
// 非アクティブの口座も返す（閉じた口座の履歴を確かめる先が要る）。一覧に並べないのとは別の話

data 口座詳細 = 口座ID AND 口座種別 AND 表示名 AND 有効フラグ AND いまの値 AND 最終更新日時?
                AND 手入力可否 AND 期間 AND 推移の点* AND 履歴行*
data 履歴行 = 発生日時 AND 変動後の値 AND 増減? AND 由来（自動反映 OR 取り崩し OR 残高補正）AND メモ?
// 増減は直前に分かっている値との差。起点が分からない最初の 1 行だけ持たない

behavior 残高一覧を読み出す = 閲覧者ユーザーID -> 残高一覧
// 事後: 閲覧者本人の active 口座だけを口座 1 件ずつ返す（種別の固定順）
// 事後: 配偶者については、別銀行貯蓄残高 + NISA積立累計 の合計 1 つだけを返す（P2-B5 / OQ-60）
// 事後: 配偶者に対象の active 口座が 1 件も無ければ合計を返さない（合計 0 円とは区別する）
// 不変: 配偶者の SMBC銀行残高・当月未払金合計・銀行名・口座件数は返さない

// --- 残高鮮度供給（家計分析の評価のため） ---

behavior 残高鮮度の根拠を供給する = 口座ID -> 残高鮮度供給
// 事後: 最終更新日時のみを供給。鮮度しきい値の判定は家計分析側で行う

behavior 取引削除で残高を再計算する = 取引ID AND 取引削除イベント -> 残高変動 AND 口座残高再計算イベント

// 事前: 家計分析から取引マージイベントを受信
```

## 4. 隣接コンテキストとの境界

| 隣接 | 関係 | 翻訳層 behavior |
|---|---|---|
| 取引取込 | 顧客-供給者（上流: メール由来取引・引落確定通知の供給） | （受信側のため翻訳層は取引取込側。本コンテキストは `behavior 取引で口座残高を更新する`／`behavior 引落確定通知で未払金を消込する` で取り込み） |
| 家計分析 | 顧客-供給者（双方向: 残高鮮度根拠を供給／取引削除・マージで残高再計算を受付） | `behavior 残高鮮度の根拠を供給する`／`behavior 取引削除で残高を再計算する`／`behavior 取引マージで残高を再計算する` |
| 経費精算 | 顧客-供給者（下流: 経費精算入金到着イベントを供給） | `behavior 銀行入金の用途を判別する` の出力イベント `経費精算入金到着イベント` が経費精算を起動 |
| オンボーディング・認証 | 顧客-供給者（上流: 初期残高入力を受付）／クロスコンテキスト参照（ユーザーID 借用） | `behavior 初期残高を登録する`（Phase 2-B からの呼出） |
| 自動分類・学習 | （直接の関係なし。資金移動の用途判別は本コンテキスト内で完結） | - |
