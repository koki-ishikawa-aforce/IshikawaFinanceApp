# シナリオ B: オンボーディング — 時系列タイムライン

> Phase 2 イベントストーミング ウォークスルー結果（2026-04-30〜2026-05-01 実施）。
> アプリのデプロイから夫婦が運用開始するまでの流れを Phase 単位で再構成。


## Phase 0: デプロイ時の前提条件 ⚙️

シナリオ B が始まる **前** に、アプリ開発者（=利用者本人、夫 or 妻）が完了させておく作業。これらはユーザー視点のフローではなく、デプロイの一部として実施される。

```
[⚙️] LINE 公式アカウントが作成された（Messaging API 有効化）
[⚙️] LINE Channel 設定値（Channel ID / Channel Secret / Channel Access Token）が
     Parameter Store に保存された
[⚙️] LINE Webhook エンドポイントがバックエンド Lambda に紐付けられた
[⚙️] 設定値 HUSBAND_LINE_USER_ID / WIFE_LINE_USER_ID が投入された
[⚙️] カテゴリマスタ規定4種が DB に seed 投入された（住居光熱通信／食費／娯楽／その他、世帯共有・削除改名不可）
[⚙️] 経費種別マスタ規定5種が DB に seed 投入された（ジム/新聞図書/AI利用/交通費/その他経費、世帯共有・削除改名不可）
[⚙️] 経費種別の月次上限の seed 値が個人別に投入された

       個人別に自動作成される（OQ-19 / #321）。DB 初期化時点では実 LINE ユーザーID が
       未確定のため投入できない。db:seed が投入するのは規定マスタのみ（#322）
```

### Section A: Gmail OAuth 連携 🔐

SMBC 通知メールと Amazon 注文確認メールを Gmail から取得するために、各ユーザーが自分の Gmail への読み取り権限をアプリに付与する。

**実装ポイント**:
- スコープは `gmail.readonly` のみ（読み取り専用、修正不可）
- LIFF 内蔵ブラウザは Google OAuth に対し `disallowed_useragent` を返すため、`liff.openWindow({ external: true })` で **OS 標準ブラウザに切り出して実行**
- アクセストークン・リフレッシュトークンは Parameter Store（KMS 暗号化）に保存
  - キー命名例: `/ishikawa/gmail/husband/access_token`, `/ishikawa/gmail/husband/refresh_token`
- 失効時の挙動は OQ-2 で確定済（API 呼び出し失敗で検知 → LINE 個人 DM → アプリ経由再認可）
- **持ち主本人の Google ログインと同意が必須**。代理認可は不可

```
[👤] ユーザーが「Gmail 連携」ボタンを押した
  ↓
[🔐] OS 標準ブラウザに遷移し、Google 同意画面が表示された
  ↓
   ├─ 「許可」→ [🔐] 認可コードを受領 → トークン取得 → Parameter Store 保存
   │            → ✅ Gmail 連携完了
   │
   ├─ 「キャンセル」→ [🟨] ユーザーが Gmail 認可をキャンセルした
   │
   └─ エラー → [🟨] OAuth 中にエラーが発生した（再試行可）
```

イベント粒度は **完了 / キャンセル / エラー** の 3 種に集約する（細粒度のステップは内部処理として持たない）。

**入力項目（4 項目を 1 画面で入力）**:

| 項目 | 単位 | 補足 |
|---|---|---|
| SMBC 銀行口座 残高 | 円 | 自分名義の SMBC 普通預金残高 |

## Phase 3: 配偶者の同様の手続き

夫が Phase 1+2 を完了した後（または並行して）、妻が同じ手続きを行う。**「夫はすでに自分の画面でアプリを使い始めている**（自分のダッシュボード・取引一覧）」という非対称な状態が生じる。

```
[時系列例: 夫が先に完了するケース]

T0: 夫が Phase 1+2 (A+B) 完了
    ↓
T0+ε: 夫の取込パイプラインが「翌日 0:00 から日次バッチで稼働」状態に
       夫の画面: 自分のダッシュボード・取引一覧は使える、月次レポート画面は「準備中」
       妻の画面: まだアプリ未起動 or 起動済でも Phase 2 が必要
    ↓
T1〜T2: 妻が Phase 1（初回アクセス）→ Phase 2 (A+B)
    ↓
T3: 妻の Phase 2 (A+B) 完了
    ↓
[🟦] アプリの利用が夫婦で開始された（運用開始イベント発火、自動）
    ↓
夫の画面: 「準備中」が解除され、月次レポート画面も使えるようになる
妻の画面: 自分のダッシュボードが見える、運用開始扱い
    ↓
T3+ε: 妻の取込パイプラインが「翌日 0:00 から日次バッチで稼働」状態に
```

### Phase 3 で確定したルール

| # | ルール |
|---|---|
| P3-1 | 登録順序自由（夫が先でも妻が先でもよい） |

```
  ↓
（LINE 関連: 並行して実施）

[👤] LINE 公式アカウントが妻に友達追加された
```

## 運用開始月の月次レポート生成タイミング

P4-1（不完全月で生成）と F2（CSV/PDF 全部取込）と F4（即時取込なし）の組み合わせから、**通常サイクルに合流する** 形に決定:

| ステップ | タイミング | 内容 |
|---|---|---|
| 1 | Phase 2-F | 運用開始月の **過去取引** を CSV/PDF で投入 |
| 2 | 運用開始翌日 0:00 〜 | 日次バッチでメール取込開始 |
| 3 | 翌月 5 日 | 通常の CSV 取込リマインダー（LINE 共通トークルーム） |
| 4 | 翌月 5〜10 日 | 夫婦が **もう一度 CSV 取込** で運用開始月の確定データを投入 |
| 5 | 翌月 5〜10 日 | 月次レポート生成・配信（運用開始月、「不完全月」フラグ付き） |

つまり、運用開始月のレポートは **翌月の通常サイクルで生成される**。ユーザーは Phase 2-F でアップロード後、翌月もう一度 CSV 取込が必要。

## 日次バッチの取込範囲修正（横断論点 Q3）

シナリオ A の日次バッチは、当初「**前回取込時刻以降の新着メール**」を取得する設計だった。

シナリオ B の Phase 2-F（初期 CSV/PDF 取込）と運用開始時のギャップを埋めるため、**取込範囲を「過去 5 日以前のメール」に拡張** する:

| 修正前 | 修正後 |
|---|---|
| 前回取込時刻以降の新着メール | **過去 5 日以前のメールを毎回スキャン**（重複は Gmail message ID で除外） |

これにより:
- 運用開始時の取りこぼし（CSV では取れず日次バッチも始まっていない数日分）をカバー
- 日次バッチ自体の冗長化保険にもなる
- 重複検出は既存の OQ-7（日付・金額・加盟店名 3 項一致 + Gmail message ID）で吸収

→ シナリオ A（04-scenario-a-monthly-cycle.md）の日次バッチ記述に反映が必要。

## ウォークスルーで決定した主要ルール（一覧）

| 領域 | ルール |
|---|---|
| 役割判定 | 設定値（HUSBAND/WIFE_LINE_USER_ID）の許可リストで自動判定。第三者は拒否 |
| Gmail OAuth | スコープ `gmail.readonly`、LIFF 外部ブラウザで実行、トークンは Parameter Store |
| 必須セクション | A（Gmail OAuth）と B（初期残高）のみ必須・順序強制。C/D/E は seed で自動完了、F は推奨 |
| マスタ seed | カテゴリ4種・経費種別5種・月次上限を Phase 0 で seed 投入。規定値は世帯共有・削除改名不可 |
| 追加項目 | カテゴリ・経費種別の追加項目は **個人別**、追加・改名・削除すべて可能 |
| 月次上限 | 個人別の seed 値（夫AI 10,000 / 妻AI 3,000 等）。「無制限」は専用カラム |
| 初期残高 | ユーザー入力時点が基準。本人のみ可視（別銀行貯蓄+NISA は合計を配偶者も可視） |
| カード未払金 | ゼロから開始、運用開始月以降のメール+CSV で積上げ |
| 初期 CSV/PDF | 運用開始月分を SMBC マイページから取込（推奨・スキップ可）。CSV 取込は即時実行 |
| 取込タイミング | 個別 Phase 2 完了で **翌日 0:00 から日次バッチ稼働**（即時メール取込なし） |
| 運用開始 | 夫婦両方の A+B 完了で自動発火。月次レポート画面が解放される |
| 配偶者待ち | 自分の画面（ダッシュボード・取引一覧）は使える、月次レポート画面のみ「準備中」 |
| LINE 通知 | Phase 4 と同時に有効化。共通トークルーム ID は join Webhook 自動取得、テスト送信あり |
| 運用開始月 | 翌月 5〜10 日の通常サイクルで「不完全月」フラグ付き月次レポート生成 |
| 日次バッチ範囲 | **過去 5 日以前のメールを毎回スキャン**、重複除外（シナリオ A への反映必要） |
