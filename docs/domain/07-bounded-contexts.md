### 1.1 仮説検証ループでの 5 つの保留論点の判定結果

仮説段階で「Step 2 で再判定」候補とした論点は、§3 で 146 イベントを実際に各コンテキストに振った結果を踏まえて以下のとおり確定した。各判定の根拠は跨がりイベント数・動詞セットの一貫性・所有者軸の違い・隣接ドキュメント（01-overview / 02-event-storming / 03-open-questions A 節 / 04〜06 シナリオ）の言語との整合性に基づく。

#### 1.1.1 家計分析と残高・資産推移管理の統合判定

**決定**: 別コンテキストとして分離して維持する（統合しない）。

**根拠**:
- 動詞セットが明確に異なる: 家計分析側は「集計された／レポートに表示された／プライバシールールが適用された／状態が昇格した」、残高・資産推移管理側は「残高が更新された／未払金が消し込まれた／NISA 積立累計に加算された／用途が判別された」。共通の動詞は無い。
- 経費(会社) の扱いが二重になる（01-overview §6.3、02-event-storming §15）。同一取引が「家計分析からは除外、残高・未払金管理には反映」される非対称性は、別集約として独立して持たないと不変条件を表現できない。
- 跨がりイベントは月次レポートの「残高推移パート」のみで、これは「家計分析が残高ビューを参照する」関係（Customer-Supplier）として §4 で表現できる範囲。集約境界を統合する必要はない。
- 取引のライフサイクル（決済→引落消込）が両者で異なる軸を持つ（家計分析は費用区分・カテゴリ単位、残高は口座単位）。

#### 1.1.2 残高鮮度アラートの所属

**決定**: 家計分析（評価ロジック・表示）と残高・資産推移管理（鮮度の根拠データ：最終更新日時を保有）の協働。アラート発動は **家計分析の月次レポート画面表示時** に閉じ、通知配信は介在しない。

**根拠**:
- 02-event-storming §9 の表現「別銀行貯蓄口座残高の鮮度（最終更新日からの経過日数）が **月次レポート画面で評価され**、N 日以上更新がなければアラート色が付与された」が画面表示の話であって push 配信ではない（OQ-6 でも「月次レポートに表示」と確定）。
- 通知配信に該当するイベントは無く、跨がりは月次レポート画面のレンダリング時のみ。「LINE 通知への混載はしない」（OQ-30 の方針と整合：「明細を載せない原則と整合」）。
- 仮説段階で「通知配信に独立アラートとして送るか」を検討したが、対応するイベントが §11 に存在せず却下。

#### 1.1.3 Phase 0 のデプロイ前提の帰属

**決定**: マスタ管理に帰属。LINE Channel 設定値・設定値投入・Webhook エンドポイント設定・seed 投入をすべてマスタ管理が担当する。

**根拠**:
- §7.1 デプロイ前提 7 件のうち、「カテゴリマスタ規定 4 種が seed 投入された」「経費種別マスタ規定 5 種が seed 投入された」「経費種別の月次上限の seed 値が個人別に投入された」の 3 件は明確にマスタ管理。残り 4 件（LINE 公式アカウント作成／Channel 設定値の Parameter Store 保存／Webhook エンドポイント紐付け／HUSBAND/WIFE_LINE_USER_ID 投入）は「許可リスト＋ Channel 設定」という設定値マスタの性質を持つ。
- オンボーディング・認証はユーザー視点のライフサイクル（初回 Login〜運用開始）を担当する一方、Phase 0 はシステム管理者視点の前提条件であり、所有者軸（誰が触るか）が異なる。動詞も「seed 投入された／保存された／紐付けられた」で「マスタが追加された」と同質。
- 別コンテキストに切り出す案も検討したが、§7.1 の 7 件のみで他のイベントが集まらず、コンテキスト数を増やすメリットが薄い。マスタ管理の責務に「デプロイ時の前提条件（LINE Channel 設定・設定値投入）」を含めるのが最小コスト。
- **将来の拡張余地**: LINE Channel 設定が他のシステム設定（外部 API キー追加等）と組み合わさって肥大化した場合は、本コンテキストから「システム構成」コンテキストとして分割することを検討する。本 Phase 3 時点では業務マスタ（カテゴリ・経費種別）と Phase 0 のみのため、分割せず「マスタ管理」の責務に含めて維持。

#### 1.1.4 資金移動の用途判別ロジック

**決定**: 残高・資産推移管理の内側に閉じ込める（自動分類・学習には載せない）。

**根拠**:
- 02-event-storming §3 資金移動 4 件と §2.1 給与（SMBC 銀行入金通知）は、すべて「銀行入金／出金の振込元・金額・摘要から用途を判別する」純粋ルールベース処理であり、加盟店名 → カテゴリの memorization 学習とは性質が違う（学習データに保存しない、ユーザー手動修正での学習対象外）。
- シナリオ A 詳細タイムライン §B「銀行入金の用途が金額・振込元名から自動判別された（25万円以上→給与、25万円未満→経費精算入金、振込元が別銀行貯蓄口座→戻し）」は、入金イベントを残高更新する直前の前処理として残高側で完結する。
- 自動分類・学習に寄せると、加盟店学習ルール（per-user）と用途判別ルール（世帯共通の閾値ルール）が混在し、所有者軸が割れる。残高・資産推移管理側は「世帯共通の口座ルール」軸で一貫させる。
- 経費精算入金の判別後の「経費精算入金が会社から SMBC に到着した」イベントは、判別された結果として残高・資産推移管理から経費精算へ Customer-Supplier で渡す（§4 で関係明示）。

#### 1.1.5 LINE 友達追加・グループ招待の帰属

**決定**: オンボーディング・認証に帰属。通知配信は「配信メッセージの送出」のみを担当し、LINE 関係のセットアップ（友達追加・招待・Webhook 受信・共通トークルーム ID 取得）はオンボーディング・認証の Phase 4 の一部として扱う。

**根拠**:
- 02-event-storming §7.2 Phase 4 の 7 件（友達追加×2／follow Webhook／グループ招待／join Webhook／通知配信機能有効化／テストメッセージ送信）は、いずれもユーザーの「運用開始までのライフサイクル」の最終ステップであり、オンボーディングの動詞セット（初期化された／取得された／登録された／検知された／紐付けが確認された）と一致する。
- 通知配信は「サマリを LINE 共通トークルームに配信した」「リマインダーを送信した」のような **運用中の push** に限定し、配信先の LINE userID／共通トークルーム ID は ID 経由でオンボーディング・認証から借りる関係（クロスコンテキスト参照）。
- 「テストメッセージが共通トークルームに送信された」「通知配信機能が有効化された」は通知配信の機能を **オンボーディングの完了確認として呼び出す** 関係であり、これは Customer-Supplier として §4 で表現する。コンテキスト境界はオンボーディング側。
- LINE Channel 設定値・Webhook エンドポイント設定の Phase 0 セットアップ（マスタ管理）と、Phase 4 の友達追加・招待（オンボーディング・認証）は、所有者軸（システム管理者 vs ユーザー）で明確に分かれる。

## 2. サブドメイン分類

> 各コンテキストを Core / Supporting / Generic に分類し、Phase 4 以降の実装労力配分の指針とする。

### 2.1 分類基準

- **Core**: 競争優位の中核。本アプリ独自のドメインルールが集中し、ここが不十分だと製品として成立しない。Phase 4 以降で意識的に実装時間を集中させるべき対象。
- **Supporting**: Core を支えるが、業界一般的な業務ロジックで構成されるコンテキスト。汎用部品では足りず本プロジェクト用に実装する必要があるが、独自性は Core より低い。
- **Generic**: 既存 SaaS・ライブラリ・標準パターンで代替可能。差別化に寄与しないため、実装コストを最小化する方針で取り組む。

### 2.2 分類結果

### 2.3 労力配分の指針

**Core（4コンテキスト）** に Phase 4 以降の実装時間を集中させる。具体的な方針は以下のとおり:

- **自動分類・学習**（最優先）: F-1・T-2・X-1 の3ルールを正確に実装し、テストを厚くする。学習データの一貫性（加盟店→フィールド独立マッピング、Amazon商品キー別テーブル）がアプリの継続利用価値を左右するため、設計の手戻りが最もコストが高い領域。
- **家計分析**（最優先・並列）: プライバシールール3段階の適用タイミング・範囲を明確に定義し、月次レポートの状態遷移（CSV確定→最終確定）の境界条件を先に固める。後から変更すると全体に波及する。
- **残高・資産推移管理**: 口座モデルとシャドウ口座の設計を早期に固める。発生主義・クレカ未払金消込・経費(会社)の非対称ロジックは不変条件が密で、後からの修正コストが高い。
- **経費精算**: 按分ロジック（先着順・上限超過→子取引分割）と月次サイクル（リセット・突合・不認定分振替）は複雑なため、ユニットテストで不変条件を先に押さえる。

**Supporting（3コンテキスト）** は動作するレベルを確保した上でエッジケースを省略可能:

- **取引取込**: メールパース精度は実運用で iterative に改善する前提でよい。重複除外（Gmail message ID）と基本パースを確実にし、完璧な対応は後回し。
- **オンボーディング・認証**: ウィザード進捗管理は最小限の実装で問題ない。LINE Login 失敗時の細かいリカバリ（論点6確定: LIFF SDK 任せ）はエッジケース省略の代表例。
- **マスタ管理**: seed 投入と基本 CRUD を先に固め、削除時リマップの複雑なシナリオは Core の実装が進んでから詰める。

**Generic（1コンテキスト）** は外部サービス依存を最小化して実装コストを圧縮:

- **通知配信**: LINE Messaging API ラッパーは最薄の実装に留める。フェイルセーフメールは SES 等の標準サービスを直接使い、独自ロジックを持たせない。LINE 配信ログは送信 payload の json 保存のみで十分（シナリオC確定: スナップショット廃止の代替）。

## 4. コンテキスト間関係

> Phase 3 Step 6 で作成（2026-05-01）。図は [diagrams/07-context-map.puml](./diagrams/07-context-map.puml) を参照（PlantUML）。
> 関係種別の定義:
> - **Customer-Supplier**: 一方（Supplier）が要求されるものを提供し、もう一方（Customer）が利用する。Supplier 側が先に変更を確定させる。
> - **ACL（Anti-Corruption Layer）**: 外部システムとの接続や、語彙・モデルが大きく異なるコンテキスト間に翻訳層を置く。
> - **Conformist**: 下流が上流の言語・モデルにそのまま従う（変換なし）。外部 SaaS の仕様に乗っかる場合に使う。
> - **Open Host Service**: 多くのコンテキストから利用される公開サービス形式のプロトコル（通知配信等）。
> - **Shared Kernel**: 複数コンテキストが同一のコードや data 定義を共有する（共通語彙レベルのみ）。

| 残高・資産推移管理 | 別銀行貯蓄口座 | ACL | API なし。手入力による残高補正と振込通知での自動加算のみ。外部モデルの不在を翻訳層で吸収 |
| 残高・資産推移管理 | SBI 証券 | ACL | API なし。SMBC→SBI 証券の振込通知イベントを NISA 積立累計加算に変換する翻訳層 |
| 残高・資産推移管理 | 楽天証券 | ACL | API なし。SMBC→楽天証券の振込通知イベントを NISA 積立累計加算に変換する翻訳層 |
| マスタ管理 | AWS Parameter Store | ACL | LINE Channel 設定値（Channel ID / Secret / Access Token）・HUSBAND/WIFE_LINE_USER_ID の読み込みを担う |
| 共通語彙（全コンテキスト） | — | Shared Kernel | `取引ID` / `ユーザーID` / `金額` / `費用区分` / `カテゴリID` / `経費種別ID` / `Gmail_message_ID` 等、08-ubiquitous-language.md §2 で定義した共通 data 定義を全コンテキストが共有する |

### 4.2 外部システム接続点（ACL の必要性）

| 外部システム | 接続コンテキスト | ACL の責務 |
|---|---|---|
| Gmail | 取引取込 | OAuth トークン管理 + Messages API でのメール取得 + Gmail message ID による重複除外（二重受信防止） |
| SMBC（メール通知） | 取引取込 | SMBC カード利用・銀行入出金・引落確定・カード返金の各メール形式のパースと差異吸収 |
| Anthropic API | 取引取込 | PDF 明細 → CSV 変換のプロンプト構築 + レスポンスパース + 失敗時ハンドリング（変換失敗は通知配信へ連携） |
| LINE Messaging API | 通知配信 | Channel Access Token 管理 + push API 呼び出し + Flex Message ペイロード構築 + 配信ログ記録 + 連続失敗カウンタ |
| LINE Login (LIFF) | オンボーディング・認証 | LIFF SDK 初期化 + LINE userID 取得 + 内部ユーザーID への変換 + 許可リスト（夫/妻）照合 |
| 別銀行貯蓄口座 | 残高・資産推移管理 | API なし。手入力による取り崩し・残高補正と、SMBC→別銀行振込通知からの自動加算のみ |
| SBI 証券 | 残高・資産推移管理 | API なし。SMBC→SBI 証券の振込通知イベントを NISA 積立累計加算として解釈する翻訳のみ |
| 楽天証券 | 残高・資産推移管理 | API なし。SMBC→楽天証券の振込通知イベントを NISA 積立累計加算として解釈する翻訳のみ |
| AWS Parameter Store | マスタ管理 | LINE Channel 設定値・LINE userID 許可リスト等のシークレット取得（デプロイ時の前提条件として読み込み） |
