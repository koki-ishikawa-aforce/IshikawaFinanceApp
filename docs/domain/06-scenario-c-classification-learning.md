# シナリオC: 未分類修正と memorization 学習 — 時系列ウォークスルー

> Phase 2 イベントストーミング ウォークスルー結果（2026-05-01 実施）。
> 未学習加盟店の取引が「未分類」で取り込まれ、ユーザーが手動修正を行い、それが学習データに反映され、後続の取引や配偶者にどう波及するかを時系列で再構成。
> 凡例: 🟧 取引系 / 🟦 ライフサイクル / 🟨 訂正・例外 / 🟥 自動処理 / 🟫 レポート / 📩 メール取込 / 📱 通知 / 📊 集計

## 概観

```
[Phase 1]              [Phase 2]              [Phase 3]              [Phase 4]              [Phase 5]              [Phase 6]
未分類検知       →     手動修正・学習      →    妻側への波及       →    CSV取込時の        →    削除と統合         →    Amazon 商品

```

シナリオA（月次サイクル）とシナリオB（オンボーディング）の主要決定を踏まえた **学習機構の振る舞いと UX** を確定するためのウォークスルー。

## 主要な前提・用語の確定

このウォークスルーで横断的に決まった用語・前提:

- **「目的軸」を「費用区分」に改称**: 既存ドキュメントの「目的軸（世帯／個人(夫)／個人(妻)／経費(会社)）」は「費用区分」と呼ぶ。月次レポートの既存表記「世帯費用」「個人費用」「経費(会社)合計」と直結し、収入取引には適用されない概念であることを明示する
- **学習データは完全個人別（F-1）**: 夫婦の学習データは別テーブルで管理。夫が「コーナン → DIY」と学習しても妻には波及しない。既定4種カテゴリでも個別学習
- **スナップショット概念の廃止**: 月末スナップショットは廃止し、ダッシュボード／月次レポートはリアルタイム再計算で統一。LINE 配信内容のみ「配信ログテーブル」で別途保持（Flex Message payload を json 保持）

夫が 5/3 14:00 にコーナンで初めて買い物。未学習加盟店なので、日次バッチで「未分類」として取り込まれる。

🟢 5/4 00:00 — 日次メール取込バッチ起動

[🟥] 日次メール取込バッチが起動された
[📩] 過去 5 日以前のメールが Gmail API で一括取得された
[📩] メール本文がパースされ取引候補が抽出された
  ↓
取引候補: { 利用日=5/3, 加盟店="ｺｰﾅﾝ", 金額=1500, カード=夫 }
  ↓
[🟥] 加盟店名で学習データを検索 → 未登録
[🟥] 学習データに無い加盟店の取引が「未分類」フラグで取り込まれた
[🟧] カード決済が発生した（発生主義で支出 + 未払金計上）
[🟧] カード利用が未払金として計上された

### Phase 1 で確定したルール

| # | ルール |
|---|---|
| **C1-1（A-1）** | 未学習加盟店の初期値: カテゴリ=「未分類」、費用区分=カード所有者の「個人(本人)」、経費種別=NULL |
| **C1-2（B-1）** | 「未分類」はダッシュボード・月次レポート上で **独立カテゴリ** として集計・表示する（修正動機を与えるため目立たせる） |
| **C1-3** | 未払金計上は分類状態と独立（発生主義、既存仕様通り） |
| **C1-4（C-2）** | ダッシュボードに「未分類: N件」ウィジェットを **常設**。LINE への混載はしない（明細を載せない原則）|
| **C1-5** | 未分類取引のユーザー通知は行わず、ダッシュボード閲覧時に気付く運用（シナリオA 既存決定の継承） |

[🟫] 取引一覧（未分類フィルタ）を開く
[🟫] コーナン取引の詳細画面を開く
  ↓
（修正画面: 1画面で3軸表示、未分類軸=カテゴリのみ赤マーカー）

[🟦] ユーザー追加カテゴリが新設された（個人別、夫に紐付く「DIY」）
[👤] カテゴリ = DIY を選択
[👤] 費用区分 = 個人(夫)（デフォルトのまま、合っている）
[👤] 経費種別 = NULL（経費(会社) ではないので変更なし）

[🟨] 取引のカテゴリが手動で修正された（未分類 → DIY）

  ├─ Yes → [🟨] 過去未分類取引が一括で再分類された（対象は本人の未分類のみ）

```

### Phase 2 で確定したルール

| # | ルール |
|---|---|
| **C2-1（D-3）** | 修正画面は **1 画面で 3 軸（カテゴリ／費用区分／経費種別）を編集**、未分類軸のみ赤マーカーで誘導 |
| **C2-2（E-1）** | 修正画面のカテゴリ／経費種別選択肢に「+ 新規追加」を出し、その場で新設可能 |
| **C2-3（I-1）** | 学習データは **保存ボタンで即時反映**（夜間バッチ等への遅延なし） |
| **C2-4（J-3）** | 過去取引への遡及は **確認ダイアログで明示同意**。対象は **本人の未分類取引のみ**（既に分類済みの取引には触らない、配偶者の取引にも触らない） |
| **C2-5（G-3 改）** | 学習データの費用区分は **4 値全てを記録対象**（世帯／個人(夫)／個人(妻)／経費(会社)）。F-1 配下では加盟店ごとの学習にカード所有者の個人(本人) 値しか実質的に出現しないが、ルックアップ動作・上書き判定（L-4）の一貫性のため記録する。未学習加盟店時のデフォルトは A-1 通り「カード所有者の個人(本人)」 |

### 学習データのスキーマ（T-2: フィールド独立）

加盟店名 → 各分類フィールドを **独立に学習**:

```
merchant_classification_rules (per-user)
├─ merchant → category（カテゴリ）
├─ merchant → cost_division（費用区分、4 値全て）
├─ merchant → expense_type（経費種別、経費(会社) 時のみ）
└─ merchant → disabled_flag（学習無効化）
```

理由: 「同じ加盟店でカテゴリは固定だが費用区分は揺れる」ケース（コンビニで昼食=個人 / 家族用買い物=世帯）に対応するため、フィールド独立で持つ。

## Phase 3: 妻側への波及と既存ルール上書き（5月後半）

F-1（学習データ完全個人別）の帰結として、妻側ではコーナンが未学習扱いになる。同時期に夫側でも既存ルールへの修正が発生するケースを順に追う。

### Step 3-A: 妻側でコーナン取引（F-1 個人別の帰結）

5月後半、妻もコーナンで買い物（ネット通販用ダンボール）。

```
🟢 5/20 — 妻がコーナンでダンボール購入（500円）

[📩] SMBCカード利用通知メール（妻分）が受信された
[📩] メール本文がパースされ取引候補が抽出された
  ↓
[🟥] 妻の学習データで加盟店「コーナン」が検索された → 未登録
        （夫の学習は妻の学習データには反映されていない＝F-1）
[🟥] 学習データに無い加盟店の取引が「未分類」フラグで取り込まれた
  ↓
[🟫] 妻がダッシュボードで「未分類: 1件」を発見
[👤] 妻が修正: カテゴリ = 「その他」（規定4種、世帯共有マスタ）
[🟨] 取引のカテゴリが手動で修正された
[🟥] 妻の学習データに「コーナン → その他」マッピングが登録された
```

ここで **夫婦間で同一加盟店の分類が異なる** 状態が発生:
- 夫: コーナン → DIY（夫の個人カテゴリ）
- 妻: コーナン → その他（規定 4 種・世帯共有）

### Step 3-B: 夫が既存学習ルールへの修正

夫が後日、コーナン併設のフードコートで食事 → SMBC利用通知（加盟店="ｺｰﾅﾝ"）。

```
🟢 5/22 — 夫がコーナンで食事（900円）

[📩] SMBCカード利用通知メール（加盟店="ｺｰﾅﾝ", 金額=900）
  ↓
[🟥] 夫の学習データで「コーナン」検索 → ヒット
[🟥] カテゴリ「DIY」で自動分類された
[🟧] カード決済が発生した
  ↓
（夫が「これは食事だから食費」と修正したい）
[👤] 修正画面: カテゴリ = DIY → 食費（規定4種）
[👤] 保存
  ↓
[🟨] 取引のカテゴリが手動で修正された（DIY → 食費）
  ↓
（既存学習ルール上書き判定）
[🟥] 既存学習ルール「コーナン → DIY」が存在
[🟫] 確認ダイアログ表示
  「以後コーナン取引は『食費』に分類しますか？」
  ├─ Yes → [🟥] 学習データのカテゴリが「食費」に上書きされた
  └─ No  → 今回のみ修正、学習データはそのまま  ← 夫はこちらを選択

                                                   ルール固定したくない）

> 夫が **No（今回のみ）** を選択したことで、学習データには「コーナン → DIY」が残り続ける。これが Phase 5 のカテゴリ削除フローまで継続する。

### Phase 3 で確定したルール

| # | ルール |
|---|---|
| **C3-1（F-1）** | 学習データは **完全個人別**（per-user テーブル）。配偶者の学習は一切波及しない |
| **C3-2（K-1）** | 夫婦間の分類不整合は **容認**。F-1 を採った時点で構造的に許容する思想と整合 |
| **C3-3** | 同じスーパー等で両方とも初回は未分類になる冗長は仕様（プライバシーと実装単純性を優先したトレードオフ） |
| **C3-4** | 規定4種カテゴリ（世帯共有マスタ）でも学習は個別。マスタの「世帯共有」と学習データの「個人別」は別概念 |
| **C3-5（L-4）** | 既存学習ルールへの修正は **「以後このルールに従いますか？」確認ダイアログ** で「今回限り」と「ルール上書き」を分岐 |
| **C3-6（M-1）** | 同一加盟店で揺れる分類（例: コーナンで DIY と食事の両方）に対し、修正画面に **「この加盟店は学習しない」チェックボックス** を提供。チェック後は常に「未分類」で取り込まれる |

## Phase 4: 月次 CSV 取込時の一括分類（5/5〜5/10）

5/5、夫婦が CSV 取込リマインダーを受けて 4 月分の SMBC カード CSV をアップロード。CSV にはメール通知対象外の取引（公共料金のクレカ払い、ETC、10円以下 等）が含まれ、一度に大量の未分類取引が発生しうる。

```
🟢 5/5 — CSV 取込リマインダー（LINE 共通トークルーム）
🟢 5/5〜10 — 夫婦が任意のタイミングで CSV アップロード

[🟧] 明細 CSV または PDF（カード）がアップロードされた
[🟥] CSV のフォーマット検証に成功し取込が完了した
[🟥] CSV から抽出された取引が、既存の通知由来取引と「日付・金額・加盟店名の3項完全一致」で突合され重複が除外された
[🟥] CSV にしか無い取引が新規に取り込まれ、自動分類された
   ├─ 学習データに加盟店があれば → 自動分類
   └─ 加盟店未学習 → 「未分類」フラグ
  ↓
（取込結果サマリ画面表示）
[🟫] CSV 取込結果サマリが表示された
   「新規取込: 32件、うち自動分類: 18件、未分類: 14件」
  ↓
[👤] 「未分類を一括分類」ボタン
[🟫] 取込直後の一括分類画面が起動された
  ↓
（未分類14件をリスト表示、加盟店ごとにまとめてカテゴリ・費用区分・経費種別を割当）
[👤] 東京電力 → 住居光熱通信 / 世帯 / NULL
[👤] NTT → 住居光熱通信 / 世帯 / NULL
[👤] ENEOS → その他 / 個人(夫) / NULL
... 他
[👤] 一括保存
  ↓
[🟨] 複数取引のカテゴリ／費用区分／経費種別が一括修正された
[🟥] 各加盟店 → 分類のマッピングが学習データに一括登録された
   ※ 同一加盟店の複数取引（東京電力 4 件等）はまとめて 1 ルールに集約される
```

5/10 に夫婦両方の CSV 取込が完了 → 月次レポート生成・配信（既存仕様通り、未分類が残っていてもレポート生成）。

| # | ルール |
|---|---|
| **C4-1（N-1）** | CSV 取込完了画面で **「新規N件、自動分類N件、未分類N件」のサマリを表示**、その場で一括分類画面へ誘導 |
| **C4-2（O-1）** | 未分類が残っていても月次レポートは生成・配信（シナリオA 既存決定の継承）。後日分類で過去レポートが書き換わるのは仕様で許容 |
| **C4-3（P）** | 規定4種に分類されるような世帯共通の加盟店（東京電力等）でも夫婦で個別学習する冗長は受け入れる（F-1 の論理的帰結） |

## Phase 5: カテゴリ削除と統合（8 月頃）

夫が「DIY という個人カテゴリを作ったが、結局住居の修繕で使うものばかりだった。住居・光熱・通信（世帯費用）に統合したい」と判断。

```
🟢 8/10 — 夫がカテゴリ管理画面で DIY 削除を実行

[🟫] 夫がカテゴリ管理画面を開く
[👤] 「DIY」を選択し「削除」
  ↓
（削除確認ダイアログ）
[🟫] 削除時の移動先選択ダイアログが表示された
   「DIY を削除します。配下の取引（28件）と学習データの移動先を選んでください」

   ① 移動先カテゴリ:
      ├─ その他（規定4種）
      ├─ 食費（規定4種）
      ├─ 娯楽（規定4種）
      ├─ 住居・光熱・通信（規定4種）  ← 夫がこれを選択
      └─ （他の追加カテゴリがあれば）

   ② 配下取引の費用区分:
      ├─ 現状維持（個人(夫) のまま）
      ├─ 世帯               ← 夫がこれを選択（家族の家の修繕費なので世帯扱いにする）
      ├─ 個人(妻)
      └─ 経費(会社)
  ↓
[👤] カテゴリ移動先=「住居・光熱・通信」、費用区分=「世帯」を選択 → 削除確定
  ↓
[🟦] ユーザー追加カテゴリの削除時に移動先（カテゴリ＋費用区分）が選択された
[🟨] ユーザー追加カテゴリが削除され、配下取引が指定移動先に移動された
   （カテゴリ: DIY → 住居・光熱・通信、費用区分: 個人(夫) → 世帯）
[🟥] 学習データのカテゴリ・費用区分参照が移動先にリマップされた
   - 「コーナン → カテゴリ: DIY」 → 「コーナン → カテゴリ: 住居・光熱・通信」
   - 「コーナン → 費用区分: 個人(夫)」 → 「コーナン → 費用区分: 世帯」
```

過去月のダッシュボード・レポート画面は **リアルタイム再計算** なので、自動的に「DIY: ¥X,XXX」表記が消え、「住居・光熱・通信」に集計が移動する。費用区分の変更により、これまで個人(夫) として集計されていた DIY 取引も世帯費用として再計算される。スナップショット概念は廃止済みのため、過去の凍結値は持たない。

### Phase 5 で確定したルール

| # | ルール |
|---|---|
| **C5-1（Q-2 改）** | カテゴリ削除時、**配下取引の移動先カテゴリ + 費用区分をユーザーが選択**（規定4種 or 残存追加カテゴリ／費用区分は4値＋現状維持）。既存仕様の「その他に自動移動」を変更 |
| **C5-2（R-2 改）** | 学習データのカテゴリ・費用区分参照は **移動先にリマップ**（学習自体は残す）。経費種別はカテゴリと無関係なのでリマップ対象外 |
| **C5-3** | スナップショット概念を廃止。過去レポートはリアルタイム再計算なので、削除カテゴリの過去表示は移動先で再集計される（事後的整合） |
| **C5-4** | 経費種別の削除も同構造（移動先経費種別 + 費用区分を選択 → 取引移動 → 学習データリマップ）。経費種別の場合、移動先費用区分は通常そのまま「経費(会社)」 |
| **C5-5** | 名称変更（DIY → 趣味 等）は副作用なし。学習データは id 参照なので何もしなくて良い |

## Phase 6: 経費種別と Amazon 商品キー学習

> **注記（2026-08-23 / #391・#572）**: 本 Phase のうち **Amazon 商品キー学習（X-1）は取り下げた**。Amazon 注文確認メールに商品カテゴリが含まれないことが実メール調査で判明し、前提が成立しなかったため。以下 Step 6-B・6-C の商品キー学習に関する記述は、当時の検討の記録として残す（現在の仕様ではない）。Amazon の取引は学習されず毎回手動で分類する。加盟店名ベースの経費種別学習（Step 6-A）と、Amazon 注文と SMBC 通知の突合・タイムアウト（C6-3）は現行のまま。加盟店名「AMAZON.CO.JP」を学習対象外とする扱いを続けるかは #391 の判断待ち（OQ-18 改訂）。

経費(会社) の経費種別は、加盟店名で判別可能なケースと、Amazon 注文確認メールの商品情報を使うケースで処理経路が分かれる。

### Step 6-A: 加盟店名ベースの経費種別学習（5/8 ジム会費）

```
🟢 5/8 — 夫が Anytime Fitness 銀座店でジム会費引落（7,000円）
       ※ ジムの月次上限 = 5,000円（夫）、夫の当月ジム経費は本件のみと仮定

[📩] SMBCカード利用通知メール（加盟店="Anytime Fitness 銀座店"）
[🟥] 加盟店名で学習データ検索 → 未登録
[🟥] 「未分類」フラグで取込
  ↓
[👤] 修正画面で:
   - カテゴリ = その他
   - 費用区分 = 個人(夫) → 経費(会社) に変更
   - 経費種別 = ジム
[🟨] 取引のカテゴリ・費用区分・経費種別が手動で修正された
[🟥] 学習データに登録された（フィールド独立、T-2）:
   - 「Anytime Fitness 銀座店 → カテゴリ: その他」
   - 「Anytime Fitness 銀座店 → 費用区分: 経費(会社)」
   - 「Anytime Fitness 銀座店 → 経費種別: ジム」
  ↓
[🟥] 経費種別「ジム」の月次累計が更新された（0円 → 7,000円、上限 5,000円を超過）
  ↓
（OQ-20 先着順按分の自動発動）
[🟥] ジム経費種別の月次累計が予算上限に達した
[🟨] 上限超過分（2,000円）が「個人(夫)」として子取引に分割された
   - 親取引: 7,000円 経費(会社)・ジム のうち 5,000円分が経費に充当
   - 子取引: 2,000円 個人(夫) として分離計上
```

次回以降、Anytime Fitness 銀座店の取引は自動的に「経費(会社)・ジム」に分類される。月次上限超過時の按分は経費(会社) フラグ確定後に自動発動する（OQ-20 既存仕様）。

### Step 6-B: Amazon 商品キー学習（5/12 書籍購入）

Amazon 取引は加盟店名「AMAZON.CO.JP」では商品ごとの判別ができないため、**加盟店名は学習対象外**、**商品カテゴリをキーに学習** する特例フロー:

```
🟢 5/12 10:00 — 夫が Amazon で技術書「達人プログラマー」3,500 円購入

[📩] Amazon 注文確認メールが受信された
[📩] Amazon 注文確認メールから商品情報が抽出された
   { 商品名="達人プログラマー", 商品カテゴリ="本", 金額=3,500 }
[📩] SMBCカード利用通知メール（加盟店="AMAZON.CO.JP", 金額=3,500）
  ↓
🟢 5/13 00:00 — 日次バッチ
  ↓
[🟥] Amazon 注文と SMBC カード利用通知が金額・タイミングで突合された
[🟥] Amazon 商品キー（商品カテゴリ="本"）で学習データ検索
   ├─ 既存ルールあり → 自動分類
   └─ 未登録 → 「未分類」フラグ
  ↓
[👤] 夫が修正: カテゴリ=その他 / 費用区分=経費(会社) / 経費種別=新聞図書
[🟥] Amazon 商品キー → 分類のマッピングが学習データに登録された
   - 「商品カテゴリ:本 → カテゴリ: その他」
   - 「商品カテゴリ:本 → 費用区分: 経費(会社)」
   - 「商品カテゴリ:本 → 経費種別: 新聞図書」
```

以後、Amazon で「本」カテゴリの商品を買うと自動的に「経費(会社)・新聞図書」に分類される。

### Step 6-C: Amazon 突合タイムアウト（先に来た側が後を 3 日待つ）

突合タイムアウトは **双方向** に適用される。SMBC 利用通知が先に来てもAmazon 注文確認メールが先に来ても、後の側を最大 3 日待つ。

**ケース1: SMBC 利用通知が先（Amazon Prime 月額課金等、注文確認メールが届かない取引）**

```
[📩] SMBCカード利用通知メール（加盟店="AMAZON.CO.JP", 金額=600）
  ↓
[🟥] Amazon 注文確認メール待ち（突合保留フラグ）
  ↓
（3日経過、突合発生せず）
[🟥] Amazon 突合タイムアウトが検知された
[🟥] 「Amazon 注文不明」フラグで未分類確定（ユーザー手動分類待ち）
   費用区分: カード所有者の「個人(本人)」がデフォルト（A-1 と同じ）
```

**ケース2: Amazon 注文確認メールが先（SMBC 通知が遅延 / 配送キャンセル等）**

```
[📩] Amazon 注文確認メール（商品="○○", 金額=3,500）
  ↓
[🟥] SMBC 利用通知待ち（注文情報を保持、取引候補化はしない）
  ↓
（3日経過、SMBC 通知が来ず）
[🟥] Amazon 注文の突合タイムアウトが検知された
[🟥] 注文情報を破棄（取引が確定しなかった注文として扱う、配送キャンセル可能性）
```

### Step 6-D: 商品情報があっても判定不能（5/14 USB ハブ）

```
[📩] Amazon 注文確認メール受信
   { 商品名="エレコム USB-C ハブ", 商品カテゴリ="家電・コンピュータ", 金額=2,000 }
[📩] SMBCカード利用通知メール受信
[🟥] 突合成功
[🟥] Amazon 商品キー（商品カテゴリ="家電・コンピュータ"）で学習データ検索
   → 未登録、自動分類できず「未分類」フラグ
  ↓
[👤] 夫が判断して手動分類:
   今回は経費(会社) ではなく個人なので → カテゴリ=その他 / 費用区分=個人(夫) / 経費種別=NULL
[🟥] Amazon 商品キー → 分類のマッピングが学習データに登録された（C2-5 改: 4 値全て学習対象）:
   - 「商品カテゴリ:家電・コンピュータ → カテゴリ: その他」
   - 「商品カテゴリ:家電・コンピュータ → 費用区分: 個人(夫)」
   - 経費種別は NULL なので学習対象外
```

以後、Amazon で「家電・コンピュータ」カテゴリの商品を買うと自動的に「その他・個人(夫)」に分類される。

### Step 6-E: 妻側への波及（経費(会社) は完全個別）

経費(会社) はプライバシールール「**本人のみ可視**」のため、F-1 と完全に整合:

## 周辺で未深掘りの論点（メモ）

シナリオC の核は網羅したが、以下は本筋から外れる付随事項のためメモ程度に記録:

- **取引削除と学習データ**: 取引そのものを削除しても学習データは残る（学習は加盟店名→分類で取引と独立）。明示しておく
- **返金（カード返金通知メール）と学習**: 返金は元取引の取消なので分類は元取引と同じ、学習への影響は無い
- **未分類が月をまたぐ**: 4月の未分類取引が 5月に修正された場合、4月レポートが書き換わる（経費精算遡及と同じ思想）

これらは実装フェーズで詳細化する。
