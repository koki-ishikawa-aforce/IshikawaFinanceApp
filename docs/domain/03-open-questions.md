| Q-D | 相手に見られたくない支出 | プライバシー3段階。**世帯**=フルオープン／**個人(夫/妻)**=明細は本人のみ・合計は相手可視／**経費(会社)**=本人のみ可視（相手から完全に見えない） |

### A.2 シナリオ B（オンボーディング）ウォークスルーで解決した論点

| ID | 論点 | 決定 |
| --- | --- | --- |
| 論点5 | 役割（夫/妻）の判定方式 | **設定値（HUSBAND_LINE_USER_ID / WIFE_LINE_USER_ID）の許可リスト** で自動判定。第三者アクセスはエラー画面で拒否 |
| 論点6 | 初回 LINE Login 失敗時のリカバリ | **LIFF SDK 任せ**（独自リトライ UI なし、専用イベントなし）。家族用なので最小限 |
| 論点7 | Gmail OAuth の実装方式 | スコープ `gmail.readonly`、LIFF 内ブラウザは `disallowed_useragent` のため `liff.openWindow({external: true})` で **OS 標準ブラウザに切り出し**、トークンは Parameter Store（KMS）に保存 |
| 論点8 | Phase 2 セクションの順序強制度 | **A（Gmail OAuth）と B（初期残高）のみ必須・順序強制**、C/D/E は seed 投入で確認のみ任意、F は推奨だがスキップ可 |
| 論点9 | 初期残高の基準時刻 | **ユーザー入力時点**。後から修正可（運用中の残高補正と同枠組み） |
| 論点10 | 三井住友カード 未払金の初期値 | **ゼロから開始**、運用開始月以降のメール+CSV で積上げ。過去未払金は遡及取得しない |
| 論点11 | 残高のプライバシー | **本人のみ可視**。ただし **別銀行貯蓄 + NISA は合計を配偶者も可視** |
| 論点12 | カテゴリマスタの構造 | 規定 4 種は **世帯共有・削除改名不可**、追加カテゴリは **個人別**（追加・改名・削除可） |
| 論点13 | 経費種別マスタの構造 | カテゴリと同構造。規定 5 種は **世帯共有・削除改名不可**、追加項目は **個人別** |
| 論点14 | 月次上限の seed 値投入 | DB 初期化時に **個人別** に seed 投入（夫AI 10,000 / 妻AI 3,000 等）。Phase 1 の役割で自動紐付け |
| 論点15 | 「無制限」の DB 表現 | **`is_unlimited` 等の専用カラム**（マジックナンバー -1 等は使わない） |
| 論点16 | 取込開始タイミング | 個別 Phase 2 (A+B) 完了で **翌日 0:00 から日次バッチ稼働**（即時メール取込なし）|
| 論点17 | 運用開始の発火条件 | 夫婦両方の Phase 2 (A+B) 完了で **自動発火 + ログ記録**（操作ボタンなし）|
| 論点18 | 配偶者完了待ち中の挙動 | 自分のダッシュボード・取引一覧は **使える**、月次レポート画面のみ「準備中」で封印 |
| 論点19 | 配偶者完了の検知方式 | **画面ロード時のみ判定**（ポーリング・WebSocket は使わない）。アプリ内バナーで通知 |
| 論点20 | 運用開始月の月次レポート | **「不完全月」フラグ付き** で生成。**翌月 5〜10 日の通常サイクルで CSV 再取込 → レポート生成・配信** |
| 論点21 | LINE Bot 通知の有効化タイミング | **Phase 4（運用開始）と同時**。共通トークルーム ID は **join Webhook 自動取得**、Phase 4 完了時にテスト送信 |
| 論点22 | 日次バッチの取込範囲 | **過去 5 日以前のメールを毎回スキャン**、Gmail message ID で重複除外（Phase 2-F とのギャップ吸収・冗長化保険）|
| 論点23 | LINE 通知単発失敗の扱い | **完全スキップ**（ログのみ）。連続失敗時のみフェイルセーフメール（OQ-14 と整合） |
| 論点24 | Phase 2-F（初期 CSV/PDF 取込） | 対象月 = **運用開始日の当月**、取込範囲 = **CSV/PDF 内の全取引**、推奨だがスキップ可、CSV 取込は即時実行 |

### A.3 シナリオ C（未分類修正と memorization 学習）ウォークスルーで解決した論点

| ID | 論点 | 決定 |
| --- | --- | --- |
| 論点25 | 用語: 「目的軸」の改称 | **「費用区分」に改称**。月次レポートの既存表記「世帯費用」「個人費用」「経費(会社)合計」と直結し、収入取引には適用されない概念であることを明示 |
| 論点26 | 学習データのスコープ | **完全個人別（F-1）**。夫婦の学習データは別テーブル。配偶者の学習は一切波及せず、規定4種カテゴリでも個別学習。プライバシーと実装単純性を優先したトレードオフ |
| 論点27 | 学習データの構造 | **フィールド独立（T-2）**。加盟店名 → カテゴリ／費用区分／経費種別 を別マッピングで保持。「同じ加盟店でカテゴリは固定だが費用区分は揺れる」ケースに対応 |
| 論点28 | 費用区分の学習スコープ | **4 値全て学習対象**（世帯／個人(夫)／個人(妻)／経費(会社)）。F-1 配下では個人(配偶者) 値は出現しないが、ルックアップ動作・上書き判定の一貫性のため記録する |
| 論点29 | Amazon 取引の学習方式 | **加盟店名「AMAZON.CO.JP」は学習対象外**、商品カテゴリをキーに学習する **別テーブル（X-1）**。突合タイムアウトは双方向 3 日 |
| 論点30 | 未分類の発見動線 | **ダッシュボードに「未分類: N件」ウィジェットを常設**（C-2）。LINE 通知への混載はしない（明細を載せない原則と整合） |
| 論点31 | 未分類取引の費用区分デフォルト | **カード所有者の個人(本人)**（A-1）。経費種別は NULL |
| 論点32 | 未分類の集計上の扱い | **独立カテゴリとして表示**（B-1）。修正動機を与えるため目立たせる |
| 論点33 | 修正画面の構造 | **1 画面で 3 軸（カテゴリ／費用区分／経費種別）を編集**、未分類軸のみ赤マーカー（D-3） |
| 論点34 | 修正画面からのマスタ追加 | **修正画面に「+ 新規追加」を出し、その場で新規カテゴリ／経費種別を作成可**（E-1）|
| 論点35 | 学習データの反映タイミング | **保存ボタンで即時反映**（I-1）|
| 論点36 | 過去未分類取引への遡及 | **確認ダイアログ**（J-3）。対象は **本人の未分類取引のみ**（既分類・配偶者取引は触らない）|
| 論点37 | 既存学習ルール上書き | **「以後このルールに従いますか？」確認ダイアログ**（L-4）で「今回限り」と「ルール上書き」を分岐 |
| 論点38 | 学習無効化機能 | 修正画面に **「この加盟店は学習しない」チェックボックス**（M-1）。チェック後は常に「未分類」で取り込まれる |
| 論点39 | 夫婦間の分類不整合 | **容認**（K-1）。F-1 を採った時点で構造的に許容する思想 |
| 論点40 | CSV 取込時の一括分類 | CSV 取込完了画面で **新規N件／自動分類N件／未分類N件 サマリ表示**、その場で一括分類画面へ誘導（N-1）。同一加盟店の複数取引は 1 ルールに集約 |
| 論点41 | 未分類のままレポート生成 | **許容**（O-1、シナリオA 既存決定の継承）。後日分類で過去レポートが書き換わるのは仕様 |
| 論点42 | カテゴリ／経費種別の削除フロー | 移動先カテゴリ（or 経費種別）+ 費用区分をユーザー選択（Q-2 改）／ 学習データを移動先にリマップ（R-2 改）／ 名称変更は副作用なし（学習は id 参照） |
| 論点43 | スナップショット概念の廃止 | **廃止**。ダッシュボード・月次レポート画面はリアルタイム集計に統一。配信時点の値の凍結は **LINE 配信ログ**（送信 payload を json 保持）で代替 |
| 論点44 | Amazon 突合タイムアウト | **3 日**（双方向）。タイムアウト後は「Amazon 注文不明」フラグで未分類確定、ユーザー手動分類待ち（V-2）|

## B. 残る論点（実装フェーズで詰める）

| ID | 論点 | 補足 |
| --- | --- | --- |
| OQ-1 | SMBC通知メール／Amazon 注文確認メールの実フォーマット調査・パースルール | (1) 利用通知・入出金通知・引落通知・返金通知、それぞれの本文構造を実メールから確定する。(2) SMBC公式案内では通知対象外とされている支出（公共料金・通信料・ガソリン・ETC・10円以下 等）が実際には通知されるケースがあるかも実測（電気代は届く観察あり、家賃は妻のメールに届くか要確認）。(3) **経費精算入金の振込元名・摘要パターンを確定**（給与振込との区別ルール）。(4) **Amazon 注文確認メールの本文構造**（商品名・カテゴリ・合計金額の抽出ルール） |
| OQ-2 ✅ | Gmail OAuth トークン失効時の再認可フロー | **解決**: 検知 = API 呼び出し失敗時 ／ 通知 = LINE 個人 DM のみ（メールフェイルセーフ対象外） ／ 再認可 UX = アプリ経由（LINE メッセージのリンク → アプリ → OAuth 再認可ボタン） |

| OQ-4 ✅(改訂) | カテゴリ追加・統合UI | **シナリオC で精緻化**: 機能 = 追加・名称変更・削除のみ（統合・階層化なし） ／ 削除時 = **配下取引の移動先カテゴリ + 費用区分をユーザーが選択**（規定4種 or 残存追加カテゴリから／費用区分は4値＋現状維持）。学習データは移動先にリマップ。経費種別の削除も同構造 |
| OQ-5 ✅(深掘り) | 自動分類の学習機構 | **シナリオC で大幅深掘り**: ① **完全個人別（F-1）**: 夫婦の学習データは別テーブル、波及なし。② **フィールド独立（T-2）**: 加盟店名 → カテゴリ／費用区分／経費種別 を別マッピング。費用区分は 4 値全て学習対象。③ **Amazon 特例（X-1）**: 加盟店名「AMAZON.CO.JP」は学習対象外、商品カテゴリをキーに学習する別テーブル、突合タイムアウト 3 日双方向。④ **修正 UX**: 1 画面 3 軸編集、未分類軸赤マーカー、新規カテゴリその場で作成可（E-1）。⑤ **学習反映**: 即時（I-1）。⑥ **過去遡及**: 確認ダイアログ（J-3）、対象は本人の未分類取引のみ。⑦ **既存ルール上書き**: 「以後このルールに従いますか？」確認（L-4）。⑧ **学習無効化**: 「この加盟店は学習しない」チェック（M-1）|
| OQ-6 ✅ | 取り崩し（別銀行貯蓄口座出金）の入力UX | **解決**: 入力起点 = アプリの口座詳細画面から「取り崩しを記録」「残高を補正」ボタン（ユーザー主体） ／ 残高ズレへの気付き = 月次レポートに「別銀行貯蓄口座: X円（最終更新 N 日前）」を表示し、N 日以上更新なしならアラート色 |
