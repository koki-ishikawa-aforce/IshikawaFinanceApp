# ドメイン発見 Phase 1: ドメインの輪郭（改訂版）

> このドキュメントは IshikawaFinanceApp のドメイン駆動設計（DDD）における戦略的設計の一次成果物である。
> 改訂版（2026-04-30）: スコープを「自動で集計できる範囲のみ」に縮小した方針を反映。
> 初版は git 履歴で参照可能。

## 1. ドメインの種別

**2人家族（夫婦）向けの、SMBC 通知メールから自動集計する家計簿＋限定的な資産管理アプリケーション**

家計簿（収支管理）と、SMBC 経由で動く資金の限定的な資産推移把握を扱う。
**「自動で集計できるところだけを追いかける」ことを設計原則** とし、メール通知が届かないデータソースは原則対象外とする。

## 2. 解決したい課題（Why）

- 夫婦の SMBC 銀行口座・三井住友カードの動きを、自分で集計せずにカテゴリ別に把握したい
- NISA への積立累計と、SMBC・別銀行貯蓄口座の残高推移を、自動で時系列に追いたい

## 3. アクター

| アクター | 説明 |
| --- | --- |
| 夫 | アプリの利用者。自分名義の SMBC 口座／三井住友カード／別銀行貯蓄口座／NISA口座を持つ |
| 妻 | アプリの利用者。自分名義の同等の口座群を持つ |

夫婦は対等な利用者として扱う。世帯管理者ロールは設けない。

## 4. ユーザーゴール（達成したいこと）

優先度の高い順:

1. **支出を目的別に把握する**
   今月どれだけのお金を、どのカテゴリ（住居・光熱・通信／食費／娯楽／その他）で支出しているかを把握したい。
   会社の立替経費および会社からの経費精算入金は **家計分析からは除外** する（ただし残高・未払金管理には反映）。
2. **資産推移を時系列で把握する**（限定版）
   以下の3軸を月次推移で確認したい:
   - NISA への積立累計（**元本ベース**。評価額は対象外）
   - SMBC 銀行口座の残高
   - 別銀行貯蓄口座の残高

## 5. ドメインエキスパート

夫婦自身（=アクター=ドメインエキスパート）。専任のドメインエキスパートはいない。

## 6. 対象範囲

### 6.1 対象口座

| 種別 | 数 | 残高更新方式 |
| --- | --- | --- |
| SMBC 銀行口座 | 夫1・妻1（各自名義） | 入出金通知メールから完全自動 |
| 三井住友カード | 夫1・妻1（各自名義） | 利用通知・引落確定通知から完全自動（発生主義・未払金管理） |
| 別銀行 貯蓄口座 | 夫1・妻1（各自名義） | 初期残高は手入力。SMBC→当該口座振込で自動加算。取り崩しは手入力で記録 |
| NISA 口座（SBI / 楽天証券） | 夫1・妻1 | SMBC→証券会社振込から積立元本を自動累計。評価額は対象外 |

### 6.2 データソース

| 種別 | 役割 | 経路 |
| --- | --- | --- |
| **主データソース: SMBC 通知メール** | 1日1回のバッチ取込で暫定計上（取込ラグ最大24時間）。発生主義で支出・未払金・残高を更新 | 夫婦各自の Gmail に届く SMBC 通知メールを Gmail API（OAuth）で取得（EventBridge 起動の Lambda が日次実行） |
| **補助データソース: 引落確定通知メール** | 月のクレカ請求総額を確定。当月利用通知合計との **差額 = 通知対象外** を「不明」として一時計上 | 同上（Gmail） |
| **補助データソース: 明細 CSV / PDF**（カード／銀行 両方） | 通知対象外を含む全明細を確定。「不明」を消し込み、各取引を正規分類に昇格 | ユーザーが各社マイページから取得し手動アップロード（月1想定）。PC では CSV ダウンロード、スマホでは画面印刷で PDF 出力。**PDF は Lambda 内で Claude API（Anthropic SDK）に直接渡して CSV 形式に変換し、CSV 取込フローに合流する** |
| **補助データソース: Amazon 注文確認メール** | Amazon 利用時の商品情報を取得。SMBC カード利用通知と金額・タイミングで突合し、書籍購入を新聞図書費（経費種別）として自動判別 | 同上（Gmail） |

利用通知メールの仕様上、一部取引（公共料金・通信料・ガソリン・ETC・10円以下 等）は通知対象外であり、メール経由では取れない。これらは引落確定 → CSV 取込で確定する。

### 6.3 経費(会社)の精算プロセス

経費取引はカード利用通知時点では「暫定」、月の月次レポートは **3 段階** で確定する:

1. **暫定状態**（引落確定通知前）: 加盟店名／Amazon 注文情報から経費種別を推定し、月次上限内なら経費(会社)、超過分は個人(本人) として暫定計上
2. **CSV確定状態**（CSV 取込後）: 通知対象外も含む完全明細で月次の暫定経費合計を確定
3. **最終確定状態**（経費精算入金との突合後）: 当月分の経費精算が **翌月 15 日頃** に SMBC へ振込まれる → 振込合計と暫定経費合計の差額（不認定分）を「個人(本人)」費用に自動振替

経費種別マスタ（5 種類）:

| 経費種別 | 月次上限 |
| --- | --- |
| ジム | 5,000 円（個人別、当面同一） |
| 新聞図書費 | 5,000 円（個人別、当面同一） |
| AI 利用費 | **夫 10,000円 / 妻 3,000円**（ベース）。案件等で一時的に増減する場合は上限値を変更して対応 |
| 交通費 | 無制限 |
| その他経費 | 無制限 |

月次累計は **月初（毎月1日 0:00）にリセット**。

### 6.4 通知チャネル

LINE を主チャネルとし、メールはフェイルセーフ（重大障害時の保険）に位置付ける。

| 用途 | 経路 | 宛先 | タイミング |
| --- | --- | --- | --- |
| CSV 取込リマインダー | LINE | 夫婦共通のトークルーム | **毎月5日**（前月分の明細が確定するタイミング） |
| 月次レポート（世帯部分・全体サマリ） | LINE | 夫婦共通のトークルーム | **CSV 取込・分析完了後**（「CSV確定」状態に昇格したタイミング） |
| 月次レポート（個人部分） | LINE | 各個人 DM | 同上 |
| OAuth失効通知 | LINE | 該当本人の個人 DM | API 呼び出し失敗時に即時 |
| 致命的エラー通知（フェイルセーフ） | メール | 夫婦各自の登録メールアドレス | **LINE 連続送信失敗時のみ**（システム障害の最終手段） |

**月次レポート最終確定状態（経費精算入金後）は配信なし**。値のみ更新され、差分は次月レポートで吸収される。
**月次レポート暫定状態（毎月1日生成）も配信なし**（内部処理のみ）。

LINE 上には **明細を載せず、サマリ＋アプリへのリンク** のみ送る設計。詳細はアプリにアクセスして本人が閲覧する（プライバシールール3段階の徹底と、LINE のテキスト UX 制約のため）。

### 6.5 技術スタック・インフラ

| レイヤ | 採用技術 |
| --- | --- |
| **アプリ形式** | LIFF（LINE Front-end Framework） |
| **フロントエンド** | Next.js（React + TypeScript）の Static Export |
| **バックエンド** | Hono（TypeScript） on AWS Lambda |
| **API ゲートウェイ** | API Gateway |
| **バッチジョブ** | EventBridge → Lambda（日次メール取込・月次バッチ）|
| **データベース** | Neon Free Tier（PostgreSQL 互換、サーバーレス） |
| **シークレット管理** | AWS Systems Manager Parameter Store（KMS 暗号化） |
| **PDF→CSV 変換** | Anthropic SDK（Claude API）を Lambda から直接呼び出し |
| **静的配信** | S3 + CloudFront（**独自ドメインなし**、CloudFront のデフォルト URL を使用） |
| **HTTPS 証明書** | ACM（無料） |

月額運用コスト目安: **30〜200円/月**（Claude API の従量課金が主な変動要素）。AWS の無料枠と Neon Free Tier をフル活用してインフラ固定費を圧縮する方針。

### 6.6 アプリ画面構成

| 画面 | 内容 |
| --- | --- |
| ダッシュボード | 月次サマリ、残高、NISA積立累計、別銀行貯蓄口座残高（鮮度アラート付き）。プライバシールールに従い、相手の個人費用は **合計のみ**、相手の経費(会社) は **完全非表示** |
| 取引一覧 | 取引明細。フィルタ（カテゴリ／目的軸／所有者／月）。明細の閲覧範囲はプライバシールール適用 |
| 経費精算管理タブ | **本人のみ閲覧可**。経費取引の一覧と当月累計（合計のみ、進捗バーなし） |
| 口座詳細 | 各口座の残高・取引一覧。別銀行貯蓄口座は「取り崩しを記録」「残高を補正」ボタンで手入力可 |

### 6.7 対象外（明示的にスコープから外す）

- 現金（ATM出金後の使途、現金支出、実残高との突合）
- PayPay 等の電子マネー
- SMBC 以外の銀行・カード（取引通知メールが来ないため）
- NISA 以外の証券口座（特定口座・個別株）／証券時価評価
- 予算超過アラート・異常支出検知
- 夫婦間の精算・事前承認・目標貯蓄額合意
- 過去メール履歴の遡及取込（運用開始日以降のみ。初期残高は手入力で確定）

## 7. 設計原則の要約

- **自動で集計できるところだけを追う**。メールが届かない情報源は原則対象外、必要最小限の手入力で補完する。
- **自動分類は memorization 学習**。加盟店名→分類のマッピングはユーザー手動修正の蓄積から学習する（明示的なルール編集 UI は持たない）。未学習の加盟店は「未分類」フラグで取込み、ユーザー修正をトリガーに学習データへ反映する。
- **発生主義**。クレカ利用は決済時点で支出計上、引落は資金移動として扱う。
- **決済と資金移動を別概念** で扱い、二重計上を避ける。
- **所有者軸（夫/妻）と目的軸（世帯/個人/経費）を分離** する。所有者は口座属性、目的は取引フラグ。
- **目的軸は 4 値**: 世帯／個人(夫)／個人(妻)／経費(会社)。**経費(会社) は記録するが家計分析（ゴール①）からは除外** し、残高・未払金管理（ゴール②）には反映する。
- **プライバシールール（3段階）**:
  - **世帯**: 夫婦どちらも明細・合計が見える（フルオープン）
  - **個人(夫/妻)**: 本人は明細・合計が見える。相手は **合計のみ** 見える（明細不可視）
  - **経費(会社)**: 本人のみ可視。相手は **合計すら見えない**（家計の話ではないため）
