## 詳細タイムライン

### 🟢 4/1 00:00 — 月初リセット

- [🟥] **経費種別の月次累計が月初リセットされた**（月初の唯一のジョブ）

### 🟢 4/1 〜 4/30 — 月中: 日次取込ループ

毎日 00:00 に日次バッチが起動し、新着メールから取引・残高更新を反映。

#### 日次バッチの基本フロー

```
[🟥] 日次メール取込バッチが起動された（EventBridge スケジュール）
  ↓
[📩] 過去 5 日以前のメールが Gmail API で一括取得された
     （重複は Gmail message ID で除外、シナリオ B で確定）
  ↓
（メール種別ごとに分岐 — 下記 A〜H）
  ↓
[🟥] 日次バッチが完了した（処理件数・成功・失敗・未分類のサマリ）
```

> 注: 当初設計は「前回取込時刻以降の新着メール」だったが、シナリオ B（オンボーディング）の Phase 2-F（初期 CSV/PDF 取込）と運用開始時のギャップを埋めるため、過去 5 日分を毎回スキャンする設計に変更。冗長化保険にもなる（OQ-7 で重複検出は確定済）。

#### A. 📩 SMBC カード利用通知（電気代・コンビニ・ガソリン・Amazon 等）

```
[📩] SMBCカード利用通知メールが受信された
  ↓
[📩] メール本文がパースされ取引候補が抽出された
  ↓
[🟥] 取引のカテゴリが学習済み加盟店ルールから自動分類された
[🟥] 取引の費用区分（世帯/個人(夫)/個人(妻)/経費(会社)）が自動分類された
[🟥] 取引の経費種別が自動分類された（経費(会社) の場合）
（未学習加盟店なら「未分類」フラグで取込）
  ↓
[🟧] カード決済が発生した（発生主義で支出 + 未払金計上）
[🟧] カード利用が未払金として計上された
```

#### B. 📩 SMBC 銀行入金通知

```
[📩] SMBC銀行入金通知メールが受信された
  ↓
[🟥] 銀行入金の用途が入金日・金額・振込元名から自動判別された（OQ-21、2026-07-24 改訂）
     勤務先からの入金は 2 シグナルで判定する（摘要では給与と経費精算を区別できないため）
     - 入金日シグナル: 月内 21 日以降 → 給与寄り / 21 日より前 → 経費精算寄り
     - 金額シグナル: 25万円以上 → 給与寄り / 25万円未満 → 経費精算寄り
     - 2 シグナル一致 → 給与 または 経費精算入金 として確定
     - 2 シグナル矛盾 → 用途不明（手動確認待ち）。自動確定しない
     - 振込元が別銀行貯蓄口座 → 別銀行貯蓄からの戻し
  ↓
[🟧] 給与が振り込まれた / 経費精算入金が会社から SMBC に到着した /
     別銀行貯蓄口座→SMBC への入金が発生した
```

#### C. 📩 SMBC 銀行出金通知（NISA 引落の実引落・別銀行貯蓄への振込・ATM 出金 等）

```
[📩] SMBC銀行出金通知メールが受信された
  ↓
[🟥] 銀行出金の用途が振込先名から自動判別された
     - 別銀行貯蓄口座への振込 → シャドウ口座残高加算
     - その他 → 「その他」として保留
  ↓
[🟧] SMBC→別銀行貯蓄口座への振込が発生した（→シャドウ口座残高加算）
```

#### D. 📩 口座引き落としの事前お知らせ（NISA 積立）

```
[📩] 口座引き落としの事前お知らせメールが受信された（楽天証券分・SBI 証券分）
  ↓
[📩] 事前お知らせメールから引落予定（金額・予定日・引落先）が抽出された
  ↓
（引落予定日に達した時、自動的に）
  ↓
[🟧] 引落予定日に SMBC 銀行残高が引落予定額分自動減算された
[🟧] 引落予定日に NISA 積立累計が引落予定額分自動増算された
```

> 注: SMBC からの実引き落とし時に出金通知メールは届かない。事前お知らせメールが情報源。

#### E. 📩 楽天証券からの積立購入約定完了メール

```
[📩] 楽天証券から積立購入約定完了メールが受信された
     （差出人: service@rakuten-sec.co.jp）
  ↓
[📩] 約定メールから約定金額・約定日が抽出された
  ↓
[🟥] 約定金額と引落予定額の整合性が検証された
  ↓
（不一致なら）
[🟨] 約定金額と引落予定額のズレが検知された（アラート）
```

> SBI 証券分のメール形式は要実調査（OQ-1）。

#### F. 📩 SMBC カード返金通知

```
[📩] カード返金通知メールが受信された
  ↓
[🟨] 返金・返品でお金が戻ってきた
```

#### G. 📩 Amazon 注文確認メール

```
[📩] Amazon 注文確認メールが受信された
  ↓
[📩] Amazon 注文確認メールから商品情報（商品名・カテゴリ・金額）が抽出された
  ↓
（後日 SMBC カード利用通知が来た時）
[🟥] Amazon 注文と SMBC カード利用通知が金額・タイミングで突合された
  ↓
[🟥] 取引の経費種別が Amazon 注文情報から自動分類された
     （新聞図書費 等、加盟店名「Amazon」では判別不能なもの）
```

### 🟢 5/5 〜 5/10 — ユーザーによる CSV 取込

夫・妻 各自が任意のタイミングで取込。

```
[🟧] 明細 CSV または PDF（カード）がアップロードされた
  ↓
（PDF の場合）
[🟥] アップロードされた PDF が Lambda 内で Claude API（Anthropic SDK）を介して
     CSV 形式に変換された
（変換失敗時）
[🟨] PDF→CSV 変換に失敗し、ユーザーに通知された
  ↓
[🟥] CSV のフォーマット検証に成功し取込が完了した
（検証失敗時）
[🟨] CSV のフォーマット検証に失敗し取込が中止された
  ↓
[🟥] CSV から抽出された取引が、既存の通知由来取引と
     「日付・金額・加盟店名の 3 項完全一致」で突合され重複が除外された
  ↓
[🟥] CSV にしか無い取引（家賃・水道・ガス・通信費 等）が新規に取り込まれ、
     自動分類された（未学習加盟店は「未分類」フラグ）
```

### 🟢 5/10 — 夫婦両方の取込完了 → レポート生成・配信・配信ログ保存

```
[🟥] 夫婦両方のカード CSV 取込が完了した
  ↓
[🟫] 月次レポートが「CSV確定」状態に昇格した
     （ダッシュボード・レポート画面はリアルタイム集計、シナリオC 確定）
  ↓
[📱] 月次レポートのサマリ（世帯費用カテゴリ別・NISA 積立累計・残高推移）が
     Flex Message のリッチカード形式で LINE 共通トークルームに配信された
[📱] 月次レポートの本人サマリ（個人費用合計・経費(会社)合計）が
     Flex Message で LINE 各個人 DM に配信された
  ↓
[📱] LINE 配信ログが保存された（送信 payload を json 保持、シナリオC 確定）
     ※ スナップショット廃止に伴う配信時点の値の凍結用途。
       後日 5/15 の経費精算で 4 月レポートの値が遡及修正されても、
       配信時点の値は配信ログから参照可能
  ↓
[📱] CSV 取込完了が検知され、当月のリマインダー送信が停止された
```

> 注: 別銀行貯蓄口座残高の鮮度（最終更新日からの経過日数）は月次レポート画面でリアルタイム評価され、N 日以上更新がなければアラート色が付与される。

### 🟢 5/15 頃 — 経費精算入金到着 → 最終確定

```
[📩] SMBC 銀行入金通知メール受信（月内 21 日より前 + 25 万円未満 = 2 シグナル一致で経費精算入金と判別）
  ↓
[🟧] 経費精算入金が会社から SMBC に到着した
  ↓
[🟥] 経費精算入金額と当月の確定経費合計が突合された

ケース別:
─ 一致 → 全額認定、不認定分なし
─ 不足（経費合計 > 入金額）:
    [🟨] 不認定分が「個人(本人)」費用として 4月に遡及計上された
─ 過剰（入金額 > 経費合計）:
    [🟨] 超過分が「経費精算とは別の入金」として記録された

  ↓
[🟫] 月次経費精算サイクルが確定し、月次レポートが「最終確定」状態に昇格した
     ※ LINE 配信なし、値のみ更新（4月レポートを書き換える）
```

> 注: 4月レポートの数字が変わるため、5/10 に LINE 配信した数字とアプリで開いた数字が食い違う（仕様）。不認定分発生時のユーザー通知は無し（明細閲覧時に気付く運用）。

### 🏁 シナリオ A 終了

- 4月の月次レポート: **最終確定** 状態（内部ラベルのみ、配信済みの内容と数字は食い違っているが許容）
- 4月の LINE 配信ログ: 永久保持（5/10 配信時点の値の証跡）
- すべての 4月分取引: 確定
- 5月の取込ループは 5/1 から既に並走中
- ダッシュボード・月次レポート画面はリアルタイム集計のため、4月の値は現在の取引データから常に再計算される

## ウォークスルーで決定した主要ルール

| 領域 | ルール |
|---|---|
| ダッシュボード | DB の取引テーブルからリアルタイム集計（暫定レポート不要、シナリオC で月末スナップショットも廃止） |
| 月次レポート | CSV 取込完了時に「CSV確定」状態へ昇格（暫定状態は廃止、CSV確定／最終確定の 2 状態のみ） |
| 配信タイミング | 夫婦両方の CSV 取込揃いで一括（個人 DM・共通トークルーム同時） |
| CSV 種別 | カード CSV のみ。銀行 CSV はスコープ外 |
| 「分析」の定義 | CSV 取込完了 = 分析完了。未分類が残っていてもレポート生成 |
| 差額確定 | CSV 取込時に「CSV にしか無い取引」が新規取込される形で確定。引落確定通知は整合チェック用 |
| 配信時点の値の保持 | LINE 配信ログテーブルに送信 payload を json 保持（シナリオC 確定、スナップショット代替）|
| 銀行入金判別 | 勤務先入金は入金日（21 日以降=給与 / 前=経費精算）と金額（25 万円以上=給与 / 未満=経費精算）の 2 シグナル一致で確定、矛盾時は手動確認待ち / 振込元が別銀行貯蓄=戻し（OQ-21、2026-07-24 改訂）|
| 不認定分の計上月 | 4月に遡及（4月レポートを書き換え。LINE 配信済みの数字との食い違いは許容、過去レポート画面はリアルタイム再計算で最新値表示）|
| 入金過剰時 | 「経費精算とは別の入金」として記録、ユーザー手動確認 |
| 経費精算未着時 | 給料日（月末の給与入金時）まで待ち、未着ならアプリ内バナー → ユーザー判断 |
| 不認定分通知 | 通知なし、明細閲覧時に気付く |
| 未分類取引通知 | 通知なし、ダッシュボードの「未分類: N件」ウィジェットで気付く（シナリオC 確定 C-2）|
