# バンドルサイズ予算の運用

CI の `Bundle size budget (web)` ステップが何を測り、予算値をどう決め、超えたときに何をするか。

> 関連: [レビュー観点の体系](./README.md) §2 / §4、`.github/workflows/ci.yml`、`packages/web/bundle-budget.json`、`packages/web/scripts/`

## 1. なぜ測るのか

わりまるは LIFF(LINE アプリ内のブラウザ)で開かれる。外出先のモバイル回線で、アプリを開いてから画面が出るまでの待ち時間がそのまま使い勝手になるため、初期表示で落ちてくる量は劣化させたくない。

一方で初期表示の重さは、機能を1つ足すたびに数 kB ずつ増えるという形で進む。1回ぶんは誰も気づかないので、閾値を切って機械的に落とすのが唯一の防ぎ方になる(`README.md` §1 の「機械が判定できる観点は CI に寄せる」)。

なお N+1 やインデックス欠落といった「設計判断が要る性能問題」はクエリ側の話で、`/data-review` の担当。ここでは扱わない。

## 2. 何を測っているか

**書き出された HTML が参照している資産の gzip 合計**を、ルートごとに測る。

| 指標    | 中身                                                       |
| ------- | ---------------------------------------------------------- |
| `js`    | その HTML が参照する `_next/static/**/*.js` の gzip 合計    |
| `css`   | その HTML が参照する `_next/static/**/*.css` の gzip 合計   |
| `total` | 上記 + HTML 自体の gzip サイズ                             |

Next.js のビルドログが出す "First Load JS" を使っていない。あちらは polyfill と CSS を数に入れないため、実際に落ちてくる量より小さく出る(例: 導入時点の `/transactions` は Next.js の表示が 176 kB、実測が 224.7 KiB)。判断材料としたいのは「利用者の回線を実際に流れる量」なので、書き出し後の HTML を出発点にしている。

gzip は圧縮レベルを 9 に固定している。配信時の実際の圧縮率は CDN 設定に依存するが、ここで見たいのは絶対値ではなく変化量なので、再現可能な単一の基準で測れば足りる。

フォントの実体(`_next/static/media/*.woff2`)は数に入れていない。`unicode-range` で必要な字だけが後から取得されるため、初期表示で全部落ちてくるわけではない。

## 3. 予算値とその根拠

`packages/web/bundle-budget.json`(単位は KiB、gzip)。

```json
"default": { "js": 241, "css": 105, "total": 356 }
```

導入時点(2026-07-25、コミット `e4fc542`)の実測から決めた。各指標の**全ルート中の最大値に約 10% の余裕**を足し、KiB 単位で切り上げている。

| 指標    | 実測の最大値(ルート)              | 予算    | 余裕  |
| ------- | ---------------------------------- | ------- | ----- |
| `js`    | 224,698 B = 219.4 KiB(/transactions) | 241 KiB | +9.8% |
| `css`   | 97,570 B = 95.3 KiB(複数ルート)   | 105 KiB | +10.2% |
| `total` | 331,349 B = 323.6 KiB(/transactions) | 356 KiB | +10.0% |

余裕を 10% にした理由: ライブラリの小さな更新や文言追加で通常起きる変動(数 kB)は吸収しつつ、機能追加による段階的な肥大化(1 回あたり十数 kB 以上)は検出できる幅として選んだ。これより広げると1回の追加が丸ごと素通りする。

`css` が 95 KiB とかなり大きいのは、日本語ウェブフォント(Zen Maru Gothic)の `@font-face` 宣言が `unicode-range` ごとに数百個並ぶため。CSS の宣言そのものであり、フォント実体ではない。

予算はルート共通の `default` を全ルートに適用する。特定のルートだけ重い状態を正当化する必要が出たら、`routes` に個別指定を書ける(指定した指標だけが上書きされ、残りは `default` のまま)。

## 4. 超えたときにすること

CI のログに、どのルートの何が・予算をどれだけ超えたかと、超過が最大のルートで重い資産の上位が出る。まずそこを見る。

- **意図しない増加**(依存を1つ足したら共有チャンクが跳ねた、動的 import のつもりが静的に取り込まれていた等) → 実装を直す。予算は動かさない
- **意図した増加**(機能追加そのものによる増分で、削る余地が無い) → `bundle-budget.json` を更新し、**その PR の本文に新しい実測値と増えた理由を書く**。あわせて本ドキュメントの §3 の表も更新する

予算を「とりあえず通すために」上げるのは、この仕組みの目的をそのまま失わせる。上げるときは必ず根拠を残す。

## 5. 手元での実行

```bash
pnpm --filter @warimaru/web build       # 先に out/ を作る
pnpm --filter @warimaru/web bundle-size
```

超過の有無にかかわらず全ルートの実測値を表で出すので、予算を更新するときの数値はこの出力から取る。

判定ロジック(予算との突き合わせ、HTML からの資産抽出、超過表示)には `packages/web/scripts/bundle-size.test.mjs` に単体テストがある。境界(予算ちょうどは超過にしない / 1 バイト超えたら落とす)もここで固定している。
