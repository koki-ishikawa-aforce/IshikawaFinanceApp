# Phase 3 進行設計（戦略的設計フェーズ）

> 作成日: 2026-05-01
> ステータス: Draft（ユーザーレビュー待ち）

## 1. 目的とスコープ

### 1.1 目的

イシカワ家計アプリの **戦略的設計（Strategic Design）** を確定させ、Phase 4（実装計画）に渡せる状態にする。

### 1.2 Phase 3 の成果物（IN）

| # | 成果物 | 形式 |
|---|---|---|
| ① | 境界づけられたコンテキスト（Bounded Context）の特定 | 一覧 + 各コンテキストの責務記述 |
| ② | コンテキストマップ | drawio 図（外部システム = Gmail / LINE / SMBC / Anthropic API / 別銀行 / SBI / 楽天証券 含む） |
| ③ | サブドメイン分類（Core / Supporting / Generic） | 表＋根拠 |
| ④ | コンテキストごとのユビキタス言語 | **ドメイン記述ミニ言語**（kawasima 記法）で `data` / `behavior` を記述 |
| ⑤ | 集約候補のリストアップ | ④ の `data` のうちどれが集約ルート候補かを別途明示 |

### 1.3 Phase 3 で確定させない（Phase 4 以降に送る）

- 実装言語での型定義（TypeScript 型・Zod スキーマ等）
- 永続化方式（テーブル設計・正規化・インデックス）
- リポジトリ・ドメインサービス・ファクトリの細部
- API 境界（HTTP エンドポイント・GraphQL スキーマ）
- イベント駆動アーキテクチャの実装（メッセージブローカー等）

## 2. 方法論

### 2.1 採用アプローチ

**案2: コンテキスト先行ループ（ハイブリッド方法論）**

仮説 → 検証 → 補正のループで進める。具体的には:

1. イベントストーミング §1〜§12 と直感を土台にコンテキスト仮説を 5〜8 個立てる
2. 146 イベントを各コンテキストに割当て、ハマらないものを発見 → 境界補正
3. コンテキスト確定後、サブドメイン分類を後付けで判定
4. コンテキストごとにユビキタス言語を書く
5. 集約候補をリストアップ
6. コンテキストマップを描く
7. シナリオ A/B/C を「コンテキスト視点」で再走 + サニティチェックで検証

### 2.2 ユビキタス言語の記法

[kawasima のドメイン記述ミニ言語](https://scrapbox.io/kawasima/%E3%83%89%E3%83%A1%E3%82%A4%E3%83%B3%E8%A8%98%E8%BF%B0%E3%83%9F%E3%83%8B%E8%A8%80%E8%AA%9E)を採用する。理由は[ユビキタス言語の本質論](https://scrapbox.io/kawasima/%E3%83%A6%E3%83%93%E3%82%AD%E3%82%BF%E3%82%B9%E8%A8%80%E8%AA%9E)に基づく:

- ユビキタス言語は単なる用語集ではなく、4 層（lexicon / syntax / semantics / pragmatics）を持つ「言語」である
- 名詞だけ並べた用語集は lexicon 層しか書けない。ミニ言語ならば `data` / `behavior` / `AND` / `OR` / `?` / `->` / `List<>` で 4 層全部書ける
- 言語設計 = ドメインモデリングそのものである以上、ミニ言語で書くことが Phase 3 の中核作業になる

### 2.3 ミニ言語の方言（プロジェクト固有規約）

#### A. 言語選択

| 項目 | 採用 |
|---|---|
| `data` / `behavior` キーワード | 英語そのまま |
| `data` 名・`behavior` 名 | 日本語（ドメイン語彙そのまま） |
| 演算子 (`AND`/`OR`/`->`/`?`/`List<>`) | 英語そのまま |

例:
```
data 取引 = 取引ID
   AND 発生日時
   AND 金額
   AND 加盟店名

behavior 取引を未分類として取り込む = カード利用通知 -> 未分類取引
```

#### B. 命名・使い分けルール

新しい記法は B-1 のみ。それ以外は kawasima 既存記法の使い分け規約。

1. **集約ルート印（B-1、新規追加）**: `data` の前に `// aggregate root` コメントを入れる
   ```
   // aggregate root
   data 取引 = ...
   ```

2. **ACL（コンテキスト境界の翻訳層）の表現**: `behavior` で「外部スキーマ → 内部 data」の変換を明示。新記法ではなく `behavior` の用途規約。
   ```
   behavior SMBC通知メールを取引候補に変換する = SMBC通知メール本文 -> 取引候補 OR パース失敗
   ```

3. **ドメインイベントの表現**: イベント自体を `data` として定義し、`behavior` の出力に含める。
   ```
   data 取引確定済みイベント = 取引ID AND 確定日時 AND 確定理由

   behavior 取引を確定する = 暫定取引 -> 確定取引 AND 取引確定済みイベント
   ```

4. **不変条件・事前/事後条件**: `behavior` 直後の `//` コメントで書く（kawasima 既存記法の流用）。
   ```
   behavior 取引を経費(会社) に変更する = 取引 AND 経費種別 -> 経費取引
   // 事前: 取引の所有者 = 操作ユーザー
   // 事後: 当月の経費種別累計が再計算される
   ```

5. **クロスコンテキスト参照は ID で**: 別コンテキストの集約を参照する場合、その集約の ID 型のみを `data` で借りる。
   ```
   // referenced from: 経費精算コンテキスト
   data 経費種別ID = 文字列
   ```

#### C. ワークフロー記述（シナリオ再走で使用）

kawasima のワークフロー記述形式（`Bounded Context: ...` を冠した形式）を採用。

```
Bounded Context: 取引取込
ワークフロー: "SMBC利用通知メールを取り込む"
  トリガー: "SMBC利用通知メールが受信された"
  主要インプット: SMBC通知メール本文
  他のインプット: -
  出力イベント: "取引候補が抽出された"
  副作用: -
```

## 3. 実行ステップ

### Step 1. コンテキスト仮説の立案

- イベントストーミング §1〜§12 と直感を土台に 5〜8 個のコンテキスト案を立てる
- 各候補に「責務の一文」「核となる名詞」「想定される境界」を付ける
- 成果物: `07-bounded-contexts.md` §1 の暫定版

### Step 2. 仮説検証ループ（2〜3 周）

- 146 イベントを §単位で各コンテキストに割当て、ハマらないものを発見
- 1 つのイベントが複数コンテキストに跨る場合、責務分割か翻訳層が要るかを判定
- 仮説を補正（コンテキスト統合・分割・名前変更）
- 成果物: `07-bounded-contexts.md` §1 確定版 + §3 イベント帰属マッピング

### Step 3. サブドメイン分類

- 各コンテキストに Core / Supporting / Generic を割当
- 「Core はどこに自分の時間を集中させるか」の答えになるように分類根拠を書く
- 成果物: `07-bounded-contexts.md` §2

### Step 4. ユビキタス言語の記述（コンテキスト単位）

- コンテキストごとに `data` / `behavior` をミニ言語で書く
- フラグではなく OR、ステータスコードではなく状態と振る舞いで表現
- 状態遷移は `data X = 状態A OR 状態B` + `behavior 遷移 = 状態A -> 状態B` で書く
- 成果物: `08-ubiquitous-language.md`（インデックス）+ `08a-ul-<context>.md`, `08b-...`, ...（コンテキスト別、5〜8 ファイル）

### Step 5. 集約候補の特定

- Step 4 の `data` のうち「ライフサイクルの起点になる data」を集約ルート候補としてマーク（`// aggregate root`）
- 不変条件が集約境界に閉じているか確認
- 集約境界を跨ぐ参照が ID 経由になっているか確認
- 成果物: `09-aggregates.md`

### Step 6. コンテキストマップの作成

- drawio で各コンテキストと外部システムを図示
- 関係種別（共有カーネル / 顧客-供給者 / ACL / 公開ホストサービス / 順応者 / 別々の道 等）を明示
- 成果物: `docs/domain/diagrams/07-context-map.drawio` + `07-bounded-contexts.md` §4 の説明文

### Step 7. 検証フェーズ

#### 7-1. シナリオ A/B/C コンテキスト視点再走

各シナリオの主要ステップを kawasima ワークフロー記述で書き直す。
複数コンテキストを跨ぐステップは、コンテキストごとに分割。

- 成果物: `10-strategic-design-validation.md` §1〜§3

#### 7-2. DDD サニティチェックリスト（15 項目）

各項目に「OK / 要修正 / N/A」を付ける。

**戦略面**:
1. 各コンテキスト内でユビキタス言語が 1 つに揃っているか
2. コンテキスト境界をイベントが跨ぐ箇所に明示的な翻訳層（ACL）があるか
3. Core サブドメインに労力配分が向いているか（Phase 4 以降の実装優先順位が Core 中心に組まれる構成になっているか）
4. コンテキスト数が適正か（少なすぎ＝モノリシック / 多すぎ＝過剰分割）

**ミニ言語面（kawasima 指針）**:
5. フラグ（boolean）で状態を表現していないか → OR で書けないか
6. ステータスコードで状態を表現していないか → 状態 OR + 遷移 behavior で書けないか
7. `?`（Optional）が濫用されていないか
8. `behavior` が存在するか（anemic な記述になっていないか）
9. ほぼ同じ `data` がコピペで増えていないか
10. behavior の失敗パスが OR で明示されているか

**集約面**:
11. 集約ルートが各コンテキストで明確に決まっているか
12. 集約境界を跨ぐ参照が ID 経由になっているか
13. 1 トランザクションで守るべき不変条件が集約境界内に収まっているか

**運用面**:
14. シナリオ A/B/C で「主役コンテキストが切り替わるポイント」がすべて明示されているか
15. 03-open-questions.md の論点で Phase 3 解決分・残課題が整理されているか

- 成果物: `10-strategic-design-validation.md` §4

### Step 8. 既存ドキュメント更新とコミット

- `03-open-questions.md` に Phase 3 で解決したものを A.4 節として追記
- `02-event-storming.md` に「§単位 → コンテキスト」のマッピング表を §16 として追記（任意）

## 5. コミット粒度とブランチ運用

- **ブランチ**: main 直コミット（既存運用通り、1 人開発）
- **コミット粒度**: 1 step = 1 コミット を基本。Step 4 はコンテキスト 1 つ書ききって 1 コミット
- **コミットメッセージ例**:
  - `docs(domain): Phase 3 Step1 コンテキスト仮説を追加`
  - `docs(domain): Phase 3 Step4 取引取込コンテキストのユビキタス言語を追加`
  - `docs(domain): Phase 3 Step7 シナリオA再走で発見したコンテキスト境界の修正`
