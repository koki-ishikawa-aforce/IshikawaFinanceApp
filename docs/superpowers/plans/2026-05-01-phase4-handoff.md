## 2. UI 要求から逆算するデータ契約（家計分析が中心）

家計分析コンテキストの集約 / Read Model 設計時に以下の画面要求を満たす API が必要:

| 画面 | 必要データ | 集約・参照 |
|---|---|---|
| ダッシュボード KPI 4 枚 | 当月支出（世帯/個人）/ 貯蓄残高（SMBC + 別銀行）/ NISA 積立原資 / 資産合計 | 取引集約（家計分析）+ 口座集約（残高・資産推移管理） |
| ダッシュボード ドーナツチャート | 当月のカテゴリ別合計（世帯 or 個人モード） | 取引集約 |
| 月次レポート ヒーロー | 当月支出 + 前月比 + 前年同月比 | 取引集約 + 月次レポート集約 |
| 月次レポート 残高推移 | 直近 6 ヶ月の 4 軸時系列 | 月次レポート集約（残高推移パート）|
| 取引一覧 | 当月の取引（フィルタ可）+ プライバシー適用 | 取引集約 + アプリユーザー（プライバシー判定用） |
| 経費精算管理 | 当月の経費種別ごとの累計（合計のみ） | 月次経費サイクル集約 |

Phase 4 では **「画面 → データ契約 → リポジトリ I/F → 集約」** の方向で逆算してスキーマを定義する。

## 3. プライバシー 3 段階の実装位置（Phase 4 で決める）

選択肢:
- **(A) ドメインサービス層で適用**: `behavior 取引一覧を取得する(操作者ユーザーID, フィルタ)` の出力をプライバシールールでフィルタ
- **(B) Read Model 層で適用**: 表示用のクエリレスポンスを構築する段階でフィルタ（CQRS 風）
- **(C) リポジトリ層で適用**: ストレージから取り出す時点で除外

推奨: **(B) Read Model**。理由は (i) ドメインモデルは「ありのまま」を表現すべき (ii) 同じ取引データを世帯モード / 個人モードで違う見え方にする必要があるため、表示直前のレイヤで判定する方が自然。Phase 4 でこの方針を spec 化。
