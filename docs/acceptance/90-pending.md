## AT-901: Gmail OAuth 連携(シナリオB Section A)

残るブロッカーはトークン失効まわりのみ(#392)。認可フロー本体 — 認可 URL 生成・トークン交換・
Parameter Store へのトークン保管・LIFF から OS 標準ブラウザへの切り出し・再認可の受け口 — は実装済み。

未実装なのは失効を検知して知らせる側で、失効検知・LINE 個人 DM への失効通知・そこからの再認可導線が無い。
検知の主体となる Gmail からのメール取得(#412)と日次メール取込バッチ(#414)は実装済みで、取得時の
認可エラーは取込の失敗として区別して記録されるところまで来ている。残るのは、それを受けて
トークンを失効扱いにし、個人 DM で再認可を促す導線(#392)。昇格は #392 の完了後に行う。

昇格時の骨子:

- 各ユーザーが「Gmail 連携」から OS 標準ブラウザで Google 同意画面を開き、`gmail.readonly` で許可 → 連携完了になる
- キャンセル・エラー時に再試行できる
- 本人以外の Google アカウントでの代理認可ができない(または警告される)
- トークン失効時: API 失敗検知 → LINE 個人 DM → アプリ経由再認可の導線(OQ-2)

## AT-902: 日次メール取込バッチ(シナリオA 日次ループ)

残るブロッカーは定時起動のみ。Gmail からのメール取得(#412)、取得 → Gmail message ID による
重複除外 → パース → 取引候補の生成 → バッチ完了までを進めるワーカー(#414)、メール本文から
金額・加盟店名を読み取るパースルール(#415)はいずれも実装済みで、
`POST /api/imports/mail-batch` から手動で通しで動かせる。ワーカーを呼ぶ Lambda
ハンドラー(`dailyMailImportHandler`)と手動起動(`pnpm --filter @warimaru/api batch:daily`)も
#416 で実装済み。

未実装なのは、それを毎日決まった時刻に起動する EventBridge スケジュールルールの定義と
デプロイ(#35 / #56 / #57)。昇格はスケジュールの投入後に行う。

パースの対象はカード利用のお知らせ・振込入金のお知らせ・口座引き落としの事前お知らせの 3 種
(実メールで確定した本文構造は `docs/domain/08a-ul-取引取込.md` §2.1)。**銀行の出金通知メールは
届いていない**ため、下記「銀行出金の用途自動判別」はメール起点では確認できない(昇格時に
この行の扱いを決める)。

昇格時の骨子:

- 実際の SMBC カード利用後、翌日 0:00 のバッチで取引が自動取込される(過去5日スキャン・Gmail message ID 重複除外)
- 学習済み加盟店は自動分類、未学習は未分類フラグ
- 銀行入金の用途自動判別(勤務先入金は入金日 21日以降/前 と 25万円以上/未満 の 2 シグナル一致で給与/経費精算入金を確定、矛盾時は手動確認待ち / 貯蓄口座からの戻し)
- 銀行出金の用途自動判別(貯蓄口座への振込=シャドウ残高加算)
- 手動確認待ちになった入金を本人が給与/経費精算入金/貯蓄戻しのいずれかに確定でき、確定後は一覧から消える(判別ドメインと API は #390 で実装済み。実機で確認するには入金を発生させるバッチと確認画面が要る)
- 配偶者の手動確認待ち入金は一覧に出ず、確定操作もできない
- バッチ完了サマリ(処理件数・成功・失敗・未分類)が確認できる
- 夫婦の一方がまだ Gmail 連携をしていない場合、その人ぶんの取込は起動されず、取込記録が
  日を追って積み上がらない(#488)。連携済みの側の取込は通常どおり完了する。ただしバッチ
  全体は異常として上がるので、連携が済んでいないことには気づける(#514)

## AT-903: LINE 通知配信(シナリオA 5/5・5/10)

残るブロッカーはリマインダーを定時に起動するスケジュールルールの定義とデプロイ(#35 / #56 / #57)。
配信処理・本文生成・停止判定と、月次レポートサマリの配信(CSV 確定イベントで発火)は #389 で、
リマインダーを呼び出す Lambda ハンドラー(`csvImportReminderHandler`)と手動起動
(`pnpm --filter @warimaru/api batch:csv-reminder`)は #416 で実装済み。
手動起動を使えば実機で 1 回ぶんの配信は確認できるが、「毎日届く」ことの確認には定時起動が要る。
昇格は EventBridge スケジュールの投入後に行う。

昇格時の骨子:

- 毎月 5 日から CSV 取込完了まで、共通トークルームに CSV リマインダーが毎日届く
- 夫婦両方の CSV 取込完了で、月次レポートサマリが共通トークルームに Flex Message で届き、本人サマリが各 DM に届く
- 運用開始月(不完全月)のサマリには、世帯・本人のどちらにも金額の上に「データが不完全な月です」の注意書きが付く(#442-A。レポート画面の注意と同じ条件で出る)
- 配信ログ(payload JSON)が保存され、後からレポート値が遡及修正されても配信時点の値を参照できる
- 取込完了でリマインダーが停止する
- 単発配信失敗はその場では諦める(ログのみ)が、LINE がエラーを返した/接続できなかった場合は
  同じ通知が次の配信機会に改めて送られる(#441-A。月次レポートサマリは月に 1 通しか機会が無いため、
  1 回の失敗で永久に届かなくならない)。タイムアウトは LINE 側に届いている可能性があるため再送信しない。
  連続障害はフェイルセーフメール

## AT-905: 月次経費サイクルの月初自動開始(シナリオA 月初)

残るブロッカーは月初バッチを定時に起動するスケジュールルールの定義とデプロイ(#35 / #56 / #57)。
夫婦それぞれの当月サイクルを開始する処理(既存サイクルがあれば作らない冪等な開始・一方の失敗で
他方を巻き込まない失敗分離)は #413 で、それを呼び出す Lambda ハンドラー
(`monthlyExpenseCycleStartHandler`)と手動起動(`pnpm --filter @warimaru/api batch:monthly`)は
#416 で実装済み。手動起動を使えば実機で開始そのものは確認できるが、「月が替わると自動で開始
されている」ことの確認には定時起動が要る。昇格は EventBridge スケジュールの投入後に行う。

昇格時の骨子:

- 月が替わると、夫婦それぞれの当月の経費精算サイクルが開始されている(前月の累計は引き継がず 0 から始まる)
- 経費(会社)に分類した取引が、当月のサイクルに積まれる(サイクル未開始で取りこぼしが起きない)
- バッチが同じ月に再実行されても、サイクルは増えず当月累計も変わらない
- 一方のユーザーの開始に失敗しても、もう一方のサイクルは開始されている

## AT-906: 引落予定・約定整合チェック(シナリオA 5/11・NISA)

昇格時の骨子:

- 引落予定メールから予定(金額・予定日・引落先)が抽出され、予定日に SMBC 残高減算・NISA 累計増算が自動反映される
- 約定完了メールとの金額整合が検証され、不一致でアラートが出る
- カード引落確定通知と当月取引合計の整合が検証され、不一致でアラートが出る
- 同じ引落確定通知が再取込されても SMBC 残高が二重に減らない。逆に、消込だけ済んで残高が未反映のまま失敗した場合は、再取込で残高がちょうど1回分減って回復する(#388)

## AT-907: 残高の手動操作(取り崩し・補正・初期残高の後修正・口座非アクティブ化)

昇格時の骨子:

- 別銀行貯蓄口座の取り崩しを記録すると、残高がその額だけ減り、残高一覧・世帯資産合計に反映される
- 通帳の実際の残高で手動補正すると、補正後の値が残高一覧に反映され、残高鮮度(最終更新からの経過日数)が当日に戻る
- 残高を超える取り崩し・負の残高への補正が拒否される
- 取り崩し・残高補正を行うと、その操作(いつ・誰が・いくら。補正は補正前後の金額)が口座の操作履歴に 1 件ずつ残り、口座詳細画面(#406)で古い順に確認できる。拒否された操作(残高超過など)は履歴に残らない(#459)
- 初期残高を後から修正すると、それ以降の変動を保ったまま現在残高が同じ差分だけずれる(AT-502 の手順1〜3 と同じ操作を口座詳細画面から行う)
- 配偶者の口座に対する上記の手入力ができない(所有者本人のみ)
- 口座を非アクティブ化すると、残高一覧・世帯資産合計から外れ、以降その口座への残高操作ができない(対象は別銀行貯蓄・NISA のみ。三井住友系は取込基盤が管理するため拒否される)

⚠ 非アクティブ化は**取り消せない**。再アクティブ化の振る舞いが未実装で、「同一ユーザー × 口座種別は一意」の制約により同種別の登録し直しもできないため、シナリオ実施時に本番の口座を閉じてはいけない(実施は検証環境に限る)。再アクティブ化の要否は判断待ち。

ブロッカー: 上記の操作を行う口座詳細画面(#406「取り崩しを記録」「残高を補正」)が未実装。ドメイン関数と API(`POST /api/accounts/:id/withdraw`, `PUT /api/accounts/:id/balance`, `PUT /api/accounts/:id/initial-balance`, `POST /api/accounts/:id/inactivate`)は #397 で実装済みで、現時点では API 直接呼び出しでのみ確認できる。
