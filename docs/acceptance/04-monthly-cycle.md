# 04. 月次サイクル(AT-3xx)

一次資料: [docs/domain/04-scenario-a-monthly-cycle.md](../domain/04-scenario-a-monthly-cycle.md)

CSV 取込 → 一括分類 → CSV 確定 → 経費按分 → 精算入金突合 → 最終確定、の書き込みフルフロー。

> ⚠ 実施上の注意
>
> - 月次レポート・精算サイクルの状態を変更するため、**実運用サイクルと重ならない対象月**(運用開始前の過去月など)で実施するか、実運用の月次サイクルそのものを受入テストを兼ねて実施する
> - メール自動取込(日次バッチ)は未稼働のため、取引の入口は CSV / PDF アップロードと手動登録のみ(AT-902 参照)
> - AT-301 → AT-302 → AT-303 → AT-304 → AT-305 → AT-306 → AT-307 の順に連続実施する前提で書かれている(AT-308 は取込の入口が PDF になるだけで、この連続実施とは独立に実施してよい)

---

## AT-301: カード CSV 取込(検証・候補確認・重複除外)

- 目的: SMBC カード CSV のアップロード → 形式検証 → 候補確認 → 取込確定が動作し、既存取引と重複しないこと
- 対象: `${WEB_URL}/imports`
- 実施者: 両方(それぞれ自分のカード明細で)
- 前提条件: SMBC マイページからダウンロードした対象月のカード CSV(または同形式のテスト CSV)

| # | 操作 | 期待結果 | ☐ |
| --- | --- | --- | --- |
| 1 | 取込画面で「カード利用明細」を選び CSV をアップロード | ジョブが受付済み → 形式検証中 → 取込中と進行する | ☐ |
| 2 | 候補一覧を確認 | CSV の取引が候補として一覧表示される | ☐ |
| 3 | 候補から 1 件を除外して取込確定 | 除外した 1 件を除いた件数で取込が確定する | ☐ |
| 4 | 取引一覧を確認 | 取込済みの取引が表示される。学習済み加盟店は自動分類、未学習は未分類 | ☐ |
| 5 | **同じ CSV をもう一度アップロード**して確定まで進める | 日付・金額・加盟店名の3項一致で重複が除外され、二重計上されない | ☐ |
| 6 | 不正な形式のファイル(テキスト等)をアップロード | 形式検証エラーとなり取込が中止される(ジョブが「失敗」表示) | ☐ |

- 事後処理: テスト用 CSV(実明細でない場合)で取り込んだ取引は削除する。実明細ならそのまま実運用データとして残す
- 備考: 依存 API `POST /api/imports/csv`, `GET /api/imports/:batchId/candidates`, `PUT /api/imports/:batchId/confirm`, `GET /api/imports/status`。PDF アップロード(Claude API 変換)は AT-308 参照

## AT-302: 取込サマリと一括分類セッション

- 目的: 取込後のサマリ(新規N/自動分類N/未分類N)が表示され、未分類を一括分類できること(C4-1)
- 対象: `${WEB_URL}/imports`, `${WEB_URL}/transactions`
- 実施者: どちらか
- 前提条件: AT-301 で未分類を含む取込が完了していること

| # | 操作 | 期待結果 | ☐ |
| --- | --- | --- | --- |
| 1 | 取込完了画面のサマリを確認 | 「新規 N 件、自動分類 N 件、未分類 N 件」の内訳が表示される | ☐ |
| 2 | 取込完了画面の「取引一覧でまとめて分類する」から取引一覧へ進み、「未分類をまとめて分類する」を押す | 一括分類セッションが起動し、未分類取引が加盟店ごとにまとめて表示される(「1 / N 店舗」の進捗つき) | ☐ |
| 3 | 加盟店ごとに分類(カテゴリ/費用区分/経費種別)を割り当て、「この店舗の N 件を分類」で順に確定する | 対象取引がすべて分類され、加盟店ごとに学習ルールが一括登録される | ☐ |
| 4 | 最後の加盟店を確定してセッションを完了する | セッションが完了状態になり(「N 件を分類しました」)、ダッシュボードの未分類件数が減っている | ☐ |
| 5 | (別の取込で)一括分類の途中で「あとで続ける」を押して離脱し、取引一覧に戻る | 取引一覧に「まとめて分類が途中のままです」と再開の導線が出て、続きから分類できる | ☐ |
| 6 | 進行中のセッションで「まとめて分類をやめる」を押す | セッションが中断(abort)され、再開の導線が消えて新しい一括分類を始められる。分類済みの取引はそのまま残る | ☐ |

- 事後処理: テストで登録した学習ルールのうち実運用に不要なものを無効化・整理
- 備考: 依存 API `POST /api/classification/bulk-sessions`, `GET /api/classification/bulk-sessions/current`, `POST /api/classification/bulk-sessions/:id/complete`, `POST /api/classification/bulk-sessions/:id/abort`

## AT-304: 経費上限超過の先着順按分

- 目的: 経費種別の月次上限を超えた取引が、上限充当分と個人費用の子取引に自動分割されること(OQ-20 / シナリオC Step 6-A)
- 対象: `${WEB_URL}/expense-settlement`, `${WEB_URL}/transactions`
- 実施者: どちらか
- 前提条件: 対象月の自分のジム経費累計が 0 円であること(上限 5,000 円を仮定)

| # | 操作 | 期待結果 | ☐ |
| --- | --- | --- | --- |
| 1 | `TEST-ジム` 7,000 円の取引を登録し、費用区分=経費(会社)/経費種別=ジム に分類 | 分類が保存される | ☐ |
| 2 | 精算画面の経費種別累計カードを確認 | ジムの累計が上限 5,000 円に達し「上限到達」表示になる | ☐ |

| 4 | ダッシュボード・レポートの集計を確認 | 経費(会社) 5,000 円・個人 2,000 円として集計されている | ☐ |

- 事後処理: `TEST-ジム` 取引(親子)を削除し、累計が 0 に戻ることを確認。学習ルールを整理
- 備考: 依存 API `POST /api/expense-settlement/cycles/:id/prorate`(自動発動でない場合は明示操作)。上限値は AT-103 の seed 値を前提

## AT-305: 経費精算入金の突合(一致・不足・過剰)

- 目的: 精算入金額と確定経費合計の突合 3 ケースが仕様どおり動作すること(シナリオA 5/15)
- 対象: `${WEB_URL}/expense-settlement`
- 実施者: どちらか
- 前提条件: AT-303 で対象月のサイクルが「CSV確定済み」、経費(会社)取引が存在すること(例: 確定経費合計 5,000 円)

| # | 操作 | 期待結果 | ☐ |
| --- | --- | --- | --- |
| 1 | 入金待ち一覧を確認(`GET /api/expense-settlement/deposits/awaiting` 相当の画面) | 対象月の精算が入金待ちとして表示される | ☐ |
| 2 | **一致ケース**: 確定経費合計と同額の入金を登録 | 全額認定され、不認定分が発生しない | ☐ |
| 3 | **不足ケース**(別サイクルまたはやり直しで): 経費合計より少ない入金を登録 | 不足分が「個人(本人)」費用として対象月に遡及計上される | ☐ |
| 4 | **過剰ケース**: 経費合計より多い入金を登録 | 超過分が「経費精算とは別の入金」として記録される | ☐ |

- 事後処理: テストで登録した入金・遡及計上された個人費用取引を削除または訂正する。3 ケースを同一月で試す場合はサイクルのやり直し可否を確認し、できなければケースごとに別のテスト月を使う
- 備考: 依存 API `POST /api/expense-settlement/deposits`, `GET /api/expense-settlement/deposits/awaiting`。銀行入金メールの自動判別(入金日 21日以降/前 と 25万円以上/未満 の 2 シグナル判定)は未稼働のため入金は手動登録(AT-902 参照)

## AT-308: 明細 PDF の取込(PDF→CSV 変換)

- 目的: 明細 PDF をアップロードすると Claude API で明細が読み取られ、以降は CSV と同じ取込フロー(候補確認 → 確定)に合流すること。変換失敗が利用者に伝わり、ジョブが失敗状態になること
- 対象: `${WEB_URL}/imports`
- 実施者: どちらか
- 前提条件: 対象月のカード明細 PDF(三井住友カードの明細画面をブラウザの印刷から PDF 保存したもの)。API に `ANTHROPIC_API_KEY` が設定されていること
- 補足: AT-301〜307 の連続実施とは独立に実施してよい(取込の入口が CSV か PDF かの違いのみ)

| # | 操作 | 期待結果 | ☐ |
| --- | --- | --- | --- |
| 1 | 取込画面で「カード利用明細」を選び PDF をアップロード | ボタンが「PDF を変換中...」になり、多重送信できない | ☐ |
| 2 | 変換完了を待つ | ジョブが「取込完了」になり、新規候補・重複除外の件数が表示される | ☐ |
| 3 | 候補一覧を確認して取込確定 | PDF に記載の明細が候補として並び、確定すると未分類取引として登録される | ☐ |
| 4 | 取引一覧を確認 | 手順 3 で確定した取引が表示される(CSV 由来の取引と同じ扱い) | ☐ |
| 5 | **同じ PDF をもう一度アップロード**して確定まで進める | 日付・金額・加盟店名の3項一致で重複が除外され、二重計上されない | ☐ |
| 6 | PDF でも CSV でもないファイル(画像等)を選ぶ | アップロードせずに「取込できるのは CSV(.csv)と明細 PDF(.pdf)です」と表示される | ☐ |
| 7 | 明細以外の PDF(取引が読み取れないもの)をアップロード | ジョブが「失敗」表示になり、次にどうすればよいかを含む案内が表示される(合計金額・件数の不一致は取込を中止した旨が出る) | ☐ |

- 事後処理: テスト用 PDF(実明細でない場合)で取り込んだ取引は削除する。実明細ならそのまま実運用データとして残す
- 備考: 依存 API `POST /api/imports/pdf`(以降は AT-301 と同じ候補確認・確定 API)。変換は Anthropic API 呼び出しのため数十秒かかることがある。変換の検証は行数一致 + 合計金額一致(OQ-23)で、不一致時は取込を中止して失敗ジョブになる
