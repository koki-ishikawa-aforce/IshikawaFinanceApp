# 受入テスト(Acceptance Test)

本番環境に対して実施する受入テストの方針・シナリオ・チェックリスト。
**すべての対象シナリオが OK になったらリリース OK** とするリリースゲートとして運用する。

> 関連 Issue: 本番環境構築 / 受入テスト実施 / Playwright E2E 自動化(Issue 番号は各 Issue 参照)

## 1. 目的と位置づけ

- 本番環境(実インフラ・実 LINE 認証・実 DB)上で、主要ユーザーシナリオが期待どおり動作することを夫婦2人の実機で確認する
- 自動テスト(Vitest 単体・統合)が担保しない「本番構成での結合」「LIFF 実機動作」「プライバシー3段階ルールの実ユーザー間検証」を対象とする
- 各シナリオの手順・期待結果は、将来の Playwright E2E テストの**仕様ソース**を兼ねる

## 2. 対象環境と環境パラメータ

シナリオ本文は環境非依存で書き、以下のプレースホルダを実環境の値に読み替えて実施する。

| プレースホルダ | production | dev(ローカル) |
| --- | --- | --- |
| `${WEB_URL}` | (CloudFront URL — 本番構築後に記入) | http://localhost:3000 |
| `${API_URL}` | (API Gateway/Lambda URL — 本番構築後に記入) | http://localhost:3001 |
| `${LIFF_URL}` | (本番 LIFF URL — 本番構築後に記入) | —(dev は LIFF 無効・`X-User-Id` フォールバック) |

- 本番の認証は LINE ID トークン(LIFF)のみ。`X-User-Id` ヘッダによる代替認証は **非本番限定**(`NODE_ENV !== 'production'`)
- 本番の許可ユーザーは夫婦2人の LINE userID のみ(許可リスト外は拒否されること自体がテスト対象: AT-003)

## 5. 本番での書き込みテストの扱い

本アプリは夫婦2人専用の実データアプリであり、**本番でも書き込みを含むフルシナリオを実施する**方針(ユーザー決定)。ただし:

- 各シナリオは「事後処理」節を必ず持ち、作成したテストデータの削除・訂正手順を記載する
- テスト取引は加盟店名に `TEST-` プレフィックスを付けて実データと区別する(例: `TEST-コーナン`)
- 月次サイクル系(AT-3xx)は月次レポートの状態を変えるため、**実運用のサイクルと重ならない対象月**(過去の空き月など)を選んで実施する
- 学習ルールが登録されるシナリオでは、事後処理でルールの無効化・削除まで行う

## 6. 実施方法

1. 実施前に対象環境・対象コミット(またはタグ)を決め、下のマスタチェックリストの「対象コミット」に記入する
2. 各シナリオファイルの手順表に従って操作し、期待結果ごとにチェックを付ける
3. シナリオ末尾の「実施記録」に実施日・環境・実施者・結果を記入する
4. 全シナリオ完了後、マスタチェックリストを更新してコミットする(実施記録も差分として残す)
5. NG が出た場合は Issue を起票し、修正 → 再デプロイ後に **NG になったシナリオと関連シナリオを再実施** する

## 8. Playwright E2E 自動化との分担

受入シナリオの一部は `e2e/` ワークスペースの Playwright テストとして自動化されている。自動化済みのシナリオは PR ごとに CI で回帰検証されるため、本番受入テストでは手動確認の優先度を下げてよい（CI green であれば手動チェックリストで ✅ として扱える）。

| AT-ID | 自動化状況 | 備考 |
| --- | --- | --- |
| AT-001 | 自動化済み | API ヘルスチェック（`e2e/tests/smoke/at-001-api-health.spec.ts`） |
| AT-004 | 自動化済み（部分） | KPI 表示・NaN 検証（`e2e/tests/smoke/at-004-dashboard-widgets.spec.ts`）。モックデータによる検証のため、実データの整合性は手動で確認する |
| AT-005 | 自動化済み | 全画面スモーク巡回（`e2e/tests/smoke/at-005-screen-smoke.spec.ts`） |
| AT-201 | 自動化済み | 取引 CRUD（`e2e/tests/classification/at-201-transaction-crud.spec.ts`）。API 経由で登録・編集・削除・未分類件数を検証 |
| AT-202 | 自動化済み | 3軸分類と学習ルール即時登録（`e2e/tests/classification/at-202-classify-learning.spec.ts`）。API 経由で分類・ルール確認・ルール適用を検証 |
| AT-301 | 自動化済み | カード CSV 取込・候補確認・除外確定・重複除外・不正ファイル検証（`e2e/tests/monthly-cycle/at-301-csv-import.spec.ts`） |

実行方法（ローカル）:

```bash

DATABASE_URL=postgres://postgres:postgres@localhost:5432/warimaru_test \
  pnpm --filter @warimaru/e2e test:e2e
```

## 9. 実装時の照合(シナリオを最新に保つ運用)

本チェックリストはリリース直前にだけ使うものではなく、**実装のたびに最新に保つ**。`/issue-work` は PR を作る前に、その変更が本ファイル群のどのシナリオに当たるかを照合する工程を持つ(`.claude/skills/issue-work/SKILL.md` 手順6)。

- 該当する AT 番号は PR 本文の「受け入れシナリオ(AT)」節に記録される。受入テストの実施時は、対象コミットまでの PR を辿れば **どのシナリオを再実施すべきか** が分かる
- ユーザーに見える振る舞いを足したのに該当シナリオが無い場合は、同じ PR でシナリオを追加する。§4 の ID 規約で領域を決め、§7 のマスタチェックリストにも行を足す。未実装機能に依存してまだ実施できないものは [90-pending.md](./90-pending.md) の AT-9xx に置く
- 既存シナリオの手順・期待結果が成立しなくなる変更では、実装とシナリオのどちらが正かを決める。実装が正しければ同じ PR でシナリオ側を更新し(**実施記録の表は消さない**)、シナリオが正しければ実装を直す
- どちらが正か決められない場合は `needs-decision` ラベル付きの Issue に切り出し、`/decide` で判断する

この工程の担保状況は [docs/review/README.md](../review/README.md) §2 の「機能適合性」行に位置づけている。
