## AT-101: 役割自動判定と /api/me 整合

- 目的: 許可リストに基づき夫/妻ロールが自動判定されること(シナリオB P1-1)
- 対象: `${WEB_URL}/onboarding`, `GET /api/me`
- 実施者: 両方
- 前提条件: AT-002 合格

| # | 操作 | 期待結果 | ☐ |
| --- | --- | --- | --- |
| 1 | 夫の実機でアプリを開く | 夫(darling)ロールとして扱われる(画面表記・設定画面の上限などが夫向け) | ☐ |
| 2 | 妻の実機でアプリを開く | 妻(honey)ロールとして扱われる | ☐ |
| 3 | (可能なら)`GET /api/me` のレスポンスを確認 | それぞれの viewerId・ロールが正しい | ☐ |

- 事後処理: なし
- 備考: ロール解決は許可リスト(`NeonAllowlistQuery`)。判定を UI から直接確認しづらい場合は、AT-603(夫婦で異なる月次上限 seed)で間接確認できる

## AT-102: 初期残高の入力

- 目的: 運用開始時点の残高(SMBC 残高・別銀行貯蓄・NISA 累計)を登録でき、残高画面に反映されること(シナリオB Section B)
- 対象: `${WEB_URL}/onboarding`(Section B), `${WEB_URL}/balances`
- 実施者: 両方
- 前提条件: AT-101 合格

| # | 操作 | 期待結果 | ☐ |
| --- | --- | --- | --- |
| 1 | オンボーディングの初期残高セクションを開く | SMBC 残高 / 別銀行貯蓄残高 / NISA 積立累計 の入力欄が 1 画面に表示される | ☐ |
| 2 | 3 項目に実際の残高を入力して保存 | 保存が成功する | ☐ |
| 3 | `/balances` を開く | 入力した値が各口座残高として表示される | ☐ |
| 4 | カード未払金の表示を確認 | 0 円から開始している(初期入力対象外: P2-B2) | ☐ |

- 事後処理: 本番の実運用値をそのまま登録するため削除不要。テスト値を入れた場合は正しい実残高で再入力し直す
- 備考: ⚠ 初期残高登録がバックエンド API に接続されていない場合(localStorage のみ)は、`/balances` への反映が確認できない。その場合は NG ではなく「未接続」として備考に記録し、接続後に再実施

## AT-104: 配偶者未完了時のレポート封印と解放

- 目的: 片方のみオンボーディング完了の状態では月次レポートが「準備中」で封印され、両者完了で解放されること(シナリオB P2-8)
- 対象: `${WEB_URL}/reports`
- 実施者: 両方(完了タイミングをずらして実施)
- 前提条件: 夫婦の一方が未完了の状態を作れること(初回オンボーディング時に実施するのが自然)

| # | 操作 | 期待結果 | ☐ |
| --- | --- | --- | --- |
| 1 | 先に完了した側で `/reports` を開く | 「準備中」相当の封印表示になる | ☐ |
| 2 | 同じユーザーで `/`(ダッシュボード)・`/transactions` を開く | 封印されず通常どおり使える(P2-横断ルール) | ☐ |
| 3 | もう一方がオンボーディングを完了する | — | ☐ |
| 4 | 先に完了した側で画面を再ロードし `/reports` を開く | 封印が解除されレポート画面が使える | ☐ |

- 事後処理: なし
- 備考: ⚠ 配偶者完了検知(SpouseCompletionQuery)がバックエンド未接続の場合、この封印/解放が localStorage ベースの疑似動作になっている可能性がある。その場合は「未接続」と記録し、接続後に再実施。検知は画面ロード時のみ(P3-3、ポーリングなし)である点に注意
