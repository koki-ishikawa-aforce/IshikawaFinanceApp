# よいワークフローの基準と現状評価

「何をもって**よい**ワークフローとするか」を言語化する。[04-principles.md](./04-principles.md) が**手段**(なぜこの形にしたか)を定めるのに対し、本書は**目的**(どうなっていれば良いか)を定める。基準は実装から独立に成立し、原則は基準に奉仕する — 原則を捨てても基準を満たせるなら、原則のほうを改訂してよい。

本書の位置づけ:

- **`docs/review/README.md` §2 との関係** — あちらは**プロダクトの品質特性**(機能適合性・性能・信頼性…)の担保表。本書は**ワークフロー自身の品質**の評価。プロダクト品質の担保が機能していること自体は、本書では基準2(安全性)の一部として参照する
- **`/retro` との関係** — 本書が `/retro` 手順5(ワークフロー全体の点検)の**物差し**。各基準の「測り方」に沿った実測は `/retro` が週次で行い、評価が変わったと判断したら現状評価の改訂案を `[改善案]` Issue として出す。採否は `/decide`
- **実測値を本書に書かない** — 数値はすぐ古びる。本書が持つのは基準・測り方・定性評価(判定と根拠)まで。今週の実測は `/retro` の報告が持つ
- **本書が測るのは output(処理量・効率)まで** — 何に価値があるか(outcome)の判断は、起票(`/issue-create`)と着手承認(人間)が担い、ワークフローはそれを前提に動く。「マージ数が多い = 生産的」ではない。価値の低い Issue が承認されればワークフローはそれを高速に処理してしまう — この限界は基準では捕まえられないため、承認の質は人間の責務として残る

## 2. 各基準の定義と評価

各基準は「基準 / なぜ良さの条件か / 測り方 / 現状評価」で書く。根拠は実装の複製ではなく参照で示す。

### 基準1: スループット — ◎

**基準** — 人間が着手を承認した仕事は、それ以降人間が何もしなくても `main` に到達し続ける。詰まっても、詰まりが後続の仕事を巻き込まない。量(単位時間あたりに流れる件数)と速さ(1件あたりの所要時間)は別物で、両方を見る。

**なぜ良さの条件か** — このワークフローの存在理由そのもの。人間1人 + AI の体制では、人間の手が空くのを待つ工程が1つあるだけで全体がその速度に律速される。

**測り方** — 週あたりのマージ数。リードタイム(着手承認からマージまでの経過時間)。open PR の滞留日数。

**現状評価** — ◎。定期 fire(2時間おき)・回収マージ・候補ループ(最大5件)・WIP 上限による流量制御が揃っており、承認からマージまでの全工程が無人で回る([01-lifecycle.md](./01-lifecycle.md) §5)。詰まりの主要因は基準4のキュー滞留に移っている。

### 基準2: 安全性 — ○

**基準** — 壊れた変更が `main` に入る頻度が低い。入ってしまったときは、それに気づき、巻き添えを最小で止め、速く復旧できる。取り返しのつかない操作は起きない。

**なぜ良さの条件か** — 自動化の信頼はここで決まる。`main` が壊れる自動化は、結局すべての出力を人間が再確認することになり、基準4ごと崩壊する。

**測り方** — `[main 赤]` Issue の件数 / マージ数(change failure rate 相当)。`main` 赤から復旧までの時間。1件の赤が巻き添えにした PR・fire の数。ガード(hooks・ブランチ保護)が実際にブロックした件数。

**現状評価** — ○。予防は7層のゲート([01-lifecycle.md](./01-lifecycle.md) §3)と実行時ガード(hooks)、封じ込めは「`main` が赤い間はバックログを止める」preflight、検知は `notify-main-failure` のメール通知が担う。復旧は `push` イベントでの失敗に限り `auto-revert-main-failure` が forward-fix を待たず revert PR を自動作成・マージまで進める(`docs/review/README.md` §4、#739)。既知のギャップは semantic conflict を**予防ではなく検知でカバー**していること([04-principles.md](./04-principles.md) 未解決課題)。プロダクト品質の担保そのもの(何を CI とレビューが見るか)は `docs/review/README.md` §2 を正とする。

### 基準3: 回復性 — ○

**基準** — 自動実行は必ず途中で死ぬ、を前提に、どんな死に方をしても次の起動が痕跡を機械的に検出して片付け、自力で通常運転に戻る。人手による「掃除」を必要としない。

**なぜ良さの条件か** — 無人運用の停止は静かに起きる(エラーではなく「毎 fire 何もせず終わる」形をとる)。自己回復がないと、停止に気づくのも直すのも人間になり、無人の意味がなくなる。2026-07-23 のゴミロックによるバックログ全停止が実例([02-labels.md](./02-labels.md) §5)。

**測り方** — 人手の介入が必要だった停止の件数。ゴミロックの残存時間(preflight が回収するまでの時間)。回収経路(即時 / preflight)ごとの発動件数。

**現状評価** — ○。preflight の4段の後始末(`main` 健全性・ゴミロック回収・コンフリクト先解消・回収マージ)と `unlock-in-progress-on-pr-close` の即時回収で、既知の死に方は自走で戻る([04-principles.md](./04-principles.md) 原則9)。ギャップは回復判定の規律が**手順の遵守に依存**していること — 2026-07-24 の二重着手は回収条件を自然言語の判断で緩めたことが原因で、同型の逸脱は構造的には塞がれていない(hooks のような実行時ガードがこの判定には無い)。

### 基準4: 人間の注意の効率 — ○

**基準** — 人間が使う時間が「人間にしか決められないこと」だけに使われる。判断待ちは1つのキューに集約され、まとめて処理でき、届いたことに確実に気づける。機械が判定できることの追認に人間を使わない。

**なぜ良さの条件か** — この体制で最も希少な資源は人間の注意。承認・確認の点が増えるほど自動化はその点で律速され、逆に判断が散らばると見落としが起きて基準2を毀損する。

**測り方** — マージ1件あたりの人間タッチ数(理想は着手承認の1回)。`needs-decision` の滞留件数と滞留日数。判断依頼への初動時間。

**現状評価** — ○。人間のゲートは着手承認1点に前倒しされ([04-principles.md](./04-principles.md) 原則1)、判断待ちは種類を問わず `needs-decision` に集約されてメール通知が届き、`/decide` で一括消化できる(原則2)。ギャップは**キューの消化そのものが人間依存**であること — 滞留すると対象 Issue の自動化が止まり、基準1に跳ね返る。滞留の観測は `/retro` 手順5に組み込み済みだが、観測は消化を保証しない。

### 基準5: フィードバックの速さ — ○

**基準** — 同じ失敗なら、より内側(速く・安い)の層で捕まる。外側の層(CI・マージ後)で初めて見つかる失敗は、内側では原理的に捕まえられないものだけになっている。

**なぜ良さの条件か** — 失敗の検知が遅い層に寄るほど、修正1回あたりの往復コスト(push・CI 待ち・fire の寿命)が積み上がり、基準1と基準2を同時に毀損する。

**測り方** — CI で初めて発覚した失敗のうち、内側の層(hooks / `/verify` / レビュー)で捕まえられたはずのものの割合。同一エラーでの `/verify` リトライ回数。`main` で初めて発覚した失敗の件数。

**現状評価** — ○。hooks(秒)→ `/verify`(分)→ レビュー(分)→ CI(〜8分)→ `main` 失敗通知 → `/retro`(週次)の6層が内側優先で張られ、整形起因の CI 失敗は `format-after-edit` により原理的に起きない([01-lifecycle.md](./01-lifecycle.md) §4、[04-principles.md](./04-principles.md) 原則7)。ギャップは**ローカルと CI の検証の非対称**(`pnpm test` は統合テストを含まない)で、「ローカル全 green なのに CI 赤」が構造的に残る([04-principles.md](./04-principles.md) 未解決課題)。

### 基準6: 可観測性(ワークフロー自身の) — △

**基準** — ワークフローに何が起きたか(何が・いつ・なぜ止まった / 撤退した / 落ちたか)を、後から機械的に集計できる形で追える。振り返りが「テキストの発掘」ではなく「記録の集計」でできる。

**なぜ良さの条件か** — 基準7(自己改善)の前提。観測できない失敗は改善に還元できず、観測のコストが高いと振り返りの精度と頻度が下がる。ワークフローが AI 駆動開発の研究土台であるためにも、挙動のデータが残ることが要る([README.md](./README.md) 目的2)。

**測り方** — 撤退・ゲート落ち・リトライの理由が、機械的に抽出可能な形(ラベル・目印・定型フォーマット)で残っている割合。`/retro` のデータ収集に要する探索量(何をどれだけ読み直す必要があるか)。

**現状評価** — △。痕跡は残る(撤退は Issue コメント、種別はタイトル目印、状態はラベル)が、**分散した自由テキスト**であり、`/retro` は毎回 PR 本文・コメント・CI ログから状況を再構成している(`.claude/skills/retro/SKILL.md` 手順2)。定型の記録形式や集計の仕組みは無く、fire 自体のログ(何を試して何秒で死んだか)は Routine のセッション外には残らない。なお、ここで言うのはワークフロー自身の可観測性であり、**プロダクト側の可観測性基盤の不在**(`docs/review/README.md` §2 信頼性の注記)とは別の問題。

### 基準7: 自己改善性 — ○

**基準** — 運用が生んだ失敗データが定期的に振り返られ、繰り返すパターンが仕様(手順・原則・テンプレート)の改訂として還元される。改訂には根拠(どの失敗から来たか)が残り、同じ議論を繰り返さない。

**なぜ良さの条件か** — ワークフローの正解は事前に設計しきれない。失敗から学ぶループが閉じていなければ、同じ失敗への個別対応が恒久コストになる([04-principles.md](./04-principles.md) 原則10)。

**測り方** — `[改善案]` Issue の起票数と消化数の乖離。改善が実際に仕様([04-principles.md](./04-principles.md)・`SKILL.md`)の改訂に到達した件数。同一原因の失敗の再発間隔。

**現状評価** — ○。`/retro`(収集 → パターン抽出 → ワークフロー全体の点検 → 起票)→ `/decide`(採否 → docs 反映)→ `/issue-work`(実装)のループが繋がっており、決定と原則の還元先も定義済み。ギャップは基準4と同根 — **ループの最後の一歩(消化)が人間依存**で、滞留すればループは開いたままになる([04-principles.md](./04-principles.md) 未解決課題)。

### 基準8: 進化可能性 — ○

**基準** — ワークフロー自体の変更が安い。手順・判定・観点はそれぞれ1箇所を直せば全体に効き、リポジトリの外(画面からしか触れない設定)に散らばった定義の貼り直しを必要としない。

**なぜ良さの条件か** — 基準7で改善案が採用されても、反映のコストが高ければ改訂は滞る。定義が複数箇所にあると片方だけが更新されて食い違い、基準2(予期しない挙動)にも波及する([04-principles.md](./04-principles.md) 原則3・11)。

**測り方** — 手順変更1件に必要なリポジトリ外の操作(Routine プロンプトの貼り直し・設定画面の変更)の数。同一定義の重複箇所数(`/docs-drift` 突合 D が検知)。

**現状評価** — ○。手順の正は `SKILL.md`、判定の定義は1箇所、docs は参照で繋ぐ規律が確立しており、マージした次の fire から新手順で動く([03-agent-runtime.md](./03-agent-runtime.md) §5)。ギャップは2つ: `/retro` と `/docs-drift` の Routine プロンプトが**手順を含んだまま**で変更に貼り直しが要ること(`docs/automation/retro-routine.md`・`docs-drift-routine.md` に「未実施」と記載)、リポジトリのファイルに書けない設定(ブランチ保護・cron)は記録との同期を保証できないこと(原則11 適用限界)。

### 基準9: 収束性 — ○

**基準** — 1つの仕事の完了が新しい仕事を生む割合(増殖率)が1を下回る。人間が新しい要件を足さない限り、バックログは処理とともに純減していく。完了は完了のまま残る。

**なぜ良さの条件か** — 増殖率が1以上だと、スループット(基準1)がいくら高くても仕事の総量は減らず、**処理しているのに前に進んでいない**状態になる。このワークフローは「仕事を捨てない」設計 — レビュー見送りは必ず Issue 化、撤退は判断依頼 Issue、`/retro` は `[改善案]`、`/docs-drift` は `[乖離報告]` を起票する — なので、1件のマージが複数の新規 Issue を生むことが構造的に起こりうる。品質と追跡可能性のためのこの機構は、意識的に観測しない限り増殖として現れる。

**測り方** — 期間内のバックログ純増減(closed Issue 数 − ワークフロー自身が生んだ新規 Issue 数。人間起点の新規要件は分けて数える)。マージ1件あたりの派生 Issue 数(増殖率)。派生の内訳(レビュー見送り / 判断待ち / 改善案 / 乖離報告)。

**現状評価** — ○。#663(2026-08-25)決定後の起票閾値の厳格化(#673: 見送りは (a) 独立した PR が必要な別リファクタリング相当の規模 / (b) ユーザーの意思決定が必要な設計判断のみを Issue 化)が実際に効き、直近1週間(2026-08-24〜08-31)の実測(#786)でバックログは純減に転じた — 期間内の Issue 作成61件・クローズ99件で純増減 -38、ワークフロー自身が生んだ新規 Issue(`[判断待ち]`/`[改善案]`/`[乖離報告]` 目印付きおよび `/decide` セッションからの分解実装 Issue、計59件)を除いて比較しても 99 − 59 ≒ +40 の純減。報告時点で open な `ready-to-implement`・`needs-decision` はともに0件で、バックログは完全に消化されている。既知のギャップは**この実測がまだ1期間分**であること — 増殖率が構造的に1未満へ落ち着いたのか、1期間限りの好転かは複数期間の推移で判断する必要があり、次回以降の `/retro` が追加観測する。また、バックログが枯渇するほど純減が進むと無人モードの fire が候補なしで空振りする割合が上がる(基準10 の裏返し)ため、両基準は合わせて見る必要がある。

### 基準10: 資源効率 — ○

**基準** — 同じ成果を、より少ない投入 — fire 回数・CI 実行分数・リトライ往復・トークン — で出せている。空振りと待ちが少ない。

**なぜ良さの条件か** — 実行資源は有限(CI は GitHub Actions の無料枠、fire は2時間に1回、セッションには寿命がある)。効率が悪いと、資源の上限がそのままスループット(基準1)の上限になる。また空振りやリトライの多さは、それ自体が上流の欠陥(Issue の曖昧さ・検証の非対称)のシグナルでもある。

**測り方** — マージ1件あたりの fire 数・CI run 数・リトライ回数。fire の空振り率(候補なし・撤退のみで終えた fire の割合)。CI 実行枠の消費時間。

**現状評価** — ○。効率化の機構は多い — CI は変更パスでステップを出し分け、追い越された run はキャンセルし(`docs/review/README.md` §4)、fire は候補ループと WIP 上限で無駄打ちを抑える。ギャップは**計測の不在**: 空振り率・リトライ回数は観測しておらず、トークン消費に至っては観測手段自体が無い。「効率が悪化した」ことに気づく仕組みがないため、評価は機構の存在に基づく推定に留まる。

### 基準11: 到達性 — ❌

**基準** — マージされた変更が、実際に利用者(夫婦2人)に届いている。`main` への到達だけでなく、本番環境への反映・稼働状況の監視・障害からの回復までを含む。

**なぜ良さの条件か** — 基準1〜10 はすべて「承認済みの仕事が `main` へ流れ着くまで」の質を測るもので、その先(本番デプロイ・監視・バックアップ)を測る基準が無かった。基準の地平が `main` で終わっていたため、CD・監視・バックアップの不在が `/retro` の点検(手順5-1 の基準突合)に一度も上がらなかった([2026-08-27-workflow-external-review.md](./research/2026-08-27-workflow-external-review.md) §1・§2)。基準11 を追加すれば、既存の突合機構がこの欠落を毎週観測し始める。

**測り方** — DORA Four Keys: デプロイ頻度(deployment frequency)・変更のリードタイム(lead time for changes)・変更失敗率(change failure rate)・失敗デプロイからの回復時間(time to restore service)([2026-08-27-lifecycle-frameworks.md](./research/2026-08-27-lifecycle-frameworks.md) §4)。

**現状評価** — ❌。CD が未着手(#56・#57)のため、デプロイ頻度そのものが計測不能。本番マイグレーションの適用手順もフェーズ表([01-lifecycle.md](./01-lifecycle.md))のどこにも定義されておらず、監視・バックアップも同様に未整備。マージ済み変更が溜まるほど、初回リリースのリスクが一括化する。

## 3. 基準間の緊張関係

良さは単一軸では最大化できない。このワークフローが既に払っているトレードオフ:

| 緊張 | 現在の置き所 |
| --- | --- |
| スループット(1) ⇔ 安全性(2) | ブランチ保護の追従必須をオフにし、semantic conflict は検知でカバー。連続マージ時だけ追従を必須にする折衷(`docs/review/README.md` §4) |
| フィードバックの速さ(5) ⇔ ターンの待ち時間 | 内側の層を厚くしすぎない — `stop-typecheck` は変更パッケージのみ、フル検証は `/verify` と CI に残す([04-principles.md](./04-principles.md) 原則7 適用限界) |
| 人間の注意の効率(4) ⇔ 白紙委任のリスク | 承認の前倒しは「1 Issue = 1 PR」粒度が守られている場合に限る([04-principles.md](./04-principles.md) 原則1 適用限界) |
| 回復性(3) ⇔ 安全性(2) | 自己回復の判定は機械的な2条件に固定し、緩めない — 積極的に回収するほど生きている作業を壊すリスクが上がる([02-labels.md](./02-labels.md) §5) |
| 品質・自己改善(2・7) ⇔ 収束性(9) | 失敗・見送り・改善案を捨てずすべて Issue にする設計は、追跡可能性と引き換えにバックログを増殖させる。従来は全部起票する側に倒しており、**それが基準9が △ だった直接原因**だった。2026-08-25 の判断(#663)で**起票の閾値を上げる側へ倒し直すことを決定**(レビュー suggestion はその場修正の比率を増やし、Issue 化を絞る)。具体的な閾値は #673 で決定済み(見送りは (a) 別リファクタリング相当の規模 / (b) ユーザーの意思決定が必要な設計判断のみ。Issue 化は (b) のみで (a) は PR 本文に記録)。この厳格化の効果は2026-08-24〜08-31の実測(#786)でバックログの純減として現れ、基準9の現状評価は○に改訂された(1期間分の実測のため継続観測は必要)。絞りすぎれば基準7のループが痩せる点は引き続き注意する |
