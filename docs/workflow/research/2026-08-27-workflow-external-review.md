## 2. `/retro` がこのレベルの欠落を出せない構造的理由

上記の欠落が週次の `/retro` から一度も上がらなかったのは偶然ではなく、スキル設計が構造的に封じている:

1. **入力が「動いているものの失敗データ」に限定** — 手順2の収集対象は Routine 起点 PR・`needs-decision`・撤退記録・CI 落ち・レビュー指摘の5種。動いていない工程(CD 等)は失敗データを生まないため、原理的に視界に入らない。**欠落は失敗として観測されない**
2. **「証拠ベース・保守的」の原則が明示的に禁止** — 手順5「運用データの裏付けがない抽象的な設計論は起票しない」。外部ベストプラクティスからの導出は、指示に正しく従った結果として出てこない
3. **改善の反映先リストが skills / docs に閉じている** — 手順4の反映先候補に「新しい GitHub Actions」「インフラ」が無く、気づいても提案が手順修正に矮小化される
4. **点検の物差し(`05-criteria.md`)自体の地平が `main` で終わっている** — 基準10個はすべて「マージまでのパイプラインの質」の基準で、「届いているか」を測る基準が無い。`/retro` は自分の自己記述への突合まではやるが、**自己記述の地平の外は誰も見ない**

対応の方向(採用決定済み): 基準11「到達性」の追加(→ 既存の突合が欠落1を毎週観測し始める)、手順5への「リポジトリ状態から機械的に確認できる構造的欠落は証拠として扱える」但し書き、体系駆動の `/workflow-review` を別スキルとして新設(`/retro` の失敗データ駆動と直交・相互補完)。

## 3. 設計工程の欠落(新機能追加の観点)

実装以降の重装備に対し、上流の設計工程だけが構造的に欠けている:

1. **フェーズ表に「設計」が存在しない** — 工程は「起票 → 着手承認 → 実装」と進む。かつての設計機構(`docs/superpowers/` の plans/specs、Phase 3〜5)は Phase 完了とともに凍結され、新機能が既存の 8 BC・集約定義に収まらないときに `docs/domain` を進化させる経路が無い(`/docs-drift` は事後の乖離検知であって設計の前進ではない)
2. **設計判断が「逃げ道」としてしか現れない** — `/backlog-ready` 基準4「設計判断なし(なら ready)」、無人モードの撤退、レビュー見送り基準 (b)。設計を正面から行う工程と成果物が未定義で、設計は実装中に AI が暗黙に行うか、撤退後に `/decide` で断片的に行われる
3. **複数 Issue にまたがる機能で設計の一貫性を担ぐものが無い** — `/issue-create` の分解の根拠となった設計はチャットの中に消える。分解後の Issue 群を消化する複数の fresh session は、書かれていない設計を各自再現することになる(原則8「セッション寿命をタスク境界に」の未言語化の適用限界)
4. **新規画面の見た目を人間が最初に見るのがマージ後になりうる** — 無人モードで新画面 Issue が流れると AI が画面設計を発明し、人間の初見はマージ済み PR のスクリーンショットになる(原則1「白紙委任」の適用限界が画面で顕在化)

対応の方向(採用決定済み): 軽量設計工程(設計ノート + 対話スキル)の新設、design-first 規約(新集約・UL 変更は docs 先行更新)+ 原則12「設計は成果物に残す」、新規画面 Issue へのレイアウト仕様要求(ready 基準の追加)。
