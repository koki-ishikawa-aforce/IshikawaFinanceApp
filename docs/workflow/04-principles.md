# AI 駆動開発の原則

割まるの運用から抽出した、**AI に開発を任せるワークフローを設計するときの原則**。各原則は「原則 / 根拠 / このリポジトリでの実装 / 適用限界」で書く。原則が目指す先 — 何をもって良いワークフローとするか — は [05-criteria.md](./05-criteria.md) に定める(原則は手段、基準は目的)。

根拠には、可能な限り**実際に起きた失敗**を挙げる。原則を「良さそうな方針」として書くと、状況が変わったときに捨ててよいのか判断できなくなるため。

このファイルは `/retro`(週次の失敗データ振り返り)と `/decide`(判断待ちの消化)の**出力の受け皿**でもある。運用で得た知見は手順(`SKILL.md`)だけでなく、ここにも反映する。

## 1. 人間の承認は1点に前倒しする

**原則** — 人間の承認ゲートは「着手前」の1点だけに置き、それ以降(マージを含む)は機械判定に委ねる。

**根拠** — 承認点が増えるほど、承認そのものが自動化の律速になる。特にマージ承認は「変更が正しいか」を人間が再確認する形になりがちだが、それは CI とレビューが既に見た内容の追認でしかない。一方、**着手承認は代替できない** — 「そもそもこれをやるべきか」は要件の問題であり、機械が判定できる形に落ちない。

**このリポジトリでの実装** — `ready-to-implement` の付与が唯一の人間ゲート。マージ可否は7条件のマージゲートで機械判定し、無人モードが自分でマージする。個別に止めたいときだけ `needs-decision` を PR に付ける。

**適用限界** — 承認を前倒しできるのは「1 Issue = 1 PR」の粒度が守られている場合に限る。着手承認の時点で成果物の姿が想像できないほど大きい Issue では、承認が実質的な白紙委任になる。`/backlog-ready` の判定基準に「1 PR 粒度」が入っているのはこのため。
なお本リポジトリは collaborator がオーナー1人で、GitHub の仕様上**自分の PR を自分で承認できない**ため、そもそもレビュー承認を必須にできないという固有事情もある(`docs/review/README.md` §4)。複数人のチームでは、この原則は「承認を減らす」ではなく「承認の位置を前に動かす」として読む。

## 2. 判断待ちを1つのキューに集約する

**原則** — AI が人間の判断を必要としたときの出口を、**種類を問わず1つに統一する**。

**根拠** — 判断依頼がチャットの最終報告・PR 本文・コメントに散ると、人間は「自分が答えるべきことの全量」を把握できない。把握できない判断待ちは滞留し、滞留した Issue の分だけ自動化が止まる。逆に1箇所に集約されていれば、**判断だけをまとめて処理する時間**を取れる。

**このリポジトリでの実装** — 撤退・見送り追認・マージゲート落ち・`main` の CI 失敗をすべて `needs-decision` ラベルに集約する。`is:issue is:open label:needs-decision` が作業キューそのもので、ラベル付与が通知トリガーを兼ね、`/decide` が対話で一括消化する。タイトル先頭の種別目印(`[判断待ち]` / `[乖離報告]` / `[改善案]`)でメールの件名から種別が分かる。

**適用限界** — 集約先のキューが消化されなければ、判断待ちは「見えている滞留」に変わるだけで解消はしない。消化の手段(`/decide`)と、キューが伸びていることに気づく仕組み(通知)がセットで要る。

## 3. 判定の定義は1箇所にしか持たない

**原則** — 同じ判定を2つの場所に実装しない。片方は必ず更新から漏れ、食い違ったときにどちらが正か決められなくなる。

**根拠** — レビュー観点の重複禁止(`docs/review/README.md` §1-3)と同じ問題が、自動化の判定ロジックでも起きる。マージ可否を `/issue-work` と `/pr-steward` の両方が持てば、条件を1つ追加したときに片方だけが厳しくなる。

**このリポジトリでの実装** — マージゲートの定義は `.claude/skills/issue-work/SKILL.md` の1箇所のみ。`/pr-steward` は PR を green にするところまでで**マージしない**。「Routine 起点の PR か」の判別基準もマージゲート条件1が正で、`/pr-steward` と `/retro` はそれを参照する。ドキュメントにも同じ規律を適用し、本ドキュメント群は条件を複製せず参照に留めている。

**適用限界** — 冗長化とは区別する。ブランチ保護の required check はマージゲートと同じ `verify` を見ているが、これは**スキル側の判定が誤って緩んだ場合の最後のガード**であり、条件の定義を二重に持っているわけではない。同様に `.env` の封鎖は `permissions.deny` と `guard-bash` の二重だが、これは別経路の封鎖であって判定の重複ではない。

## 4. 機械が判定できる観点は CI に寄せ、レビューに残さない

**原則** — 閾値・パターン・型で自動判定できるものは CI のステップにする。レビュー(人間または AI)には、**設計判断が要る観点だけ**を残す。

**根拠** — 3つある。(a) 機械判定は見落とさない、(b) **レビューの観点が増えるほど1観点あたりの精度が落ちる**、(c) 無人運用の1サイクルが重くなる。

**このリポジトリでの実装** — フォーマット・lint・型・テストの成否・依存脆弱性・バンドルサイズは CI。`*.module.css` のトークン直値は stylelint が機械的に落とすため、`ui-reviewer` は「stylelint が拾えない境界例(インライン style・`calc()` 内の直値)」だけを見る。切り分けの原則と観点の追加手順は `docs/review/README.md` §1・§5 が正。

**適用限界** — CI に寄せられるのは「判定が安定して速い」場合まで。実行時間の長い検証を常時実行にすると、実行枠と待ち時間を消費して開発速度そのものを落とす。CI 側も変更パスでステップを出し分けている(`code` / `web` / 常時)。

## 5. レビューは責務で分割し、重複を明示的に禁じる

**原則** — 1つの巨大なレビューではなく、**観点ごとに分割した複数のレビュー**を変更パスに応じて起動する。境界が近いレビュー同士は、どちらが何を見るかを表で切り分ける。

**根拠** — 原則4の (b) の裏返し。「すべてを見る」レビューは実質的に何も深く見ない。一方で分割すると境界が重なり、同じ指摘が2回出る(レビュー時間の無駄であり、片方だけが更新されて食い違う原因にもなる)。

**このリポジトリでの実装** — 7つのレビュースキルと対応するサブエージェント。境界が近い3組は明示的に分担を定義している。

| 組 | 切り分け |
| --- | --- |
| `/ui-review` と `/ux-review` | 見た目の規約適合 と 使いやすさ。コントラスト比・ロール識別・フォーカス可視化の3点は `ux-reviewer` の「責務分担」表で分担 |
| `/data-review` と `/reliability-review` | 再実行の結果が**データに二重適用として残らないか** と **失敗が握りつぶされていないか** |
| `/security-review` と `/reliability-review` | ログの**シークレット / PII 流出** と **障害を診断できる識別子が残るか** |

**適用限界** — 分割数には上限がある。全レビューを常時起動にすると無人運用の1サイクルが破綻するため、起動条件は必ず変更パスで絞る(`docs/review/README.md` §5-3 が「無条件に常時起動にしない」と明記している)。

## 6. 規約は指示ではなく実行時ガードで守らせる

**原則** — 破壊的操作・取り返しのつかない操作の禁止は、プロンプトやドキュメントでの指示ではなく、**実行時にブロックする仕組み**で担保する。

**根拠** — LLM に対する指示は確率的にしか守られない。守られる確率が 99% でも、定期 fire する自動化では失敗が定期的に発生する。`main` への直接 push や `rm -rf` は1回でも通れば取り返しがつかない。

**このリポジトリでの実装** — `guard-bash.mjs`(PreToolUse)が `main` への直接 push・force push・`drizzle-kit push`・`.env` の読み出し・リポジトリルートへの `rm -rf` を exit 2 でブロックする。コマンドは実行されず、理由が Claude にフィードバックされる。`.env` は `permissions.deny` でツール側も塞ぐ。

**適用限界** — ガードはパターンマッチであり、意図の理解ではない。回避しようと思えば書き換えられるし、パターンから漏れた表現は通る。**守らせたい規約が多いほど、ガードで書けるのは一部**になる。ガードに向くのは「形が固定で、1回でも通ると致命的」な操作に限る。

## 7. 失敗の検知は早い層ほど安い

**原則** — 同じ失敗を捕まえるなら、**より内側(実行が速く、コストが低い)の層**で捕まえる。内側の層は外側の層の部分集合になるよう設計する。

**根拠** — 整形漏れを CI で捕まえると、修正 → push → CI 再実行で数分〜十数分を失う。同じものを編集直後の hook で捕まえればコストはゼロに近い。無人運用ではこの往復が fire の寿命を削り、「CI を待ち切れずに PR が open のまま残る」という別の問題を生む。

**このリポジトリでの実装** — hooks(秒)→ `/verify`(分)→ レビュー(分)→ CI(〜8分)→ `main` 失敗通知(マージ後 数分)→ `/retro`(週次)の6層([01-lifecycle.md](./01-lifecycle.md) §4)。`format-after-edit` により `format:check` 起因の CI 失敗は原理的に起きない。

**適用限界** — 内側の層を厚くしすぎると、1ターンごとの待ち時間が増えて対話が成立しなくなる。`stop-typecheck` が**変更があったパッケージだけ**を typecheck し、フル検証を `/verify` と CI に残しているのはこの線引き。
また、内側の層は外側と**同じ検証を走らせているとは限らない**。`pnpm test` は adapters-postgres の統合テストを含まないため、ローカル全 green でも CI が赤くなりうる。この非対称性は「ローカルで再現できない失敗」として必ず残るので、統合テストの実行判定を `packages/domain` の振る舞い変更にまで広げるなど、**ずれを狭める方向で運用する**(実例: `applyPrivacyFilter` の変更が `transactionListQuery.test.ts` を壊した)。

## 8. セッション寿命をタスク境界にする

**原則** — 1つの自動実行セッションで扱う仕事を「1タスク = 1 PR」に固定し、量はセッションの**回数**で稼ぐ。

**根拠** — セッションが長くなるほどコンテキストが劣化し、後半の判断精度が落ちる。1セッションで5件処理するより、1件ずつ5回起動するほうが各判断の質は高い。fresh session は前の失敗を引きずらないという副次効果もある。

**このリポジトリでの実装** — 1 fire = 最大1 PR = 1 fresh session。2時間おきの fire なので1日最大 12 件。撤退・スキップが起きた場合だけ候補ループで次の Issue へ進む(最大5候補)が、**実装コストを既に払った撤退**(`/verify` 行き詰まり・push 前の重複検知)では候補ループに戻らず fire を終える。

**適用限界** — セッション寿命はタスクの完了より先に尽きうる。CI を待ち切れずに fire が終わるケースがあるため、「次の fire が前の fire の後始末を拾う」設計(回収マージ)が必ずセットで要る(原則9)。

## 9. 自己回復を前提に設計する

**原則** — 無人運用は「失敗しない」ではなく「**詰まったら次の起動で自力で戻る**」で設計する。各起動は、前の起動が残した中途半端な状態を回収してから本来の仕事に入る。

**根拠** — 自動実行は必ず途中で死ぬ(セッション寿命・ネットワーク・API エラー)。死に方を予測して塞ぐより、死んだ痕跡を機械的に検出して片付けるほうが安上がりで、**未知の死に方にも効く**。

2026-07-23 には、異常終了で残った `status:in-progress`(ゴミロック)が `ready-to-implement` な Issue すべてに溜まり、Routine が毎 fire「候補なし」でスキップし続けてバックログが完全に停止した。ロックを取る仕組みだけを作り、**外す仕組みを作らなかった**ことが原因。

**このリポジトリでの実装** — 各 fire の preflight で、(a) `main` の健全性チェック、(b) ゴミロックの回収、(c) コンフリクトの先解消、(d) 回収マージ、を新規着手の前に行う。preflight を WIP 上限チェックより前に置いているため、マージで枠が空けばその fire でそのまま新規着手へ進める。

**適用限界** — 自己回復の判定は**機械的でなければならない**。2026-07-24 の二重着手事故は、ゴミロック回収の2条件(open PR が無い / 2時間以上経過)を自然言語の判断で緩めたことが直接原因だった。「たぶん死んでいる」で回収すると、生きている作業を壊す。回復の条件はコマンド出力で確定できる形に落とし、緩めないことを手順に明記する。

## 10. 失敗データを捨てず、仕様に還元する

**原則** — 自動実行が生む失敗データ(撤退・リトライ・レビュー指摘・往復回数)を捨てない。**繰り返し起きているパターン**を定期的に抽出し、ワークフローそのものの改善に変換する。

**根拠** — 1回の撤退は個別対応で済むが、同じ理由の撤退が毎週起きているなら、それは Issue の書き方か手順の欠陥であって、個別対応し続けるのは損失。個々の fire は自分の失敗しか見えないので、**横断して見る主体が別に要る**。

**このリポジトリでの実装** — 週次の `/retro` が直近期間の撤退・CI リトライ・レビュー指摘を収集し、繰り返すパターンから `skills` / `CLAUDE.md` / Issue テンプレート / 本ドキュメント群(`docs/workflow`)への改善案を `[改善案]` + `needs-decision` の Issue として起票する。個別パターンに加えて、本ファイルの原則・未解決課題との突合と改善ループの滞留観測(ワークフロー全体の点検。`.claude/skills/retro/SKILL.md` 手順5)も行う。読み取り専用で、採否の判断は `/decide` が行う。

**適用限界** — 抽出は起票までで、**仕様に反映されるかは人間の判断待ちに依存する**。改善案が `needs-decision` に溜まったまま消化されなければ、このループは閉じない(§未解決課題)。
また「捨てない」は「すべて Issue にする」と同義ではない。2026-08-25 の実測(#663: 1週間で新規 104 件 / クローズ 54 件、`ready-to-implement` 滞留 173 件)で、起票が消化を継続的に上回るとキュー自体が機能しなくなることが裏付けられ、**起票の閾値を上げる(レビュー suggestion はその場修正を既定とし、Issue 化を絞る)方向が決定された**。閾値の具体的な基準は #673 で決定済み: 見送ってよいのは (a) 独立した PR が必要な別リファクタリング相当の規模、(b) ユーザーの意思決定が必要な設計判断のみで、**Issue 化するのは (b) だけ**((a) は PR 本文のレビュー結果節に記録する)。基準の定義は各レビュー skill の SKILL.md を正とする。

## 11. 手順はリポジトリに置き、起動側は薄く保つ

**原則** — 手順・判定条件はバージョン管理され PR で更新できる場所に置く。起動側(スケジューラのプロンプト、CI の設定画面、外部サービスの設定)には**「どれを起動するか」だけ**を書く。

**根拠** — 更新経路が違う場所に同じ情報があると、更新のたびに片方が古くなる。特に画面からしか更新できない設定に手順を書くと、リポジトリ側を直しても実行される手順は古いままになる。

**このリポジトリでの実装** — Routine のプロンプトは「どのスキルを・どのモードで・何語で報告するか」のみ。手順の正はすべて `.claude/skills/*/SKILL.md` にあり、**PR をマージした次の fire から新しい手順で動く**。同じ理由で、`CLAUDE.md` は要約と索引に留め、一次資料を複製しない。

**適用限界** — リポジトリのファイルに書けない設定は残る(ブランチ保護、Routine の cron、GitHub の通知設定)。これらは**ドキュメントに値を記録する**ことで代替している(`docs/review/README.md` §4「`main` のブランチ保護」、`docs/automation/*` の「Routine のセットアップ」)。記録しても実体と同期する保証はないため、この部分は原則3(定義を1箇所に)を守りきれていない箇所として残る。

## 12. 設計は成果物に残し、セッションを跨いで参照可能にする

**原則** — 実装より前に確定する設計判断(新しい集約・境界づけられたコンテキストの導入、複数 Issue にまたがる機能の分解方針、新規画面のレイアウト)は、チャットの中で終わらせず、リポジトリにコミットされる成果物として固定する。

**根拠** — fresh session(原則8)は前のセッションの対話を引き継がない。設計判断がチャットの中にしか無いと、分解後の Issue 群を消化する複数の fresh session がそれぞれ「書かれていない設計」を再発見・再現することになり、セッション間で解釈がずれる。2026-08-27 の外部レビューで、フェーズ表に設計工程が存在せず(起票 → 着手承認 → 実装)、設計判断が `/backlog-ready` の見送り・無人モードの撤退・レビュー見送り基準 (b) という「逃げ道」としてしか現れていないことが指摘された(`docs/workflow/research/2026-08-27-workflow-external-review.md` §3)。

**このリポジトリでの実装** — 2つの経路で設計を成果物化する。(1) 複数 Issue にまたがる機能・新規画面のレイアウト方針は `/feature-design` が対話でヒアリングし、`docs/design-notes/` に設計ノートとして残す(`/issue-create` の分解が参照する)。(2) 新しい集約・ユビキタス言語の用語を導入する変更は、design-first 規約(`.claude/skills/issue-work/SKILL.md` 手順3)により `docs/domain/09-aggregates.md`・該当 UL 資料を実装と同じ PR で先行(または同時)更新し、`/ddd-review` が実装より古い docs を根拠にレビューする期間を作らない。原則8(セッション寿命をタスク境界にする)が前提とする「1タスク = 1 PR」を、設計工程でも同じ形で担保する。新規画面を含む Issue にレイアウト仕様(ワイヤーフレーム参照または本文内の記述)を `/backlog-ready` の ready 基準として要求する対応は、本原則が挙げる欠落の一つとして採用決定済みだが、本 PR の時点では未導入(#738)。

**適用限界** — 成果物化のコストは軽量設計工程(1〜2ページの設計ノート)に留めている。すべての設計判断を厳密な仕様書にすると工程が重くなり、原則4(機械判定できない観点をレビューに残す)とのバランスを崩す。設計ノート・UL 資料が古くなる(実装で判断が変わったのに更新されない)リスクは残る。`/docs-drift` の4突合(公開API・`09-aggregates.md`・UL 資料・実行基盤一覧)は `docs/design-notes/` を対象に含んでおらず、design-first 規約で先行更新する `09-aggregates.md`・UL 資料の陳腐化だけを事後検知できる。設計ノートの陳腐化を機械的に検知する仕組みは現状無い。

| 課題 | 現状 | 検討の方向 |

| **semantic conflict の予防** | 別ファイルを触る変更が意味の上で衝突するケース(実例: #494 と #503)を、マージ前に検出していない。ブランチ保護の "Require branches to be up to date" をオンにすれば防げるが、マージのたびに全 PR が追従 → CI 再実行となり待ちが積み上がる。待ちを吸収するマージキューは organization 所有リポジトリでしか使えない | **予防より検知でカバー**する判断。`notify-main-failure` が数分後に気づかせ、無人モードは `main` が赤い間バックログを止める。同一 fire で2件目以降をマージするときだけ追従を必須にする折衷を採っている。頻発するようなら設定をオンに切り替える |
