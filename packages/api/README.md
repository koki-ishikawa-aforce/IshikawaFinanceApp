# @warimaru/api

Hono の API サーバと、定時起動するバッチのエントリポイント。
依存の合成は `src/composition-root.ts` に一本化していて、API もバッチも同じ `createDeps` を通る。

## 起動口

| 起動口             | 実体                     | 起動される側                                      |
| ------------------ | ------------------------ | ------------------------------------------------- |
| API サーバ         | `src/index.ts`           | Hono（`src/app.ts`）。ローカルは `pnpm dev`       |
| バッチ（Lambda）   | `src/batch/handlers.ts`  | EventBridge のスケジュール（01-overview.md §6.5） |
| バッチ（手動起動） | `src/batch/run-local.ts` | 上と同じハンドラー。`pnpm batch:*`                |

## バッチ

`src/batch/handlers.ts` が export するハンドラーを、EventBridge のスケジュールから起動する。
スケジュールルールの定義・IaC・デプロイ設定はこのパッケージの外（#35 / #56 / #57）。

| export                            | 周期 | 中身                                                         | 受入シナリオ |
| --------------------------------- | ---- | ------------------------------------------------------------ | ------------ |
| `dailyMailImportHandler`          | 日次 | SMBC 通知メールの取込（取得 → 重複除外 → パース → 候補生成） | AT-902       |
| `csvImportReminderHandler`        | 日次 | CSV 取込リマインダーの配信（毎月 5 日から取込完了まで）      | AT-903       |
| `monthlyExpenseCycleStartHandler` | 月次 | 夫婦それぞれの当月の経費サイクル開始                         | AT-905       |

日次を 2 つに分けているのは、起動時刻を別々に決められるようにするため。メール取込は日付が
変わってすぐ、リマインダーは人が読む時間帯に届いてほしい。

Lambda のハンドラー指定は `dist/batch/handlers.<export 名>`（例: `dist/batch/handlers.dailyMailImportHandler`）。

### 入力（EventBridge のイベント）

読むのは 2 つだけで、どちらも省略できる。

- `time`: 発火時刻。「いつのぶんの処理か」の基準にする（省略時は実行時刻）
- `detail`: 対象の上書き。ターゲット入力に JSON を置くと、コードを変えずに運用中に変えられる
  - `targetYearMonth`（`YYYY-MM`）: 月次サイクル開始・リマインダーの対象年月
  - `scanDays`（正の整数）: 日次メール取込がさかのぼる日数（既定 5 日。論点22 / OQ-31）

知らないキー・型違いは黙って既定値に落とさず失敗させる（意図と違う対象を処理した結果が
「成功」として残らないようにするため）。

### 失敗したとき

ジョブの中の失敗（片方のユーザーの取込失敗など）は、他方の処理を最後まで進めてから
まとめて例外にする。Lambda はこれを失敗として記録するので、EventBridge のリトライ・
監視の対象になる。結末は 1 件ずつその場でログに出す（上限時間で打ち切られた回でも、
どこまで済んだかが残るように）。ログに出るのは役割・件数・エラー種別・取込バッチ ID だけで、
ユーザーID・メール本文・加盟店名は含めない。

例外は、CSV 取込リマインダーの送信失敗（単発の失敗はスキップして翌日送り直す。論点23）。

### 環境変数

API サーバと同じものを使う（読み出しは `composition-root.ts` の `compositionEnvFromEnvironment`
に一本化）。定時起動では **`DATABASE_URL` が必須**で、未設定なら合成の前に失敗する。
`createDeps` は未設定だとインメモリのモックへ落ちる作りだが、定時起動がそれで走ると
「対象者ゼロ」で 3 ジョブとも成功して終わり、設定漏れに誰も気づけないため禁じている
（モックで動かせるのは手動起動だけ）。

そのほか、バッチ固有のものが 1 つある。

| 変数               | 既定            | 用途                 |
| ------------------ | --------------- | -------------------- |
| `BATCH_TIMEOUT_MS` | 600000（10 分） | 1 回の実行の上限時間 |

### 上限時間

`BATCH_TIMEOUT_MS` で 1 回の実行に上限を掛ける。Lambda の残り時間が分かる場合はその手前に
寄せる。上限に達したら、どのジョブが何ミリ秒で止まったかを記録してから失敗させる
（Lambda 側のタイムアウトで殺されるとログが残らない）。

打ち切りは待つのをやめるだけで、進行中の処理そのものは止められない。Lambda の実行環境は
関数の終了とともに凍結されるが、次の起動で解凍されると残りの処理が続きから動く。
また、月次サイクル開始が「保存済み・開始イベント未発行」の位置で打ち切られた場合、
次回は「開始済み」と判定されて開始イベントは出し直されない（#484 の既知の制約）。

### バッチの手動起動

EventBridge 無しで、Lambda と同じ経路を手元から動かせる。環境変数は API サーバと同じもので、
手動起動に限り `DATABASE_URL` 未設定でもモック合成で動く（データを用意せずに疎通だけ確かめる用）。

```bash
# 日次メール取込（さかのぼり日数は既定の 5 日）
pnpm --filter @warimaru/api batch:daily

# 日次メール取込（7 日ぶんさかのぼる）
pnpm --filter @warimaru/api batch:daily --scan-days=7

# 月次サイクル開始（対象年月を指定。省略時は起動時刻から JST 暦の当月）
pnpm --filter @warimaru/api batch:monthly --target-year-month=2026-08

# CSV 取込リマインダー（基準時刻を指定して「5 日以降」の判定を再現する）
pnpm --filter @warimaru/api batch:csv-reminder --at=2026-08-05T00:00:00Z
```

終了コードは 0（成功）/ 1（ジョブの失敗）/ 2（呼び出し方の誤り。未知のジョブ名・引数の書式違い）。
成功時は結末の要約を JSON で標準出力に書く。
