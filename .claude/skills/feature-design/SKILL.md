# 軽量設計工程(設計ノート)

`/issue-create` の前段に置く、対話専用の設計工程。これまで工程は「起票 → 着手承認 → 実装」と進み、要件と実装の間に設計工程が無かった。複数 Issue にまたがる機能では、分解の根拠になった設計判断がチャットの中に消え、分解後の Issue 群を消化する複数の fresh session が書かれていない設計を各自再現することになっていた(2026-08-27 外部レビュー、`docs/workflow/research/2026-08-27-workflow-external-review.md` §3)。本スキルはその設計判断を1〜2ページの成果物として固定し、`docs/design-notes/` にコミットして、分解後の各 Issue から参照できるようにする。

**対話専用。無人モードは持たない。** 設計判断そのものを人間との対話で確定させることが目的のため、`/issue-work` のように確認の代わりに撤退する無人経路は定義しない。

## いつ使うか

`/backlog-ready` 基準4(設計判断が残っていない)で見送られる規模の機能、または次のいずれかに該当する要件:

- 複数の境界づけられたコンテキスト・集約にまたがり、分解の根拠(どの Issue が何を担うか、依存順)を残す必要がある
- 新しい画面・フローを追加し、レイアウト方針を実装前に固めたい(`docs/domain/wireframes/` の参照可否を含む)

1 Issue で完結する小さな変更には使わない。そのまま `/issue-create` へ進む。

## 手順

### 1. 要件のヒアリング

AskUserQuestion で以下を確認する:

- 目的(誰の何を解決するか)
- 触れる境界づけられたコンテキスト・集約の見当(`docs/domain/07-bounded-contexts.md`・`docs/domain/09-aggregates.md` を読んで候補を提示する)
- 新規画面を含むか。含む場合はレイアウト方針(既存ワイヤーフレームの流用可否・新規に必要か。`docs/domain/wireframes/README.md` を参照)

対話の中で決定事項(採用した設計・却下した代替案とその理由)を都度メモしておく。決定に至った理由が設計ノートの本体になる。

### 2. 設計ノートの作成

`docs/design-notes/YYYY-MM-DD-<slug>.md` に、以下の構成で1〜2ページ程度にまとめる。詳細な実装コードは書かない(実装は分解後の Issue 側の責務)。

```markdown
# <機能名>の設計ノート

> 作成: YYYY-MM-DD(対話セッション)
> 関連 Issue: 分解後にここへ追記する

## 決定事項

<採用した設計と、却下した代替案があればその理由>

## 触れる境界づけられたコンテキスト・集約

<BC 名と集約名の一覧。新規集約であれば概要>

## レイアウト方針(新規画面がある場合)

<画面遷移・主要な状態(読み込み中・エラー・空)の方針。詳細なワイヤーフレームは docs/domain/wireframes/ を別途参照>

## Issue 分解と依存順

<分解案。各 Issue の粒度と着手順(依存がある場合)>
```

**命名規約**: `YYYY-MM-DD-<slug>`。`slug` は機能を表す英数字ハイフン区切り(`docs/workflow/research/` の日付 + slug 命名を踏襲)。置き場は `docs/design-notes/`。

新規画面を含まない設計では「レイアウト方針」節は省略してよい。

### 3. PR でコミット

```bash
git fetch origin main && git switch -c docs/design-note-<slug> origin/main
```

設計ノートを追加し、`pnpm format:check` を通してからコミット・push・PR 作成する(`main` への直接 push は禁止。他の docs-only PR と同じ扱い)。CI が green になったら AskUserQuestion で「今マージする / レビューに残す」を確認する。

### 4. `/issue-create` への接続

設計ノートの合意が取れたら、同一セッション内で `/issue-create` を起動して要件を分解する(`.claude/skills/decide/SKILL.md` 手順3e の「続ける」と同じ形)。

- 分解後の各 Issue の「参考資料」に設計ノートのパス(`docs/design-notes/YYYY-MM-DD-<slug>.md`)を追記する
- 設計ノート冒頭の「関連 Issue」にも起票した Issue 番号を追記し、相互参照にする(設計ノートが `main` にマージ済みなら追記コミットを別途 push する)

分解を後回しにする場合は、設計ノートの PR 本文に「`/issue-create` での分解は別セッションで行う」と記録する。

## 完了の定義

設計ノートが `main` にマージされ、分解後の Issue から参照できる状態になった時点(分解まで同一セッションで行う場合は Issue 群の起票まで)。
