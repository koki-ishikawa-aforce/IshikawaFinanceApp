# 信頼性・可観測性レビュー

変更差分を「外部依存やイベント処理が失敗したときに何が起きるか」「その失敗に気づけるか」に照らしてレビューする。実際のレビューは `reliability-reviewer` サブエージェントが行う。

割まるの失敗は例外ではなく**金額の静かなずれ**として現れる。未払金の計上漏れ・按分の再計算漏れ・月次レポートの未確定は、画面上は正常に見えたまま数字だけが合わなくなる。

## 起動条件

`docs/review/README.md` §3 のトリガー表に従い、差分が以下を含む場合に起動する:

- `packages/domain/src/*/events/**`(ドメインイベントの追加・変更)
- `packages/api/src/event-handlers/**`
- `packages/api/src/notification/**`
- 外部 API 呼び出しの追加・変更(`packages/api/src/gmail-oauth/**`、`packages/api/src/pdf-conversion/**`、`packages/api/src/aws/**`、その他 `fetch` / SDK 呼び出し)

イベント型の**定義だけ**を追加し、購読も発行もまだ無い差分では省略してよい(失敗経路が存在しないため)。省略した場合は PR 本文にその旨を書く。

## 責務分担

- **署名検証・トークン検証・認可の位置**は `/security-review` の担当。本レビューは扱わない
- **ログの PII** は、差分が `/security-review` の起動パス(`routes/**` / `middleware/**` / `gmail-oauth/**` / `aws/**`)を含む場合はそちらの担当。本レビューが見るのは `/security-review` が起動しないパス(イベントハンドラー・`notification/**`・外部ゲートウェイ)に限る
- **冪等性**は `/data-review` と面を分ける。あちら = 再実行の結果が**データに二重適用として残らないか**、本レビュー = **再実行で回復できる形になっているか**(ガードが壊れやすくないか・スキップが判別できるか・回復手段が実在するか)
- **冪等性テストの十分さ**はテスト品質レビュー(#329)の担当。本レビューは実装がそうなっているかを見る

## 手順

1. `git diff main...HEAD --name-only` で変更範囲を確認し、上記の起動条件に該当するか判定する
2. 差分に含まれるイベントハンドラーが `safeSubscribe` 経由か素の `eventBus.subscribe` かを `packages/api/src/event-handlers/index.ts` で確認する(失敗が利用者に届くかがここで決まる)
3. `reliability-reviewer` サブエージェントを起動し、以下を渡す:
   - 変更ファイル一覧(またはレビュー対象の diff 範囲)
   - 関連する Issue 番号と受け入れ条件(あれば)
   - 追加・変更したイベント型と、その購読者・発行元が分かっていれば添える
4. レビュー結果を **must-fix** / **suggestion** に分けてユーザーに提示する
5. must-fix は必ず修正する。**suggestion も原則その場で修正する(デフォルトは対応)**。修正後は `/verify` を再実行して green を確認する
6. 例外として、以下のいずれかに該当する suggestion のみ見送ってよい:
   - 修正範囲が今回の diff を大きく超える(別リファクタリングが必要)
   - 設計判断の変更を伴い、ユーザーの意思決定が必要(監視基盤の導入・リトライ基盤の新設など)
7. 見送る suggestion は黙って放置せず、理由を添えてユーザーに提示したうえで GitHub Issue 化して追跡する(`needs-decision` を付けて `/decide` に接続する)

## 特に落とせない指摘

次の4つは、見落とすと家計の数字が黙ってずれる。指摘が出た場合は suggestion であっても見送らない:

- **冪等性ガードを例外メッセージの文字列一致で判定している**(ドメイン側の文言変更で黙って壊れ、`safeSubscribe` 配下なら誰も気づかない)
- **金額・残高・月次レポートに関わる処理を、記録も残さずスキップまたは握りつぶしている**
- **外部呼び出しにタイムアウトが無い**(イベント配信が同期なのでリクエストごと吊る)
- **「再実行で回復する」と書いているが、その再実行を起こす経路が実在しない**

## この実装の前提(誤検出を防ぐために必ず確認する)

- `safeSubscribe` を**使っていない**ハンドラー(`master-data-remap.ts` / `master-data-deletion-coordinator.ts`)は、例外をルートへ伝播させて `remap_failed` に倒すため**意図的に外している**。ここに `safeSubscribe` を足すよう指摘してはならない
- リトライ基盤は存在しない(論点23)。LINE 送信の単発失敗は `retry_abandoned` で終端化する
- 能動的に人へ届く通知はフェイルセーフメール1経路だけで、**LINE 連続送信失敗がしきい値に達したときだけ**発火する(OQ-14)
- 構造化ログ・ログ収集・監視・アラート・相関 ID の基盤は無い。「監視で拾える」を前提にした判定はしない
