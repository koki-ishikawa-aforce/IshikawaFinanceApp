# 要件の Issue 化

要件を「/issue-work でそのまま実装に入れる品質」の GitHub Issue に落とし込む。

## 手順

### 1. 要件の確認

以下が不明なら、実装の前提として AskUserQuestion で確認する:

- 目的(誰の何を解決するか)
- 受け入れ条件(何ができたら完了か)
- 対象の境界づけられたコンテキスト(見当がつかなければ `docs/domain/07-bounded-contexts.md` を読んで候補を提示)

### 2. 分解の提案

**1 Issue = 1 PR で完結する粒度**を基準にする。大きい要件は分解案(Issue のリスト)を提示してユーザーの合意を得てから作成する。依存関係がある場合は着手順も示す。

### 3. Issue 作成

`.github/ISSUE_TEMPLATE/task.md` の構造に沿って `gh issue create --title "..." --body "..."` で作成する。

- **受け入れ条件は検証可能なチェックボックス**で書く(「〜が pnpm test で通る」「〜画面で〜が表示される」など)。これが後で /issue-work の検証ループの終了条件になる
- 対象コンテキストを明記する
- 着手をブロックする先行 Issue は「依存(ブロッカー)」節に `#N` で列挙する(無ければ「なし」)。単なる参照は「参考資料」に書く(「参考資料」内の Issue 参照は Routine の着手ブロック条件にならない)
- 関連するドメイン資料(`docs/domain/09-aggregates.md` の該当集約など)を参考資料に挙げる
- **新しい画面・フローを追加する Issue**では、レイアウト仕様(`docs/domain/wireframes/` の該当ワイヤーフレーム参照、または本文内のレイアウト記述)を本文に含める。既存画面の修正・文言変更には不要

### 4. ready 判定(無人消化への接続)

作成した各 Issue に `/backlog-ready` の判定基準(backlog-ready スキル参照: リポジトリ内で完結・受け入れ条件が検証可能・依存解決済み・設計判断なし・1 PR 粒度・新規画面/フローはレイアウト仕様あり)を適用する:

- 基準を満たすものは `ready-to-implement` を付与する(無人消化 Routine の対象になる旨を報告に添える。外せばいつでも取り消せる)
- 依存する Issue が open でも他の基準を満たすなら付与してよい(Routine の依存チェックが先行 Issue のクローズまで着手を自動で遅延する)。先行 Issue の実装結果次第で受け入れ条件が変わりうる場合のみ付与せず、「#X のマージ後に `/backlog-ready` で再判定」と報告する
- ユーザーが「無人消化に流さない」と明示した Issue には付与しない

作成後、Issue の URL 一覧と ready 判定の結果をユーザーに報告する。
