# 使用性(UX)レビュー

変更差分を `docs/design/usability.md` の規範に照らしてレビューする。実際のレビューは `ux-reviewer` サブエージェントが行う。

見るのは「迷わないか / 間違えないか / 手数が少ないか / 支援技術で使えるか」。見た目が正しいか(トークン・テーマ・アイコン)は `/ui-review` の担当で、**本レビューでは扱わない**。

## 起動条件

`docs/review/README.md` §3 のトリガー表に従い、差分が以下を含む場合に起動する:

- `packages/web/**` のうち**画面・フローの追加変更**を含む差分。具体的には:
  - `packages/web/src/app/**` のページ・レイアウト(`page.tsx` / `layout.tsx`)の追加変更
  - `packages/web/src/components/**` のうち、利用者が見る表示・操作を持つ部品の追加変更
  - `packages/web/src/hooks/**` のうち、画面の状態(ローディング・エラー)の扱いが変わるもの
  - `packages/web/src/components/ui/common.module.css` の `.loading` / `.empty` / `.error` / `.button` 系の変更(採用パターンそのものの変更)

`packages/web` の変更であっても、次のみの差分では起動を省略してよい(省略した場合は PR 本文にその旨を書く):

- 色・余白・書体だけの変更(利用者の操作と表示内容が変わらないもの)
- テストコード・VRT スナップショットのみの変更
- 設定ファイル・ビルド設定のみの変更

`/ui-review` は `packages/web/**` の変更で常に起動する。本レビューは上記に該当する場合に**加えて**起動する(両方回る差分がある)。

## 責務分担

- **`/ui-review`(デザインシステム適合)とは観点が重ならない**。トークン規律・絵文字・テーマ両対応・`aria-label` / `aria-hidden` / 色依存・`DESIGN.md` 整合の5観点は `/ui-review` の担当。`ux-reviewer` 側にも「これらを指摘しない」ことと境界の分け方(コントラスト比・ロール識別・フォーカス可視化)を明記済み
- **プライバシー3段階ルールの判定ロジックの置き場所**(ViewerContext・否定形テスト)は `/ddd-review` の担当。本レビューは「API が返した判定結果を UI がどう見せているか」だけを見る
- **機械判定できるもの**(lint / stylelint / 型 / フォーマット / VRT)は CI が担保する。VRT は見た目の差分検出であり使用性は判定しないため、スナップショットが green であることを適合の根拠にしない

## 手順

1. `git diff main...HEAD --name-only` で変更範囲を確認し、上記の起動条件に該当するか判定する
2. `ux-reviewer` サブエージェントを起動し、以下を渡す:
   - 変更ファイル一覧(またはレビュー対象の diff 範囲)
   - 関連する Issue 番号と受け入れ条件(あれば)
   - 追加・変更した画面が**どの状態に到達しうるか**分かっていれば添える(その月にデータが無い場合・相手の個人費用を表示する場合・通信が失敗する場合など)
3. 画面を新規追加した差分では、以下が漏れなくレビューされていることを確認する:
   - `ローディング` `空` `エラー` の3状態がすべて実装されているか(`docs/design/usability.md` §1-1)
   - 内容が差し替わる領域に `role="status"` があるか(同 §8-4)
   - フォームがある場合、`<label>` が `htmlFor` で関連付けられ、金額入力が `type="text"` + `inputMode="numeric"` か(同 §8-3 / §4-1)
4. レビュー結果を **must-fix** / **suggestion** に分けてユーザーに提示する
5. must-fix は必ず修正する。**suggestion も原則その場で修正する(デフォルトは対応)**。修正後は `/verify` を再実行して green を確認する(`packages/web` の見た目が変わる修正では VRT スナップショットの更新まで含めて green にする)
6. 例外として、以下のいずれかに該当する suggestion のみ見送ってよい:
   - 修正範囲が今回の diff を大きく超える(別リファクタリングが必要)
   - 設計判断の変更を伴い、ユーザーの意思決定が必要
7. 見送る suggestion は黙って放置せず、理由を添えてユーザーに提示したうえで GitHub Issue 化して追跡する(その場で `gh issue create` する。`needs-decision` を付けて `/decide` に接続する)

## 特に落とせない指摘

次の4つは、見落とすと利用者が「アプリが壊れている」と受け取るか、取り消せない操作を誤って実行するか、支援技術の利用者が操作の結果を知れない。指摘が出た場合は suggestion であっても見送らない:

- **状態の欠落**(`docs/design/usability.md` §1-1)— 取得失敗時に何も表示されない画面は、利用者から見て白紙と区別できない
- **権限で見えない値の黙った空表示**(同 §2-1 / §2-2)— 相手の個人明細が空欄・ハイフンで出ると、意図的な非公開ではなく不具合・登録漏れに見える
- **破壊的操作の確認欠落と影響の非表示**(同 §3-1 / §3-2)— 取引削除・最終確定・マスタ削除のリマップは取り消せない
- **差し替わる領域の通知欠落**(同 §8-4)— 月の切り替えでグラフが空状態に変わっても読み上げが発生しない。共通部品(`EmptyState` / `LoadingState` / `ErrorState`)を使えば通知が付くため(#341 / #421)、これらを使わずに空・ローディング・エラーを書き起こしている差分は**必ず指摘する**(下記)

## 既知の未対応を増やさない

`docs/design/usability.md` §9 に、規範を新設した時点で既存実装が満たしていない箇所が11件記録されている(`<label>` の関連付けが無い、タップターゲットの最小サイズが未定義など)。

本レビューの目的は、これらを**新しい画面で繰り返さないこと**にある。差分が触れていない既存箇所は指摘しないが、**新しく追加した画面・部品が §9 と同じ違反を犯している場合は新規指摘として扱う**(`ux-reviewer` 側にも明記済み)。

とくに **差し替わる領域の通知(§8-4)は特例**で、共通部品を使わずに書き起こすと通知が抜けたまま増え続ける。差し替わる領域を新設・変更する差分では必ず新規指摘とするよう `ux-reviewer` に指示している。

§9 の項目そのものを解消する変更を行った場合は、`docs/design/usability.md` §9 の該当行を削除する差分を含める。
